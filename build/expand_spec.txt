四、扩写方法：锚点插入，不是重写
------------------------------------------------------------
- 原稿的「现场」「误判」「自检清单」「一句话总结」，以及所有 `## X.Y` 标题，
  **一字不动保留**（尤其小节编号绝对不能改）。
- 在现有 `##` 小节之前、或小节内部，插入新的 `### 小节标题` 与段落。
  第 6–8 章就是这么做出来的，照它们的形态来。
- 新增内容一律用 `###`（三级标题），**不要新增 `##` 大节**，否则会打乱
  全书编号与自动生成的目录。
- 推荐做法：写一段 Python 脚本，用 (锚点字符串, 新增文本) 列表逐处
  s.replace(锚点, 新增文本 + 锚点, 1)，并 assert 每个锚点都存在。
  脚本只用于落盘，不要留在产物里。
- 每章新增 3–6 个 `###` 小节，合计约 2500–3500 汉字。

五、新增内容必须是「实料」（质量红线）
------------------------------------------------------------
严禁铺陈、严禁把原话换个说法再讲一遍。每章新增内容至少覆盖以下 8 类中的 4 类：

1. 可量化推演：用真实数字算出结论（Little's law、池容量公式、吞吐上限、
   超时预算、QPS×耗时、放大倍数）。必须有算式 + 结果 + 一句业务含义。
2. 源码/机制链路：框架或中间件内部到底发生了什么（类名、方法名、关键字段），
   用 ASCII 时序图或流程图画出来。
3. 可运行验证：一段 JUnit / Shell / SQL / 配置，读者复制就能证伪某个结论。
4. 对照表：把易混淆概念横着摆开，每格给「判据」而不是「定义」。
5. 取证命令序列：线上出问题时按什么顺序敲哪几条命令、看输出里哪个字段。
6. 版本区间：结论适用于哪个版本（Boot 3.x / JDK 17–21 / MySQL 8.0 / Redis 7…），
   哪些点升级会漂移。
7. 交叉引用：用「第 N 章」指向本书其他章，把 27 章串成一条线
   （例：连接池 ↔ 第 4 章、传播行为 ↔ 第 6 章、行锁 ↔ 第 14 章）。
8. 一个反常识点：每章至少一句「多数人以为 X，实际是 Y」，并给出理由。

六、技术准确性（最重要，高于文采）
------------------------------------------------------------
- 不许编造 API 名、配置 key、默认值、错误码、异常类名。
- 拿不准的，写成「需在自己的版本上验证」，不要写成定论。
- 主动挑出原稿里「看着对、其实错」的表述并修正，在修正处补一小段
  说明为什么错。范例：第 7 章原写「@Transactional(timeout=3) 是整个方法的
  硬上限」，实际只在申请连接/执行语句时检查，HTTP 阻塞期间不检查。
- 代码里可用 ❌ / ✅ 标记（渲染管线会转成印刷体 ✕ / ✓）；正文里也用这两个符号。
- 中文用简体；引号用中文全角；代码、配置、路径里的引号一律 ASCII 直引号。

------------------------------------------------------------

  words: 改为脚本实测汉字数，格式 `words: 5233   # 汉字计数，由脚本实测`
  其余 front-matter 字段（book/volume/chapter/order/title/sources）一律不动。
