# 第二十章　积压：从 10 万到 0 的 40 分钟

> 卷四 · 异步与峰值

**本章要回答**：堆积报警了，第一件事是扩容消费者吗？

**本章你能带走**
- 一个前置判断：**很多"积压"是假象，扩了也没用**
- 一个扩容天花板：**有效上限 = 队列数，超过纯属浪费**
- 一套处置顺序：扩容 → 转发 → 丢弃，代价依次上升

**难度构成**：本章主线【必读】；含【进阶】深挖 1 处；章末「延伸」小节放支线深挖与知识库指针。

## 20.1　现场：扩了 8 个消费者，位点不动

凌晨两点告警：订单消息堆积 12 万条。

值班同学按手册操作：消费者从 4 个扩到 12 个。**半小时后，堆积 15 万条，还在涨。**

扩容无效，说明问题不在消费能力。

**当时怎么误判的**：凌晨两点告警，第一反应是「消费者挂了或卡死」——看了眼监控，单个消费者 TPS 还是 200，不像挂了；又怀疑「是不是 topic 被限流」，查了 Broker 流控也没触发。在「再扩 8 个」和「回滚扩容」之间犹豫时，有人随口问了句「队列数多少」，一查 `QueueCount: 4`，才明白扩的 8 个全是空转。这一句提问省了后面两小时瞎折腾。

查了三件事：

**① 消费 TPS 是多少？**

从监控看，单个消费者的 TPS 一直是 200，跟扩容前一模一样。12 个消费者总 TPS 应该 2400，但实际只有 200——**说明只有 1 个消费者在干活**。

**② 队列数是多少？**

```bash
sh mqadmin topicStatus -n nameserver:9876 -t order-topic
# QueueCount: 4
```

**队列只有 4 个。** RocketMQ 的并发消费按队列分配，一个队列只能被一个消费者消费（同一消费组内）。所以：

> **消费者数量超过队列数时，多出来的消费者是空闲的。**
> 4 个队列 → 最多 4 个消费者有效 → 扩到 12 个，8 个在空转。

**③ 扩容队列不就行了？**

不行。**给已有 topic 扩容队列，会破坏顺序消息**（第 21 章），而且新队列的数据是新的，老队列的积压还在。

所以"扩消费者"之前，必须先看队列数。**这是积压处置的第一个坑：以为加机器就能解决，实际撞到了分区数的天花板。**

### 【必读】Lag 不是一个数：按分区求和与取最大

20.1 的现场说「堆积 12 万」，但这个值怎么算出来的，决定了后面所有处置对不对。**Lag 从来不是「最新位点减消费位点」这么一次相减**，分区是各自独立的计数器：

```
Lag(group, topic) = Σ over 每个分区 p ( LogEndOffset(p) − CommittedOffset(p) )
告警看的是 max over p ( ... )，以及 dLag/dt 的符号
```

**多数人以为 Lag 是简单相减，实际总 Lag 会把单个分区的堆积摊薄到所有分区上。** 12 个分区里 11 个 lag 为 0、1 个 lag 为 12 万，总 Lag 仍是 12 万，可平均到每个分区只有 1 万——按平均值设阈值就漏了。更麻烦的是：扩容到 12 个消费者也没用，因为那 12 万条全压在一个分区上，一个分区同一时刻只能被组内一个消费者消费，剩下 11 个实例全在空转。

```bash
# 逐分区看 Lag，而不是只看控制台的 Diff Total
kafka-consumer-groups.sh --bootstrap-server kafka1:9092 \
  --group order-consumer --describe
# TOPIC  PARTITION  CURRENT-OFFSET  LOG-END-OFFSET  LAG     CONSUMER-ID
# order  0          982300          1102300         120000  c1-...   ← 全堆在这
# order  1          1102280         1102300         20      c2-...
# order  2          1102295         1102300         5       c3-...
```

读输出看三列：`CONSUMER-ID` 为空说明该分区根本没分到消费者；`LAG` 为 0 但 `CURRENT-OFFSET` 长时间不动，是 20.2 要讲的假象；某分区 `LAG` 独高、其余接近 0，是分区倾斜或热 key，扩容解决不了，得查生产端的 key 分布。

还得分清两个位点：`position` 是内存里「下一条要拉」的位置，`committed offset` 是提交到 `__consumer_offsets` 的位置。自动提交被关掉后，处理已经推进了 `position`、却没提交 `committed`，此时进程重启会从旧的 `committed` 回退——**表现是「消息又来了一遍」，是重复不是丢失**（第 18 章、第 19 章）。把它误判成积压，会去扩一批根本不需要的消费者。`--describe` 的列名随客户端版本略有差异，需在自己的版本上核对。

## 20.2　先判断：是真积压还是假象

RocketMQ 有一个非常反直觉的行为：

> **被 TAG / SQL92 过滤掉的消息，也计入堆积量。**

也就是说，如果你的消费者订阅 `TAG_A`，而 topic 里有 10 万条 `TAG_B` 的消息，监控上会显示"堆积 10 万"——**但那些消息本来就不该被你消费**。

判断方法，两个指标：

| 指标 | 真积压 | 假象 |
|---|---|---|
| 消费位点（offset） | 不动 | **持续推进** |
| 消费 TPS | 掉到 0 或极低 | **正常** |

**位点在推进 = 消息在被消费 = 堆积量只是"过滤掉的那部分"。** 这种情况不需要处置，只需要修监控口径。

第二个假象：**死信队列/重试队列的堆积**被算进了主 topic。查一下 `%RETRY%` 和 `%DLQ%` 的堆积量，它们是独立 topic。

### 【必读】扩容的算式，与「扩了也不动」的四个根因

扩消费者之前先算四步，比拍脑袋加机器省半小时：

```
① 所需并发 C = 峰值生产 TPS × 单条平均耗时(s)
② 单实例开 T 个消费线程 → 实例数 N = ceil(C / T)
③ 硬约束：N ≤ 分区数 P，且 concurrency ≤ P
④ 反推分区数：P ≥ C / T，留 30% 余量 → P ≈ 1.3 × C / T
```

代一组真实数字：峰值 2000 TPS、单条 50ms，得 `C = 2000 × 0.05 = 100` 并发；单实例 20 线程，`N = 5` 个实例；分区数至少 5，建议 8。20.1 的现场是 4 个队列扩到 12 个消费者，有效只有 4 个、8 个空转，正撞第 ③ 条。

还有一个比扩容更该先算的式子——**追平时间**：

```
T_clear = 当前积压量 / (消费 TPS − 生产 TPS)
```

现场 12 万条积压、消费 200 TPS、生产 250 TPS，分母是 **−50**，追平时间为负，意思是**永远追不平**。这解释了「扩了半小时，堆积从 12 万涨到 15 万」：只要消费 TPS 不高于生产 TPS，积压就是数学上不收敛的，跟机器数量无关。要让分母转正，先把单条耗时降下来，或临时降生产。

四个「扩了也不动」的根因，按排查顺序：

| 根因 | 现场信号 | 取证 | 为什么扩了没用 |
|---|---|---|---|
| ① 超过分区/队列数上限 | `concurrency > P`，部分 `CONSUMER-ID` 为空 | `--describe` 看分配 | 多出来的实例分不到队列，纯空转，还多一次 rebalance |
| ② 下游是瓶颈（DB / HTTP） | CPU 空闲、单条耗时长、连接池打满 | `jstack`、`SHOW PROCESSLIST` | 扩容只是把慢复制 N 份，DB 先被打挂（第 7 章） |
| ③ rebalance 风暴 | lag 锯齿状、日志频繁 rebalance | `kafka-consumer-groups.sh --describe --members` | 每加一台机器触发一次全组暂停，位点不推进 |
| ④ 毒消息 / 反序列化失败卡死单分区 | 某分区 lag 独高、其余为 0 | 消费日志里的反序列化异常 | 该分区永远轮不到别的消费者，加多少实例都无效 |

第 ③ 条最反直觉：**在 rebalance 风暴期间加消费者，等于给抖动添柴**——扩容本身就是一个触发 rebalance 的动作。这时候正确的第一步不是加机器，是先把 `max.poll.interval.ms` 超时和 GC 停顿压下去（第 2 章的重试风暴是同一条链）。第 ④ 条要靠 `ErrorHandlingDeserializer` 加死信 Topic 兜住脏数据，否则那个分区会一直卡到天亮。

**扩消费者是处置顺序里排第二的动作，不是第一；先算清楚 C 与 P，再决定加不加。**

把四个根因压成一份能照着敲的取证序列，比在群里猜快得多：

```bash
# ① 消费者数 vs 分区数：先看天花板
kafka-topics.sh --bootstrap-server kafka1:9092 --describe --topic order \
  | grep -E 'PartitionCount|ReplicationFactor'
kafka-consumer-groups.sh --bootstrap-server kafka1:9092 \
  --group order-consumer --describe --members      # 看每个实例分到几个分区

# ② 下游是不是瓶颈：线程停在哪
jstack -l <pid> | grep -A 8 'ConsumeMessageThread_'   # 停在 SocketInputStream / getConnection 即下游慢
# MySQL 侧
SHOW STATUS LIKE 'Threads_running';
SHOW PROCESSLIST;

# ③ rebalance 是否频繁
grep -c 'rebalance' consumer.log

# ④ RocketMQ 队列数与堆积分布
sh mqadmin topicStatus -n nameserver:9876 -t order-topic
sh mqadmin consumerProgress -n nameserver:9876 -g order-consumer
```

`--members` 里 `CONSUMER-ID` 为空的分区就是没分到人的；`jstack` 里大量线程停在 `SocketInputStream.read` 或 `HikariPool.getConnection`，说明瓶颈在下游而不是消费者数量（第 7 章的取证顺序在这里同样适用）。

扩容本身也要算：一次 `kubectl scale --replicas=12` 会触发一次全量 rebalance，一次加 2 个、观察 lag 斜率变负后再加下一批，抖动小得多。**扩容前先确认「分区数减当前消费者数」还有多少余量**，余量为 0 时加机器只是给 rebalance 添柴。

最后一个数值得记住：积压量 = `(生产 TPS − 消费 TPS) × 持续时间`。现场生产 250、消费 200，差 50 条/秒，半小时正好攒出 9 万条，和 12 万涨到 15 万对得上。**这个式子把「积压」从监控上的一个数字，变成了两个速率的差值积分**，也说明为什么「消费 TPS 与生产 TPS 的差」（20.5 第二个指标）比堆积量更早报警：差值一出现，积分就注定要涨，只是还没堆到阈值。

顺带把「扩了也不动」的第五种收进来：20.2 说的 TAG 过滤假象。位点持续推进、消费 TPS 正常，只是堆积量里混了本不该被消费的消息——这种情况扩了当然不动，因为它根本不需要动。

## 20.3　真积压：处置顺序

按"代价从小到大"排，**不要一上来就用最贵的手段**。

### 【必读】第一步：找消费慢的根因

在扩容之前，先花五分钟看消费者在干什么。四个高频原因：

| 原因 | 表现 | 处理 |
|---|---|---|
| 消费逻辑里有循环查库（N+1） | 单条消息耗时 200ms+ | 批量查、加缓存 |
| 同步调用下游接口 | 消费耗时 = 下游 RT | 改异步、加超时 |
| 单条处理而非批量 | 每条一次 DB 往返 | 批量消费（`consumeMessageBatchMaxSize`） |
| 消费者被限流/线程数太小 | CPU 空闲但 TPS 上不去 | 调 `consumeThreadMax` |

**如果消费逻辑本身很慢，扩容只是把慢复制 N 份，DB 反而更容易被打挂。**

### 【必读】第二步：扩容到队列数上限

```java
// 消费线程数（不是实例数）
consumer.setConsumeThreadMin(20);
consumer.setConsumeThreadMax(64);
```

注意两个"扩容"是不同的：

- **加实例**：受队列数限制（一个队列一个消费者）
- **加线程**：受消费者内部线程池限制，单实例能扛更多

**在队列数已经打满的情况下，加线程仍然有效**——一个消费者可以开多个线程消费同一个队列（顺序会乱，见第 21 章）。这与第 7 章"等锁型故障加线程只是给排队队伍扩容"的负收益不同——此处队列数已封顶，加的是消费并发度，属互补场景（加线程在"等锁/等连接"瓶颈为何是负收益，见第 7 章）。

### 【必读】第三步：临时转发到"大队列" topic

如果积压量太大（比如百万级），正常消费要几小时，而业务等不了：

```
① 起一个临时消费者，不做业务处理，只把消息搬到新 topic（新 topic 有 32 个队列）
② 新 topic 的消费者用 32 个实例并行消费
③ 消费速度提升 N 倍（N = 新队列数 / 老队列数）
```

代价：多一次消息搬运、顺序全乱、需要额外机器。**这是"应急手段"，不是常态方案。**

### 【必读】第四步：跳过非核心消息

如果积压的是日志、埋点、通知这类"丢了不影响钱"的消息：

```java
// 判断消息年龄，太老的直接跳过
if (System.currentTimeMillis() - msg.getStoreTimestamp() > 3600_000) {
    log.warn("skip stale message, born at {}", msg.getStoreTimestamp());
    return SUCCESS;                        // 丢弃，保核心链路
}
```

**这是唯一"主动丢消息"的合法场景**：消息本身可丢，且延迟消费已经失去意义（三小时前的"支付成功"短信，现在发出去只会打扰用户）。

前提是**你明确知道这类消息可以丢**，并且写进了文档。

### 【必读】临时转发：把 4 个队列搬到 32 个队列

20.3 第三步说了思路，这里给出能跑的形状。核心是**临时抬高队列数这个天花板**，而不是提高业务处理能力：

```bash
# ① 建一个 32 队列的临时 topic（-w 为写队列数，参数名需按版本验证）
sh mqadmin updateTopic -n nameserver:9876 -t order-topic-tmp -w 32 -r 3

# ② 起搬运工消费者组，用新 consumerGroup 从头读，避免影响原组位点
# ③ 临时 topic 的消费者批量拉取、直接落「待处理表」，离线任务再补业务
# ④ 追平后切回原 topic，删除临时 topic，回滚所有临时扩容
```

```java
// 搬运工：只搬运，不碰业务，原样透传幂等键给下游
@RocketMQMessageListener(topic = "order-topic",
        consumerGroup = "relay-to-tmp-group",
        consumeMode = ConsumeMode.CONCURRENTLY, consumeThreadNumber = 4)
public class RelayConsumer implements RocketMQListener<MessageExt> {
    private final RocketMQTemplate template;

    @Override
    public void onMessage(MessageExt m) {
        Message<String> out = MessageBuilder
                .withPayload(new String(m.getBody(), StandardCharsets.UTF_8))
                .setHeader(RocketMQHeaders.KEYS, m.getKeys())   // 业务键不能丢（第 19 章）
                .build();
        template.syncSend("order-topic-tmp", out);
    }
}
```

加速比有个简单算式：`加速比 ≈ 新队列数 / 老队列数 = 32 / 4 = 8 倍`。12 万条按原 200 TPS 要 600 秒，8 倍后约 75 秒。但**这 75 秒只是搬完，不是处理完**——业务仍由离线任务按数据库能承受的速率补。

代价必须写进预案：顺序全丢（第 21 章）、消息重复（第 19 章要求消费端幂等）、多一份存储、临时 topic 用完要清理。**转发不是「提高消费能力」，是「把队列数这个天花板临时抬高」，它买的是时间，不是吞吐；强有序业务禁用。**

## 20.4　消费端反压：别把积压变成雪崩

积压时最容易犯的错：**消费者拼命拉消息，把下游打死。**

```java
// ❌ 无限制拉取：一次拉 1000 条，全部并发处理 → 下游瞬间被打穿
consumer.setPullBatchSize(1000);
consumer.setConsumeThreadMax(200);
```

正确的做法是**让消费速率跟下游容量对齐**：

```java
// ✅ 拉取量 × 线程数 ≈ 下游能承受的并发
consumer.setPullBatchSize(32);
consumer.setConsumeThreadMax(20);      // 32 × 20 = 640 并发上限
```

同时给下游调用设超时和熔断——**积压的时候，下游通常也已经很紧张了**。

### 【必读】反压：让拉取速率跟下游容量对齐

20.4 给了「拉取量 × 线程数 ≈ 下游并发」这句话，把它补成可算的约束。积压时下游通常也已经很紧张，三条约束缺一条就会把积压变成雪崩：

```
约束一  下游并发上限 ≈ 连接池大小 / 单次调用耗时(s)
        例：Hikari maximumPoolSize=20、单次写 20ms → 20 / 0.02 = 1000 次/秒
约束二  pullBatchSize × consumeThreadMax ≤ 下游并发上限
约束三  max.poll.records × 单条耗时 < max.poll.interval.ms（默认 300s）
```

按约束一算，`pullBatchSize=1000 × consumeThreadMax=200` 是 640 量级的瞬时并发，乘上每秒 50 次就是 3 万多次/秒，是下游 1000 次/秒的 30 倍——**拉得越快，下游越慢，lag 越降不下来**。约束三则是 Kafka 特有的坑：500 条 × 0.7 秒 = 350 秒，超过 `max.poll.interval.ms` 的 300 秒，整批被踢出组、触发 rebalance，积压反而更糟；降到 200 条 × 0.7 秒 = 140 秒才安全。

```java
// ❌ 一次拉 1000 条 × 200 线程：瞬时打穿下游，还会整批超时被踢
consumer.setPullBatchSize(1000);
consumer.setConsumeThreadMax(200);

// ✅ 按下游容量反推：单条 20ms、下游 1000 次/秒 → 并发上限 20，留一半余量
consumer.setPullBatchSize(20);
consumer.setConsumeThreadMax(20);      // 20 × 20ms = 400 并发，安全
```

`fetch.min.bytes` 与 `fetch.max.wait.ms` 控制拉取节奏，RocketMQ 的 `consumeMessageBatchMaxSize`、RabbitMQ 的 `prefetch` 同理。**反压不是限流自己，是保护下游**：下游变慢、消费超时、调用方重试，负载被放大成平方（第 2 章），这时候任何「拉满」的配置都在给雪崩加油。

## 20.5　预防：三个必配的监控

积压是可以提前发现的，前提是你看对了指标：

| 指标 | 告警阈值 | 说明 |
|---|---|---|
| **堆积量（Diff Total）** | > 1 万，或持续上涨 5 分钟 | 最直接的信号 |
| **消费 TPS 与生产 TPS 的差** | 消费 < 生产 持续 5 分钟 | **这个比堆积量更早** |
| 单条消息处理耗时 P99 | > 500ms | 提前发现"消费变慢" |

第二个指标最有价值：**当生产 TPS 稳定高于消费 TPS 时，积压是必然的**，只是还没堆到告警阈值。这个信号通常比堆积量告警早 10–30 分钟。

再补一个容量规划的习惯：

> **消费能力（TPS）应该是峰值生产 TPS 的 2–3 倍。**
> 平时跑在 30% 水位，才有应对突发和"消费变慢"的余量。

### 【必读】三个必配监控：指标名、阈值与告警条件

那张表给了口径，这里补上能直接粘进告警配置的**具体指标名与阈值**。指标名随 exporter 与版本不同（Burrow、kafka_exporter、JMX、RocketMQ Exporter 各有命名），上生产前需在自己的版本上核对：

| # | 指标 | 具体名（示例） | 告警阈值与条件 |
|---|---|---|---|
| 1 | 消费 Lag | `kafka_consumergroup_lag`、`kafka_consumer_fetch_manager_records_lag_max`；RocketMQ `rocketmq_group_diff`（Diff Total） | `> 10000` **且** `rate(lag[5m]) > 0` 持续 5 分钟 |
| 2 | 生产 / 消费 TPS 差 | `rocketmq_consumer_tps` vs `rocketmq_producer_tps`；`kafka_consumer_fetch_manager_records_consumed_rate` | `consumer_tps < producer_tps` 持续 5 分钟，比堆积量早 10~30 分钟 |
| 3 | 单条处理耗时 P99 | `rocketmq_consumer_consume_rt`；自定义 `consumer_handle_seconds{quantile="0.99"}` | `> 0.5s` |

再补两个「不出事也想不起来」的：`kafka_server_replicamanager_underreplicatedpartitions > 0` 持续 5 分钟（ISR 收缩，`acks=all` 正在退化，第 18 章），以及 `%DLQ%` 堆积量 > 0 立即告警。

```yaml
groups:
- name: mq-backlog
  rules:
  - alert: ConsumerLagGrowing
    expr: kafka_consumergroup_lag > 10000
      and rate(kafka_consumergroup_lag[5m]) > 0
    for: 5m
    labels: { severity: warning }
    annotations:
      summary: "消费组 {{ $labels.group }} lag 持续上涨"
  - alert: ConsumeSlowerThanProduce
    expr: rocketmq_consumer_tps < rocketmq_producer_tps
    for: 5m
    labels: { severity: critical }
```

**「lag > 阈值且增长率为正」这个「且」不能省**：常驻型消费组 lag 应接近 0，但任务型（批处理）消费组在任务间隙增长是正常现象，两类告警规则必须分开，否则每天夜里误报一轮，告警就被静音了。


本章结论对应 **Kafka 3.x/4.x、RocketMQ 4.9+/5.x、Spring Kafka 3.x**。`max.poll.interval.ms`（默认 300s）、`session.timeout.ms`（默认 45s）、RocketMQ 队列数与 `consumeThreadMax` 的默认值都需按版本验证；Kafka 4.0 起 KIP-848 新协议（客户端 `group.protocol=consumer`）让 rebalance 只影响变动分区，扩容的副作用比旧协议小，这是升级时值得重新测一轮的点。

## 20.6　自检清单

- [ ] 知道每个 topic 的**队列数**，且消费者实例数不超过它（或已知会浪费）
- [ ] 积压告警区分"真积压"（位点不动）和"假象"（TAG 过滤）
- [ ] 消费 TPS 有监控，且与生产 TPS 对比
- [ ] 消费逻辑里没有循环查库/同步调下游
- [ ] 拉取批量 × 线程数与下游容量匹配，不是越大越好
- [ ] 有"临时转发 + 并行消费"的预案（脚本或开关）
- [ ] 明确哪些消息可以丢弃（写进文档）
- [ ] 消费能力按峰值生产 TPS 的 2–3 倍规划

## 20.7　一句话总结

> 积压的本质永远是"生产 > 消费"，只有三种解法：**提高消费、降低生产、丢弃**。
> 扩容只解决第一种，而且它的天花板是队列数。
