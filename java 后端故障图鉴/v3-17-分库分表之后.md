# 第十七章　分库分表之后那些"查不到"

> 卷三 · 数据落地

**本章要回答**：为什么分表之后，订单列表少了几条？为什么后台统计数字对不上？

**本章你能带走**
- 一张表：分片键选错的四种代价
- 一个方法：基因法——让两个维度都能精准路由
- 一条底线：**分片之后，全局唯一 ID 必须换掉自增**

**难度构成**：本章主线【必读】；含【进阶】深挖 2 处；章末「延伸」小节放支线深挖与知识库指针。

## 17.1　现场：列表少了几条，后台数字对不上

一张订单表 2 亿行，按 `user_id` 哈希分成 16 片。上线一周后：

**问题一：后台运营的"全站订单列表"少数据。**

因为它按 `create_time` 排序分页，没有 `user_id` → **无法路由 → 只能广播到 16 片，各取 1 页，再在内存里归并**。如果每片取 10 条，归并后能不能得到真正的"前 10 条"？**不能**——第 1 片的第 11 条可能比第 2 片的第 1 条还新。

**问题二：昨天的 GMV 统计比财务少了 3%。**

因为 `SUM(amount)` 被拆成"16 片各自求和再相加"，看似没问题。但**分页时"每片取 N 条再归并"是有损的**——它只能保证"近似前 N"，永远拿不到准确的全量排序。

**问题三：客服按订单号查，查不到。**

因为分片键是 `user_id`，按 `order_no` 查没有路由依据 → 广播 16 片（一次查询变 16 次），而且如果中间件没开广播，就是直接查不到。

> **分库分表不是"表变多了"，是"从今往后每个查询都要回答一个问题：我该去哪个片？"**
> 答不上来的查询，都会变成广播或者错误。

**当时怎么误判的**：运营报"列表少数据"时，第一反应是"主从延迟，从库还没同步到"（查 `Seconds_Behind_Master` 正常，排除）；又怀疑"中间件路由算错了，把数据分到别的片"（对了几条订单号，路由是对的）。最耽误时间的是"会不会 binlog 同步链路抖了一下丢了记录"——查 Canal 位点、跑对账脚本大半天，什么都没丢。最后有人把"各片 `LIMIT 10` 归并的结果"和"直接 `ORDER BY` 全量"摆在一起，才发现从第 2 页起就漏，根因是跨片分页的有损归并，不是丢数据。这一下把方向从"数据一致性"扭回"查询路由维度"，后面的优化才对路。

## 17.2　分片键选错，代价是什么

分片键的选择标准，四条，缺一不可：

| 标准 | 说明 | 反例 |
|---|---|---|
| **高基数** | 值足够多，能均匀打散 | 用 `status`（只有 5 个值）→ 严重倾斜 |
| **分布均匀** | 哈希后各片数据量接近 | 用 `tenant_id`（大客户占 80%）→ 热点片 |
| **覆盖绝大多数查询** | 90% 的查询都带这个条件 | 订单表用 `order_no` → 按用户查全广播 |
| **不可变** | 值不能改 | 用 `phone` → 换号就要迁数据 |

选错的四种代价：

1. **跨片查询**：不带分片键的查询 → 广播 N 次 → RT × N，DB 压力 × N
2. **跨片分页**：内存归并，**结果不准确**（上面的问题一）
3. **跨片聚合**：`COUNT`/`SUM` 要合并，复杂查询做不了
4. **数据倾斜**：某一片特别大，扩容也救不了（因为路由规则没变）

**订单表的标准答案是 `user_id`**，因为"我的订单"是最高频查询。但代价是"按订单号查"和"后台按时间查"都要额外处理——这就是 17.4 节要讲的。

### 【必读】分片键选错的代价：把广播放大倍数算出来

17.2 说跨片查询要广播 N 次。设分片数 `N = 16`、单片点查 `t = 5ms`。

**放大倍数**：不带分片键的查询被改写成 `N` 条 SQL，于是

```sql
-- ❌ 无分片键：广播 16 片，一次请求借走 16 个连接
SELECT * FROM t_order WHERE status = 1 ORDER BY create_time DESC LIMIT 20,10;

-- ✅ 带分片键：精准路由到单片，只占 1 个连接
SELECT * FROM t_order WHERE user_id = 10086 AND status = 1
 ORDER BY create_time DESC LIMIT 20,10;
```

```
单次 DB 工作量   = N × 1 次 = 16 次
单次 RT（并行） ≈ t + 归并开销 ≈ 5ms + 2ms = 7ms
单次 RT（串行） = N × t = 80ms        （中间件若串行下发更糟）
连接占用        = 16 个连接同时被这一个请求占住
```

Hikari 默认 `maximumPoolSize = 10`（第 4 章），一个不带分片键的请求瞬间借走 16 个连接、超过整个池子；`10 / 16 ≈ 0.6` 个并发就把池子借空，其余请求卡在 `getConnection()`（默认等 30 秒）。**它慢的不是自己，是把所有人的连接都借光了。**

再算吞吐：峰值 `Q = 2000` QPS，其中"忘了带分片键"占比 `r = 5%`，即 100 次/秒。这 100 次各放大 16 倍，等于额外 `1600` 次/秒 的 SQL：

```
DB 总 QPS = Q × (1 - r) + Q × r × N
          = 2000 × 0.95 + 2000 × 0.05 × 16
          = 1900 + 1600 = 3500 次/秒
```

**5% 的坏查询，让 DB 总负载涨了 84%**；占比 20% 时是原来的 4 倍。迷惑之处在于"QPS 没涨多少、DB CPU 却翻倍"——放大藏在每个请求内部。

| 坏味道 | 放大倍数 | 最先打满的资源 | 判据 |
|---|---|---|---|
| 无分片键点查 | N（16） | 连接池 | `Threads_connected` 逼近上限，SQL 都很短 |
| 无分片键 + 深分页 | N × (offset+limit) | 内存 / 网络 | 归并节点内存随页码涨（见 17.5） |
| 跨片 `JOIN` 未配绑定表 | 最坏 N² | CPU / 临时表 | 笛卡尔积，结果行数远大于输入 |
| 一次请求里 N 条广播串行下发 | N × RT | Tomcat 线程 | 单接口 RT 正比于 N |

> 反常识点：多数人以为"跨片查询只是慢一点"，实际它先打满的是**连接池**而不是 CPU——N 个短 SQL 同时占住 N 个连接，池子比 CPU 小一个数量级。

所以影子库压测时应捕获所有 SQL，凡 `WHERE` 里没有分片键的一律拒绝上线；放大倍数乘在每个请求上，靠"以后注意"防不住。

## 17.3　基因法：让两个维度都能精准路由

需求：既要按 `user_id` 查，又要按 `order_no` 查，都希望精准路由（不广播）。

思路：**把 `user_id` 的分片信息"藏"进 `order_no` 里。**

```
分片数 N = 16（2^4，取低 4 位）
user_id 的分片基因 = user_id % 16

生成 order_no：
  高位：时间戳 + 序列号        （保证趋势递增、全局唯一）
  低 4 位：user_id % 16        （基因）
```

这样：

```java
// 按 user_id 查：直接算
int shard = userId % 16;

// 按 order_no 查：从订单号里取出基因
int shard = (int) (orderNo & 0b1111);      // 低 4 位就是分片号
```

**两条路都能精准路由，不需要广播，也不需要额外索引表。**

前提和限制：

- 分片数必须是 2 的幂（否则取模不能位运算，且基因位长度不整）
- `order_no` 必须由你们的系统生成（外部传入的订单号藏不了基因）
- 基因位数固定 → **分片数固定，扩片要重新设计**（这又回到"一次预留足够分片"）

## 17.4　全局唯一 ID：自增必须换掉

分表之后，每张表的 `AUTO_INCREMENT` 各涨各的，必然重复。三种替代：

| 方案 | 实现 | 优点 | 缺点 |
|---|---|---|---|
| **雪花算法** | 时间戳 + 机器 ID + 序列号 | 趋势递增、本地生成、无依赖 | 依赖时钟（回拨会重复）；19 位 → 前端丢精度（第三章） |
| **号段模式** | DB 批量发号（如一次 1000 个） | 性能好、不依赖时钟 | 需一个号段服务；重启会浪费号段 |
| **Redis INCR** | 原子自增 | 简单 | 依赖 Redis；持久化配置不当会重复 |

雪花算法的两个坑必须处理：

```java
// ① 时钟回拨：直接抛错，不要"等待"或"补偿"
if (now < lastTimestamp) {
    throw new IllegalStateException("clock moved backwards, refuse to generate id");
}

// ② 机器 ID 必须唯一：K8s 里用 Pod 序号，不要用 IP 哈希（重启会变）
```

**19 位 id 传到前端会丢精度**——这是第三章的内容，分表之后会集中爆发，因为自增 id 从 10 位变成了 19 位。上线前必须配 `Long → String`。

### 【必读】雪花 ID 的时钟回拨：分类、阈值与处理

17.4 给了"回拨直接抛错"的代码，但没说为什么不能"等一下"，也没说什么样的回拨可以容忍。先分类：

| 类型 | 幅度 | 常见原因 | 能不能等 |
|---|---|---|---|
| 小幅回拨 | 几 ms ~ 几十 ms | NTP 渐进校准、虚拟机时钟漂移 | 可短等，但要上限 |
| 大幅回拨 | 秒级 ~ 分钟级 | 手工改时间、NTP 跳变、重启后 RTC 落后 | **不能等** |
| 持续回拨 | 反复发生 | 宿主机时钟源不稳定 | 换机器 / 下线该节点 |

雪花结构是 `时间戳(41bit) | 机器ID(10bit) | 序列号(12bit)`，同毫秒靠序列号去重。**"等"的风险**：等待期间机器时间仍落后于 `lastTimestamp`，此时发号会和回拨前已发的 ID 撞在同一个"毫秒+机器+序列"上，直接重复主键；而且它不报错，只有对账能发现。

分档处理：

```java
private long lastTimestamp = -1L;
private static final long MAX_WAIT_MS = 100;   // 小幅回拨最多等 100ms，按业务压测定

public synchronized long nextId() {
    long now = System.currentTimeMillis();
    if (now < lastTimestamp) {
        long drift = lastTimestamp - now;
        if (drift <= MAX_WAIT_MS) {
            waitUntil(lastTimestamp + 1);       // 小幅：等到超过上次时间戳
            now = System.currentTimeMillis();
            if (now < lastTimestamp) {          // 等完还落后 → 升级为失败
                throw new IllegalStateException("clock drift beyond wait budget");
            }
        } else {
            // 大幅回拨：直接拒绝，绝不"等待"或"用上次时间戳硬凑"
            throw new IllegalStateException("clock moved backwards, refuse to generate id");
        }
    }
    lastTimestamp = now;                        // 同毫秒 sequence++，跨毫秒归零
    return pack(now);
}
```

三条配套措施比这段 if 更重要：

1. **机器 ID 必须唯一且稳定。** K8s 里用 StatefulSet 的 Pod 序号或启动参数注入，不要用 IP 哈希——Pod 重建 IP 会变，和新 Pod 的机器 ID 撞上是重复的另一条路（17.4 已点过）。
2. **回拨要告警**（哪台机器、回拨多少 ms），连续回拨就摘节点。
3. 真要绝对不中断，换与时钟无关的号段模式（17.4 表格那一行）。

> 反常识点：多数人以为"时钟回拨等一等就过去了"最稳妥，实际等待期间发号仍在继续，重复 ID 的概率反被拉高；**对全局唯一 ID 来说，宁可短暂不可用，也不能冒重复主键的险**——后者没有报错，只有对账能发现。

版本区间：`41/10/12` 是标准 snowflake 的经典划分，各框架（ShardingSphere 5.x、UidGenerator、Leaf）位数与回拨策略不同；`MAX_WAIT_MS` 与是否允许等待务必在自己的实现上验证。

## 17.5　跨片查询的三类难题

### 【必读】跨片 JOIN

**方案一：冗余字段**（最常用）

订单表里冗余 `user_name`、`item_title`，避免 JOIN。代价是"用户名改了要同步"，但同步是异步可接受的。

**方案二：广播表**

小表（字典、配置、城市）在每个片都存一份完整副本。

**方案三：异构到 ES**

把需要复杂查询的字段同步到 ES，查询走 ES、详情回源 DB。**这是"后台多条件筛选"的标准解法。**

### 【必读】跨片分页（最容易被忽略的坑）

```sql
-- 需求：全站订单按时间倒序，第 3 页
-- 中间件做法：每片取 30 条 → 内存归并 → 取第 21~30 条
```

**这个结果其实是对的，但代价被低估了。** 每片取 `offset + limit = 30` 条（不是 `LIMIT 20,10`），全局第 21~30 条中任意一条在它自己片内的排名都不会超过 30，因此一定落在候选集里，归并后能精确取到。第 1 片的第 31 条确实可能比第 3 片的第 1 条还新，但它排不进全局前 30，丢掉不影响第 3 页；17.1 现场里"列表少了几条"说的是**每片固定只取 10 条**的中间件，那是另一种实现。

正确做法仍然只有两条，但理由要改成"成本"而不是"不可能"：

1. **带分片键**：`WHERE user_id = ?` → 单片查询，完全正确且便宜
2. **异构**：把全量数据同步到 ES / 数仓，分页走那边

**"无分片键的精确深分页"不是做不到，是代价随页码快速增长，涨到一定程度必须禁掉。** 这是成本问题，不是信息论上的不可能；把它说成"不可能"会让人放弃优化，直接翻车在深页上。本节末尾的小节把这笔账算出来。

### 【必读】跨片聚合

`COUNT` / `SUM` / `AVG` 可以各片算再合并，但要注意：

- `COUNT` / `SUM`：可以加
- `AVG`：**不能直接平均**，要 `SUM(sum) / SUM(count)`
- `DISTINCT COUNT`：几乎无解，必须异构到 ES/数仓
- `GROUP BY` + `ORDER BY` + `LIMIT`：等价于跨片分页，同样不准确

### 【必读】跨片分页的二次查询：正确，但代价随页码平方增长

先把 17.5 里那句"这个结果是错的"纠正过来：**"每片取 `offset + limit` 条再归并"是能得到精确结果的**，它只是贵。证明只要一句——

> 全局按 `create_time` 倒序排名第 `k` 的记录，在它所属分片内的排名一定 `≤ k`。
> 因为排它前面的 `k-1` 条最多全部来自这一个片，所以该片内至多有 `k-1` 条比它新。

于是取每片前 `offset + limit` 条，全局前 30 条一定全在候选集里，归并后取第 21~30 条**精确无误**。17.1 现场"列表少了几条"说的是**每片固定只取 10 条**（`LIMIT 0,10`）那种实现，它对第 1 页成立、对第 2 页起就漏，与"每片取 30 条"不是一回事。

真正的问题是代价。设分片数 `N = 16`、每页 `L = 10`、页码 `p`（`offset = (p-1)L`）：

```
每片取回行数   = offset + L = p·L
N 片总回传行数 = N · p · L
归并端候选集   = N · p · L 行，要做一次全局排序
```

代数字：

| 页码 p | 每片取回 | 16 片总回传 | 相对第 1 页 |
|---|---|---|---|
| 1 | 10 | 160 | 1× |
| 10 | 100 | 1,600 | 10× |
| 100 | 1,000 | 16,000 | 100× |
| 1000 | 10,000 | 160,000 | 1000× |

**总数据量随页码 `p` 线性增长**，已经够呛；但用户是"一页一页翻过去"的，从第 1 页翻到第 `p` 页的**累计传输行数**是

```
Σ(i=1..p) N·i·L = N·L·p(p+1)/2 ≈ N·L·p²/2
```

这就是"平方增长"：单次成本线性，累计成本平方。代 `N=16, L=10, p=1000` ≈ 8000 万行被搬过内存。**深分页必须在网关禁掉**（`page > 100`），或改游标分页 `WHERE create_time < 上一页最后一条`，回传量恒为 `N·L`，与页码无关。

**④ 跨片聚合的近似方案**：

| 聚合 | 能否精确 | 做法 | 误差/代价 |
|---|---|---|---|
| `COUNT` / `SUM` | ✅ 精确 | 各片求和再相加 | 无 |
| `AVG` | ✅ 精确 | `SUM(sum)/SUM(count)`，**不是各片 AVG 再平均** | 无 |
| `COUNT DISTINCT` | ❌ 精确几乎无解 | 各片 `PFADD` 到 HyperLogLog 再 `PFMERGE` | 标准误差约 0.81%（需在自己的版本上验证） |
| `P99` / 中位数 | ❌ | t-digest / 各片直方图合并 | 尾部误差；精确需全量拉到数仓 |
| `GROUP BY ... ORDER BY ... LIMIT` | ❌ | 等价于跨片分页 | 同上，改走 ES / 数仓 |

17.1 那个"GMV 少 3%"的锅不在 `SUM`（可加、精确），而在按有损取样结果求和；ES / 数仓异构承载的正是 `DISTINCT`、分位数、深分页。

## 17.6　扩容：唯一安全路径

分片数定下来之后，"加两片"是最危险的操作，因为 `user_id % 16` 变成 `% 18` 会导致**几乎所有数据都要搬迁**。

唯一安全的路径，五步，全程不停机：

```
① 双写：新老规则同时写（老库 + 新库）
② 迁移：历史数据按新规则搬到新分片
③ 校验：逐条比对（行数 + 校验和 + 抽样内容）
④ 灰度切读：按 user_id 灰度，1% → 10% → 50% → 100%
⑤ 下线老库：观察一周无异常再停双写
```

关键在第 ③ 步——**没有校验的迁移等于赌博**。校验脚本要能回答"哪条数据不一致"，而不只是"有不一致"。

**更省事的做法：一开始就预留足够分片。** 分 64 片但只部署 4 个库（每库 16 片），扩容时只是把片从一个库挪到另一个库——**不用改路由规则，只挪数据**。这是业内最常用的策略。

## 17.7　什么时候不该分表

最后这一段是提醒。分库分表的成本极高，先问三个问题：

1. **索引优化过了吗？** 80% 的"单表太大"其实是缺索引或 SQL 写得差
2. **读写分离做了吗？** 读多写少的场景，一主多从能撑很久
3. **真的超过阈值了吗？** 单表 500 万行 / 2GB 是**参考值**，不是红线。字段窄、索引少，2000 万行也能跑得很好

**分表是最后手段，不是性能优化的第一步。** 见过太多"为了性能分表"，结果引入跨片查询、分布式事务、数据一致性，整体可用性反而下降。


（什么时候不该分表的量化判据、取证命令与阈值清单，见章末附录。）
## 17.8　自检清单

- [ ] 分片键满足四条标准（高基数、均匀、覆盖主查询、不可变）
- [ ] 分片数是 2 的幂，且预留了扩容空间
- [ ] 全局 ID 用雪花/号段，不用自增；前端配置了 `Long → String`
- [ ] 需要按第二维度查的，用了基因法或索引表，不是靠广播
- [ ] 无分片键的分页/聚合走 ES 或数仓，不在 DB 里硬算
- [ ] `AVG` 用 `SUM/COUNT` 计算，不是各片平均再平均
- [ ] 扩容走"双写 → 迁移 → 校验 → 灰度 → 下线"五步
- [ ] 确实评估过"不分表"的可行性（索引、读写分离）

## 17.9　一句话总结

> 分库分表把"一次查询"变成了"一次路由决策 + N 次查询 + 一次归并"。
> 你换来的写入能力，要用**查询灵活性**去支付——这笔账要在动手前算清楚。

### 基因法的位运算实现：一份可运行示例

17.3 给了思路，这里给一份能直接跑的实现，把"低位清零 → 写入基因 → 两条路都精准路由"三步钉死。

```java
public final class GeneRouter {
    private static final int  SHARD_BITS = 4;                        // 16 = 2^4 片
    private static final long SHARD_MASK = (1L << SHARD_BITS) - 1;   // 0b1111

    /** 雪花 ID 低 4 位清零后，嵌入 user_id 的分片基因 */
    public static long nextOrderNo(long userId, long snowflakeId) {
        long base = snowflakeId & ~SHARD_MASK;      // ① 低位清零，不破坏高位趋势递增
        return base | (userId & SHARD_MASK);        // ② 写入基因
    }

    /** 两条查询路径落在同一片，靠的是同一个掩码 */
    public static int shardByUser(long userId)     { return (int) (userId & SHARD_MASK); }
    public static int shardByOrderNo(long orderNo) { return (int) (orderNo & SHARD_MASK); }

    public static void main(String[] args) {
        long userId = 10086L;
        long snow   = 7_321_123_456_789_012_345L;   // 模拟一个雪花 ID
        long no     = nextOrderNo(userId, snow);
        System.out.printf("userId=%d  orderNo=%d%n", userId, no);
        System.out.printf("shard(user)=%d  shard(orderNo)=%d%n",
                shardByUser(userId), shardByOrderNo(no));
        // shard(user)=6  shard(orderNo)=6  → 同一片
        assert shardByUser(userId) == shardByOrderNo(no);
    }
}
```

跑 `javac GeneRouter.java && java -ea GeneRouter`，断言通过即证明两维路由一致；`& ~MASK` 位运算与 `orderNo % 16` 等价（x 非负时），省一次整数除法。

三个前提：

| 前提 | 为什么 | 违反后的代价 |
|---|---|---|
| 分片数是 2 的幂 | 基因位数 = `log2(N)` 必须是整数 | 取模与位运算不等价，路由错片 |
| 订单号由本系统生成 | 外部传入的号藏不了基因 | 按订单号查仍得广播 |
| 基因位数固定 | 16 片 4 bit、32 片 5 bit | 扩到 32 片时旧数据低 4 位全是旧基因，**全量重算** |

最后一条把"分片数"焊死进了 ID：17.6 的"一次预留足够分片"对基因法是硬约束——要么按 64 片（6 bit）预留，要么接受扩片时重写所有历史 ID。

基因法借走的是雪花 ID 的序列号低位（第 17.4 章同源）：12 bit 扣掉 4 bit 只剩 8 bit = 256 个/毫秒，高并发前先算够不够。

### 扩容五阶段的验收表与回切点

17.6 给了五步流程，但线上真正决定"敢不敢切"的是每一步的**验收项**和**回切点**。把流程摊成阶段表，双写期间每一步都可回退：

| 阶段 | 动作 | 读流量归属 | 验收项（不达标不进下一阶段） | 回切点 |
|---|---|---|---|---|
| ① 双写 | 老库 + 新库同时写，影子写失败进补偿队列 | 100% 老库 | 影子写成功率 > 99.99%；补偿队列无堆积 | 停影子写即可，零影响 |
| ② 历史迁移 | 按新规则搬存量，带 `version/update_time` 防覆盖 | 100% 老库 | 校验脚本：行数一致 + 关键字段哈希一致 + 抽样内容一致 | 只影响新库，老库不动 |
| ③ 数据校验 | 逐条比对，能回答"**哪条**不一致"而非"有不一致" | 100% 老库 | 不一致清单清零；增量追平（双写期间差额补完） | 同上 |
| ④ 灰度切读 | 按 `user_id` 灰度 1% → 10% → 50% → 100% | 逐步切到新库 | 每档观察错误率、RT、对账差异；异常一键回切 | **任一档异常即回切到老库** |
| ⑤ 下线老库 | 观察一周无异常后停双写、摘配置 | 100% 新库 | 老库只读保留一段时间再下线 | 保留老库期间仍可回切 |

三处最容易出事的地方：

- **② 的迁移脚本必须带版本条件**（`IF(VALUES(version) > version, ...)`），否则会冲掉双写期间的新写入。
- **① 的影子写不能阻断主链路**：新库写失败只记日志 + 进补偿队列，绝不能让下单失败，否则"扩容"直接变成"全站下单不可用"。
- **③ 的校验要覆盖增量**（`binlog` 订阅追平，第 15 章 CDC 那套）。

直接把 `% 16` 改成 `% 18` 会让路由整体重排，等于全量搬迁 + 全量缓存失效；"预留 64 片、只挪片不改规则"则零重算、零路由变更。

双写期是最终一致（第 18 章），校验脚本即一次对账（第 15 章），灰度切读与缓存预热（第 16 章）一样是把一次性切换拆成可回退的小步。

### 什么时候不该分表：可量化的阈值判断

17.7 说"500 万行 / 2GB 是参考值"，这里给一组能直接量、能据此拍板的判据。**分表要解决的是"索引装不进内存、写扛不住"，不是"行数看着多"。**

**① B+ 树层数，不是行数。** InnoDB 默认 16KB 页，聚簇索引非叶节点一项约 `8B 主键 + 6B 指针 = 14B`，单页能放约 `16KB / 14B ≈ 1170` 个索引项：

```
2 层：约 1170 × (每页行数) —— 千万级以内
3 层：约 1170² × ...       —— 百亿级
```

也就是说，几千万行仍是 3 层 B+ 树、点查 3 次页 IO，行数不是瓶颈；门槛是 **Buffer Pool 装不装得下热点索引 + 数据页**：

```
命中率 = 1 - 物理读 / 逻辑读
目标：Buffer Pool 命中率 ≥ 99%（OLTP 经验值，需在自己的负载上压测）
若命中率 < 95% 且物理读随数据量陡增 → 加内存 / 优化索引，而不是分表
```

**② 写容量：用 QPS × 耗时算，而不是拍脑袋。**

```
单实例写吞吐上限 ≈ (CPU 核数 × 每核并行事务数) / 平均事务耗时
例：写 QPS 3000、平均事务 5ms → 需要并发度 ≈ 3000 × 0.005 = 15 个活跃事务
若活跃事务数长期 > 连接数 / 2，且 CPU > 70%，才是"写扛不住"的信号
```

和第 7 章 Little's law 同一套（公式 L=λ×W 与符号见第 4 章）：先看到达率 × 耗时有没有超过容量；读写分离能把这个数再乘上从库数量。

**④ 一张"先别分表"的量化清单**（按顺序打勾，全过了再谈分片）：

| 检查项 | 量化阈值 | 不达标先做什么 |
|---|---|---|
| 慢 SQL / 缺索引 | `EXPLAIN` 出现 `type=ALL` 或 `rows > 1万` | 加索引、改 SQL（80% 的"单表太大"止于此） |
| Buffer Pool 命中率 | < 99% | 加内存、冷热分离、缩 `SELECT *` |
| 读压力 | 读写比 > 5:1 | 一主多从 + 读写分离 |
| 单表容量 | > 2GB 且归档后仍降不下来 | 冷热归档、大字段拆扩展表 |
| 写 QPS × RT | 逼近实例容量且 CPU > 70% | 先垂直/水平拆库，最后才分片 |
| 连接池 | `Threads_connected` 长期逼近 `max_connections` | 连接池与事务边界（第 4、7 章） |

取证命令序列，按顺序敲：

```bash
mysql> SHOW TABLE STATUS WHERE Name='t_order'\G     # Data_length / Rows
mysql> SHOW GLOBAL STATUS LIKE 'Innodb_buffer_pool_read%';
#   命中率 = 1 - Innodb_buffer_pool_reads / Innodb_buffer_pool_read_requests
mysql> EXPLAIN SELECT ... WHERE create_time > ...;  # 看 type / rows / Extra
mysql> SHOW ENGINE INNODB STATUS\G                  # 看 BUFFER POOL AND MEMORY 段
```

> 反常识点：多数人以为"单表过 500 万行就该分"，实际决定点查快慢的是 **B+ 树层数（几千万行仍是 3 层）和 Buffer Pool 命中率**；一张 2000 万行、索引克制、热点全在内存里的表，往往比一张刚分完片却要到处广播的表快得多。**分表是把查询灵活性换成写入能力，这笔账在动手前必须用上面的数字算，不能靠行数拍板。**
