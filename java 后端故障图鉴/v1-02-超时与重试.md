# 第二章　超时与重试：为什么越重试越慢

> 卷一 · 请求进来

**本章要回答**：下游只是"抖了一下"，为什么五分钟后整个集群都挂了？

**本章你能带走**
- 一次重试风暴的完整数学推演：为什么 1 秒超时 + 3 次重试 = 4 倍流量
- 一张"哪些接口能重试"的判定表
- 一条硬规则：**写接口不重试，重试必幂等，熔断先于重试**

**难度构成**：本章主线【必读】；含【进阶】深挖 0 处；章末「延伸」小节放支线深挖与知识库指针。

## 2.1　现场：一次抖动如何变成雪崩

14:22，商品服务的一条 SQL 因为统计信息过期，RT 从 20ms 涨到 800ms。它没挂，还在正常返回。

14:24，订单服务开始大量 `Read timed out`。因为 Feign 的默认读超时是 **1 秒**——而这条链路已经逼近这个值。

14:26，订单服务的线程池打满。所有线程都在等商品服务返回。

14:28，网关开始 502。整个下单链路不可用。

**商品服务从头到尾没有宕机，它只是慢了 40 倍。** 真正把"慢"变成"死"的，是三件事叠加：

1. Feign 默认 1 秒超时（没人配过）
2. Ribbon 默认"换一个实例重试一次"
3. 上游线程被超时占满（1 秒 × 4 倍请求量）

这就是本章的核心结论：

> **重试不是可靠性的补丁，是故障的放大器。**
> 它只在"偶发性失败"上有价值；对"容量不足"，它把 1 份压力变成 4 份。

### 【必读】现场复盘：一次抖动到全站 502 的六分钟

2.1 给了四个时间点，但没解释为什么"商品服务只是慢了 40 倍"就足以在六分钟内拖垮整条下单链路。把 14:22–14:28 摊成一条时序，每个时间点发生的都是可计算的事：

| 时刻 | 发生了什么 | 可算的数 |
|---|---|---|
| 14:22 | 商品服务一条 SQL 因统计信息过期 RT 20ms→800ms | 单条串行服务率从 50/s 降到约 1.25/s |
| 14:24 | 订单服务开始 `Read timed out` | 上游 readTimeout=1s，800ms 已逼近阈值，长尾必超 |
| 14:26 | 订单服务线程池打满 | 200 线程 × 1s 超时 ≈ 200 请求/秒的占用，到达率 > 服务率 |
| 14:28 | 网关 502 | 线程池无空闲，新请求排队到网关超时 |

**① 为什么"没挂、还在正常返回"反而更危险。** 商品服务如果直接宕机，调用方会立刻收到连接拒绝，快速失败、线程迅速释放，故障被限制在局部；它偏偏还在 800ms 后返回成功，于是每个上游线程都被稳稳占住 1 秒再超时，重试又补上第二发。**"慢"比"挂"更能吃掉上游的线程**，因为它把失败推迟到了超时那一刻，期间资源一直被占着。这是第七章 7.2 那句"一条链路上任何一环变慢，都会被事务放大成全系统排队"在重试链路上的同构版本。

**② 1 秒超时不是原因，是触发器。** 真正的问题是"没人配过"：Feign 用着 Ribbon 时代的默认 1 秒，而下游 P99 已经涨到 800ms，超时率按定义会陡增。若超时按下游 P99 × 2~3 配成 2 秒，14:24 那批 `Read timed out` 本不会发生；但那样线程会被占 2 秒，14:26 只会更早到来。**超时设短设长都救不了容量不足**——2.4 讲的"太长比太短更危险"就是这个意思。唯一能改变结局的，是让上游在下游劣化时**别再往里塞请求**：熔断（2.6）、重试层收敛（2.3）、以及把不必要的重试层从链路里砍掉。

**③ 一个反常识点：故障的起点在下游，根因在上游。** 多数人按"谁先坏"归因，会去修商品服务的慢 SQL；慢 SQL 当然要修，但它是**诱因**，把 40 倍劣化变成全站 502 的是上游那套默认重试与超时配置。商品服务从头到尾没宕机，恢复也很快，而订单服务的线程池一旦打满，队列里积压的超时请求不会凭空消失，下游恢复后故障还要再持续一阵（第七章 7.3 ② "下游恢复了，故障还会持续一阵"）。**排障时把"诱因"和"放大器"分开，才知道该同时修两处，而不是只修那个先坏的。**

**④ 这次该带走的判据。** 看到"下游 RT 上涨 + 上游超时率陡增 + 线程池打满"三件套，先量一个比值：`下游实际 ingress QPS ÷ 外层用户 QPS`。比值 ≈ 1 是正常的慢，比值 4、27、54 说明重试在放大（2.7 给了可运行的压测复现）。这个比值比任何单点的 RT 曲线都更能回答"是该优化下游，还是该关掉上游的重试"。

> 六分钟里没有任何一个组件"坏"了。坏的是三件各自都不足以致命的默认值，在同一条链路上对齐了——和第六章那次超卖是同一种事故结构。

**当时怎么误判的**：第一反应是"商品服务挂了"——可一查，它还在正常返回 200、RT 只是 800ms，没宕机；紧接着又怀疑"订单服务自己算力不够、是不是有死循环"，翻了线程栈，发现线程全卡在等超时返回，不是算。走了条死路：有人花半天去优化商品服务那条慢 SQL，以为把它治好就能止损，却没意识到下游劣化本身救不了上游的容量缺口；还有人去查订单服务的 GC 日志，怀疑 Full GC 把线程卡住，也是白查。真正扭转方向的是把"下游 ingress QPS ÷ 外层用户 QPS"算出来，比值 4、27、54，才看清是重试把 1 份压力放大成几十份。教训：故障的起点在下游、放大器却在上游那套没人配过的默认重试——诱因和放大器要分开修。

## 2.2　重试风暴的数学

假设下游 RT 从 50ms 恶化到 2s（还在硬撑），上游读超时设为 1s，重试 3 次：

```
1 个用户请求
   → 第 1 次调用（1s 超时）
   → 第 2 次调用（1s 超时）
   → 第 3 次调用（1s 超时）
   → 第 4 次调用（1s 超时）
   = 4 次下游调用，客户端等 4 秒
```

于是下游流量 ×4。下游队列更长 → RT 更慢 → 更多超时 → 更多重试。

这是一个**正反馈循环**，它有个可怕的特性：**一旦启动，自己停不下来**。下游恢复的唯一办法是上游先停止重试，而上游停止重试的唯一办法是下游先恢复。

真实集群里还有第二个乘数：**Ribbon 换实例重试**。`MaxAutoRetriesNextServer=1` 意味着每个实例失败后换一个再试，2 个实例的集群实际流量可以是 8 倍。

### 【必读】N 层重试的放大倍数：把 4 倍写成通式

2.2 算出的"×4"只是单层、单实例的最简情形。真实链路是 N 层调用，每层都可能有自己的重试，放大倍数是**连乘**，不是相加。

设第 i 层每个请求最多尝试 `1 + r_i` 次（`r_i` 是重试次数），那么一个最外层用户请求打到最底层服务的次数：

```
放大倍数 = ∏(1 + r_i)        i = 1..N
```

代入现场那条链：网关 → 订单 → 商品 → 库存，共 3 层可重试调用，每层重试 2 次（即 3 次尝试）：

```
∏ = 3 × 3 × 3 = 27 倍
```

再叠上 Ribbon"换一个实例重试一次"（`MaxAutoRetriesNextServer=1`）这个额外乘数 ×2，最底层实际承受 **54 倍**。业务含义很直接：库存服务 400 QPS 的容量，在最外层只有 `400 / 54 ≈ 7.4 QPS` 的真实用户请求时就会被打满——**不是用户涨了 54 倍，是链路自己把 1 个用户请求复制成了 54 个。**

把 Little's law 套上去，还能算出雪崩何时不可逆（公式与符号见第 4 章）。底层服务率 `μ = 400/s`，外层到达 `λ₀ = 10/s`，经 54 倍放大后底层 `λ = 540/s > μ`，队列按 `λ − μ = 140/s` 线性增长，10 秒积压 1400 个请求；队列变长 → RT 变长 → 超时变多 → 更多层开始重试 → 放大倍数继续上涨。**这就是 2.2 说的"正反馈自己停不下来"的定量版本：`ρ = λ/μ > 1` 时队列没有稳态。**

解法也随之确定：要降的是 `∏` 这个乘积本身，而乘积里最容易归零的因子是"层"——把链路里不必要的重试层砍掉（第 5 章讲熔断先于重试，第 7 章 7.3 ① 讲"上游重试把负载放大成平方"，都是同一个乘积的不同写法）。**调重试次数是改一个因子，砍重试层是把乘法变短，后者收益大得多。**

## 2.3　默认值：所有"灵异故障"的源头

Spring Cloud 的几个默认值，写在这里，因为它们是**给 demo 用的，不是给生产用的**：

| 组件 | 默认值 | 后果 |
|---|---|---|
| Feign + Ribbon | connect 1000ms / read 1000ms | 下游稍抖就全线超时 |
| Feign `Retryer.Default` | 重试 5 次，间隔 100ms→1s | 最坏情况一个请求打 6 次 |
| Ribbon | `MaxAutoRetries=0`、`MaxAutoRetriesNextServer=1`、`OkToRetryOnAllOperations=false` | 非 GET 默认不重试（幸运），GET 会换实例重试 |
| HttpClient | `maxTotal=20`、`defaultMaxPerRoute=2` | 高并发排队（下一章） |
| RestTemplate | 无默认超时 | 传 `SimpleClientHttpRequestFactory` 不设超时 = 永不超时 |

**RestTemplate 没有默认超时**这一条要特别注意：`new RestTemplate()` 用的是 `SimpleClientHttpRequestFactory`，`connectTimeout` 和 `readTimeout` 默认是 0——**0 表示永不超时**。一个卡住的下游能让调用方线程永远挂着，直到线程池耗尽。这比 1 秒超时危险得多。

```java
// ❌ 永不超时
RestTemplate rt = new RestTemplate();

// ✅ 显式超时
SimpleClientHttpRequestFactory f = new SimpleClientHttpRequestFactory();
f.setConnectTimeout(2000);
f.setReadTimeout(5000);
RestTemplate rt = new RestTemplate(f);
```

### 【必读】默认值提醒：Retryer.Default 不是 Boot 的默认重试器

2.3 表格里那行"Feign `Retryer.Default` 重试 5 次，间隔 100ms→1s"需要修正——**多数人以为这是 Spring Boot 下的默认行为，实际它是 `feign.Retryer.Default` 这个类自己的字段默认值，不是 Spring Cloud OpenFeign 装进容器的那个 Bean。**

Spring Cloud OpenFeign 的自动配置类 `FeignClientsConfiguration` 里注册的是：

```java
@Bean
@ConditionalOnMissingBean
public Retryer feignRetryer() {
    return Retryer.NEVER_RETRY;      // ← Boot 集成下默认不重试
}
```

也就是说，只要你不自己 `@Bean Retryer`，Feign 层一次都不重试。真正默认开着的是**负载均衡层**的换实例重试（旧 Ribbon `MaxAutoRetriesNextServer=1`）。把"类的字段默认值"当成"框架的装配默认值"，是这类"灵异故障"最常见的来源之一，和第六章拆掉的"打印 `this.getClass()` 判断代理"是同一种错：**看的是定义，不是运行时那个对象。**

别靠记，直接问容器：

```java
// 可运行验证：打印容器里真正的 Retryer 与 readTimeout 配置
@SpringBootTest
class FeignDefaultsProbeTest {
    @Autowired private ApplicationContext ctx;

    @Test void probe() {
        // 期望 NEVER_RETRY；若输出 Default，说明有人自定义了 @Bean Retryer
        System.out.println("Retryer = " + ctx.getBean(Retryer.class).getClass().getName());
        System.out.println("readTimeout(config) = " + ctx.getEnvironment()
                .getProperty("feign.client.config.default.readTimeout", "<未显式配置>"));
    }
}
```

`readTimeout` 的打印尤其重要，因为**超时默认值随版本漂移得厉害**：

| 结论 | 适用版本 | 升级时要重验 |
|---|---|---|
| Ribbon `DEFAULT_CONNECT_TIMEOUT=1000` / `DEFAULT_READ_TIMEOUT=1000` | Spring Cloud Hoxton 及以前（Ribbon 时代） | 现场那个"1 秒超时"属于这一档，别照搬到新项目 |
| Ribbon 被移除，改用 Spring Cloud LoadBalancer | Spring Cloud 2020.0（Ilford）起 | 新负载均衡器**默认不带重试**，需显式引入重试依赖才会换实例 |
| OpenFeign `Request.Options` 自带 connect/read 默认值 | 各版本不同 | 用上面的 probe 打印，别抄文档；文档常滞后于实现 |
| `feign.sentinel.enabled=true` 后自动建 Feign 资源 | Spring Cloud Alibaba | 别再手写 `@SentinelResource`，会重复建资源（第五章） |

凡涉及"默认是多少"的结论，都用这段 probe 在自己的版本上跑一遍再采信。（2.2 那个"8 倍"到底成不成立，取决于有几层重试真的开着，细节见章末延伸。）

## 2.4　超时怎么定：不是越短越好，也不是越长越好

超时值有一个唯一合理的锚点：**下游的 P99 RT**。

```
readTimeout ≈ 下游 P99 RT × 2 ~ 3
connectTimeout ≈ 2000ms（建连只受网络影响，与业务无关）
```

两个方向的错法都常见：

- **太短**：正常的长尾请求被误杀，然后触发重试，把 1% 的失败放大成 4% 的流量
- **太长**：`read timeout 30s` 意味着上游线程被占 30 秒。200 并发 × 30s = 6000 线程·秒，线程池瞬间打满。**超时设长了，比设短了更危险**——短的只是失败，长的会拖死自己

再补一条容易漏的：**总超时 ≠ 单次超时**。3 次重试 × 1s，用户要等 3 秒以上。用户端超时如果是 2 秒，你重试到第 3 次的时候用户早就走了——**白打两次，还把下游压得更死**。

### 【必读】超时预算是自上而下传递的

2.4 讲"单次超时按 P99 估"，但漏了更关键的一层：**一条链路上各层的超时不是各自拍的，它们必须共享一个自上而下的总预算。**

设用户端总预算 `T`（比如 2 秒），链路上有 N 段，第 i 段的单次读超时 `t_i`、重试次数 `r_i`，则必须满足：

```
Σ [ t_i × (1 + r_i) ] + 各段固定开销  <  T
```

不满足的后果是"无效工作"：用户 2 秒就走了，第 3 次重试还在下游跑着，占着线程和连接，却没有任何人会读它的结果（第七章 7.3 ②"下游恢复了故障还持续一阵"讲的就是这批请求）。现场那次 `1s × 4 = 4s` 对上前端 2 秒预算，是典型的**预算倒挂**。

反过来，正确做法是从 T 往下分配，而不是从各段往上凑：

| 层 | 分配到的预算 | 单次 readTimeout | 重试 | 该层最坏耗时 |
|---|---|---|---|---|
| 网关 → 订单 | 2000ms | 800ms | 1 次 | 1600ms |
| 订单 → 商品 | 剩余 400ms 内 | 150ms | 0 次 | 150ms |
| 商品 → 库存 | 剩余 250ms 内 | 60ms | 0 次 | 60ms |

三条硬约束，写进 CR 比记数值有用：

1. **下游超时 < 上游剩余预算**。否则上游已判超时，下游还在跑。
2. **`connectTimeout` ≪ `readTimeout`**。建连只受网络影响（2 秒足够），读超时才和业务有关；把两者配成一样大，等于把建连失败也当业务慢处理。
3. **重试要算进预算，不能只看单次**。`3 次 × 1s` 的用户体感是 3 秒以上，不是 1 秒。

gRPC 用 `deadline` 把这个预算随请求头一路透传，HTTP 侧没有统一标准，常见做法是自定义一个 `X-Request-Deadline` 头传绝对时间戳、各层发起调用前先扣掉已用时间（需在自己的框架里验证）。**没有透传机制的链路，只能靠配置表人工对齐——所以这张表必须写进容量文档，不能散落在各服务的 yml 里。**

> 多数人以为"每个服务各自配好超时就行"，实际超时是一个**端到端的预算分配问题**：单看每一层都合理，叠起来就可能超过用户预算，而超出的部分恰好是最没人负责的那部分。

## 2.5　哪些接口能重试：一张判定表

| 接口性质 | 能重试吗 | 条件 |
|---|---|---|
| GET 查询 | ✅ 可以 | 天然幂等 |
| PUT 全量更新 | ✅ 可以 | 幂等（同值覆盖） |
| DELETE | ⚠️ 谨慎 | 语义幂等，但可能触发级联 |
| POST 创建（下单/支付/扣款） | ❌ 禁止 | 必须重试时，先做幂等键 |
| 有副作用的 RPC | ❌ 禁止 | 短信、发券、扣库存 |
| 消息投递 | ⚠️ 看语义 | at-least-once 下必须幂等消费 |

写接口想重试，只有一条路：**幂等键**。

```java
// ✅ 幂等重试的前提：同一业务键重复提交只生效一次
@PostMapping("/pay")
public Result pay(@RequestHeader("Idempotency-Key") String key, @RequestBody PayCmd cmd) {
    if (!idempotentStore.tryLock(key, Duration.ofMinutes(5))) {
        return Result.of(idempotentStore.getResult(key));   // 返回首次结果，不重复扣款
    }
    try {
        Result r = payService.pay(cmd);
        idempotentStore.saveResult(key, r);
        return r;
    } finally {
        idempotentStore.unlock(key);      // 失败可重试，成功则结果复用
    }
}
```

没有幂等键，重试就是**把"少了一单"变成"多了两单"**。后者更难收拾。

### 【必读】退避抖动：纯指数退避会自己制造脉冲

2.7 自检清单里写了"指数退避 + 抖动"，但没说为什么**光有指数退避不够**。先算一笔：1000 个客户端在同一时刻被下游拖到超时，若都用 `base=100ms` 的纯指数退避，第 1/2/3 次重试分别落在 `100 / 200 / 400ms`——所有人算出的时刻一模一样，于是下游在 t=100ms、200ms、400ms 各挨一记 **1000 QPS 的脉冲**。退避只是把重试推后了，没有把它摊开，这叫惊群（thundering herd）。

加抖动后，第 k 次重试时刻在 `[0, base×2^k]` 内均匀散开：

```
full jitter:    sleep = random(0, min(cap, base × 2^k))
equal jitter:   sleep = base×2^k/2 + random(0, base×2^k/2)
decorrelated:   sleep = min(cap, random(base, prev_sleep × 3))
```

同样 1000 个客户端、cap=4s，full jitter 把它们摊到 4 秒区间，瞬时到达率约 `1000 / 4 = 250 QPS`，**是纯指数那三记脉冲峰值的 1/4**。这就是抖动的全部价值：不改变重试总量，只改变重试的**时间分布**。

```java
// ✅ 可运行：带 full jitter 的退避，打印 1000 个客户端的重试时刻分布
public final class Backoff {
    private static final long BASE = 100L, CAP = 4_000L;
    private final ThreadLocalRandom rnd = ThreadLocalRandom.current();

    /** 第 attempt 次重试（从 0 开始）应睡眠的毫秒数 */
    public long fullJitter(int attempt) {
        long ceiling = Math.min(CAP, BASE * (1L << Math.min(attempt, 20)));
        return rnd.nextLong(0, ceiling + 1);
    }

    public static void main(String[] args) {
        Backoff b = new Backoff();
        long[] buckets = new long[8];               // 每 500ms 一桶
        for (int i = 0; i < 1000; i++) {
            long sleep = b.fullJitter(5);           // 第 6 次重试，ceiling=3200ms
            buckets[(int) Math.min(7, sleep / 500)]++;
        }
        // 期望八桶大体均匀；若全落在第 0 桶，说明你写的是纯指数退避
        System.out.println(Arrays.toString(buckets));
    }
}
```

```java
// ❌ 纯指数退避：1000 个客户端在同一毫秒一起醒来
Thread.sleep(BASE * (1L << attempt));

// ✅ full jitter：同一批客户端被摊到整个区间
Thread.sleep(new Backoff().fullJitter(attempt));
```

对照着跑一下上面的 `main`：把 `fullJitter` 换成 `BASE * (1L << attempt)`，八桶输出会退化成 `[1000, 0, 0, 0, 0, 0, 0, 0]` 这种单桶形状。**能跑出分布的退化，比在文档里写"要加抖动"有说服力得多。** 退避与 2.6 的"重试占比上限"是一对：抖动摊开瞬时峰值，占比上限掐断总量。

## 2.6　熔断：重试的前置条件

正确的时序是：**熔断 → 快速失败 → 半开试探 → 恢复**，重试只在"熔断器认为下游健康"的窗口里发生。

```yaml
# Feign + Sentinel 的配置顺序比数值更重要
feign:
  sentinel:
    enabled: true
  client:
    config:
      payment-service:
        connectTimeout: 2000
        readTimeout: 5000
        retryer: feign.Retryer.NEVER_RETRY     # 支付类：禁止重试
      order-service:
        connectTimeout: 2000
        readTimeout: 8000
        retryer: feign.Retryer.Default         # 只读查询：允许
ribbon:
  MaxAutoRetries: 0
  MaxAutoRetriesNextServer: 0                   # 写接口场景全局关掉
  OkToRetryOnAllOperations: false
```

再叠加一条"重试流量占比"的上限——很多团队会做，但往往只写在文档里：

> 当某接口的**重试请求数占总请求数超过 10%**，说明它不是"偶发失败"，是"容量不足"。此时**重试必须自动关闭**，而不是继续放大。

这一条比任何超时数值都有效，因为它把"重试"从静态配置变成了自适应策略。

### 【必读】一次可运行的重试风暴复现

把 2.2 的正反馈、本章的放大倍数与 5.5 的"熔断先于重试"合成一条能自己跑的验证：一个故意变慢的下游 + 一个带重试的调用方，用恒定速率压测观察放大倍数。

```bash
# ① 下游：固定 800ms 返回（模拟"没挂，只是慢了 40 倍"）
wrk2 -t2 -c20 -d60s -R20 --latency http://localhost:8081/slow

# ② 调用方：readTimeout=1s、重试 3 次，看下游实际收到的 QPS
wrk2 -t4 -c100 -d60s -R20 --latency http://localhost:8080/api/order
# 期望（无熔断）：下游 ingress ≈ 20 × 4 = 80 RPS，且随队列增长继续上飘

# ③ 打开熔断后重跑同一条命令（开关按项目实际的熔断器实现调整）
wrk2 -t4 -c100 -d60s -R20 --latency http://localhost:8080/api/order
# 期望：超时率越阈值后下游 ingress 从 80 掉回接近 20，且失败快速返回
```

关键在两次都**用 `-R` 恒定速率**而不是 wrk 默认的尽力打满——否则服务变慢时发压速率自动下降，放大倍数会被"客户端自己怂了"掩盖（wrk/wrk2 的 Coordinated Omission 问题，第十二章压测篇展开）。

判据只有一条：**下游 ingress QPS ÷ 外层 ingress QPS 就是实测放大倍数**。健康时 ≈ 1；出现 4、27、54 这类数字，说明链路上有重试层没关；熔断打开后它必须回落 ≈ 1。把这个比值做成监控指标，比"重试占比超过 10% 就关重试"更早一步——**因为它量的是乘积本身**。

熔断与重试的时序不能反：

```
下游劣化 → 错误率/慢调用比例越阈值 → 熔断 Open（快速失败，零下游调用）
        → timeWindow 后 Half-Open（放少量探测）→ 成功则 Closed，重试窗口重新打开
```

重试只允许发生在 Closed 窗口内。若把重试放在熔断之前，Open 之前那几秒的重试恰好把下游最后一点容量吃光——**这也是为什么 5.5 那条"只配限流没配熔断"的坏味道，到了重试链路上会更致命。**

## 2.7　自检清单

- [ ] 所有 Feign 客户端都显式配置了 `connectTimeout` / `readTimeout`（没有"继承默认"的）
- [ ] `readTimeout` 按下游 P99 × 2~3 估，且**小于**用户端总超时
- [ ] 写接口（下单/支付/扣减）`Retryer.NEVER_RETRY` + `MaxAutoRetriesNextServer=0`
- [ ] `RestTemplate` / `WebClient` / `OkHttp` 都设了超时，没有 `0`（0 = 永不超时）
- [ ] 熔断器已开启，超时率阈值有配置
- [ ] 重试有上限、有退避（指数退避 + 抖动），没有固定间隔的密集重试
- [ ] 有"重试占比"监控指标
- [ ] 所有可重试接口都验证过幂等（用同一个 key 打两次，看数据）

## 2.8　一句话总结

> 超时是**止损**，重试是**加杠杆**。先学会止损，再谈杠杆。
> 顺序反了，杠杆会把止损变成雪崩。
