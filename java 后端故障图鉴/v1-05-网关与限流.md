# 第五章　网关与限流：全局限流为什么没限住

> 卷一 · 请求进来

**本章要回答**：限流规则配了 1000 QPS，为什么峰值打进来 4000，服务还是被打挂？

**本章你能带走**

- 一张表：单机限流 vs 集群限流的偏差有多大

**难度构成**：本章主线【必读】；含【进阶】深挖 1 处；章末「延伸」小节放支线深挖与知识库指针。

## 5.1　现场：限流规则写了，流量一条没少

大促前的压测，运维在网关配了"单接口 1000 QPS"的限流。压测工具打 4000 QPS，预期放过去 1000、拒绝 3000。

实际：全部放过去了，服务被打挂。

三个问题依次暴露：

**问题一：规则是单机的，不是全局的。** 网关 4 个实例，每个实例独立计数 1000 QPS——**总放行量是 4000**。所谓"全局限流"，实际是"每台机器各限各的，然后再乘一个实例数"。

**问题二：规则只在内存里。** 配置是通过 Sentinel Dashboard 推的，没做持久化。网关重启过一次（滚动发布），规则丢了，谁也没发现——**Dashboard 上还显示着规则，但那是内存里的副本，重启即空**。

**问题三：限流的位置选错了。** 有的接口走了网关，有的走内部直连（服务间调用），还有的走了另一条路由前缀。限了主入口，漏了两个旁路。

> 限流失效的三种形态，本质是三个不同的问题：**维度错、位置错、状态错**。

### 【必读】压测现场：三个问题是怎么逐个显形的

5.1 的三个问题不是一次看出来的，是按"先量总量、再重启、最后核旁路"的顺序逼出来的，这个顺序本身就是可复用的排查路径：

**① 先量总放行量，别看单机面板。** 压测打 4000 QPS，网关每台实例的 Dashboard 都显示"1000 QPS，未超限"——四个面板各自都对，合起来是 4000。判据是**把 N 台机器的放行数求和，再和规则里那个数字比**，而不是逐台看"有没有超"。这一步直接暴露问题一（维度错）。

**② 再滚动重启一台，看规则还在不在。** Dashboard 上规则一直亮着，但那是推送后的内存副本；重启一个实例后重新发压，该实例不再返回 429，总放行量反而上升。**验证限流是否持久化，唯一可靠的动作是重启，不是看控制台**（5.3）。这一步暴露问题二（状态错）。

**③ 最后核路由清单，找 bypass。** 把网关所有路由前缀、服务间直连的内部域名列一张表，逐条发一个超阈值的请求，看哪些返回了 200。现场漏掉的是一条 `/internal/**` 前缀和一个服务间直连域名。限流是"挡在最外层"，而旁路请求根本没经过最外层——这一步暴露问题三（位置错）。

> 三个问题对应三个不同的判据：求和、重启、清单。它们都不能靠"看一眼配置"完成，这也是为什么 5.7 要把阈值压测变成带期望值的断言——**配置过不等于验证过**。

**当时怎么误判的**：第一反应是"限流规则根本没配生效"——可 Sentinel Dashboard 上明明显示着 1000 QPS 的规则，又去怀疑"是不是压测工具统计口径错了"，两边看着都像。走了条死路：有人盯了整整一个下午的单台网关面板，每台都写着"1000 QPS、未超限"，四台各自都对，从没把放行数求和；还有人去查 Sentinel 的流控效果是不是被谁改成了"放行"，其实规则早就在一次滚动发布后丢进了内存，Dashboard 上还亮着的是副本。真正扭转方向的是把 N 台实例放行数一加（4×1000=4000），再滚动重启一台复现规则丢失——才看清是"维度错 + 状态错 + 位置错"三件事叠一起。教训：配置过不等于验证过，限流要验的是"流量真的被挡住"，不是"规则真的被显示"。

## 5.2　维度：单机限流会放大 N 倍

这是最容易犯、也最容易解释不清的错。

```
网关 4 实例，每实例限 1000 QPS
   ↓
集群总放行 = 4 × 1000 = 4000 QPS
   ↓
下游只扛得住 1200 QPS
   ↓
被打挂
```

两种解法，取舍不同：

| 方案 | 实现 | 精度 | 代价 |
|---|---|---|---|
| 单机限流（均分） | 每实例阈值 = 总数 / 实例数 | 粗，实例数变化需重配 | 无额外依赖 |
| 集群限流 | Redis + Lua 原子计数，或 Sentinel 集群流控 | 准 | 多一次 Redis 往返；Redis 本身成为依赖 |

单机限流的隐藏坑：**流量不均**。K8s 里 4 个 Pod，负载均衡不是绝对均匀的，某台机器可能拿到 40% 的流量，于是它在总流量 40% 的时候就开始拒绝了，而实际集群只用了 40% 的容量。

所以正确做法是：

- **入口按接口/租户做集群限流**（总量要准）
- **应用内按资源（线程池、DB 连接）做单机限流**（保护自己就够，不用准）

### 【必读】单机限流放大 N 倍的完整算式

5.2 那个 `4 × 1000 = 4000` 是最简情形，完整算式还要算上"流量不均"和"实例数会变"。设集群有 N 个实例、每实例阈值 `q`，单实例限流下：

```
集群实际放行上限 = N × q
```

代入现场：N=4、q=1000 → 4000 QPS，而下游只扛 1200，超了 3.3 倍。这只是"均分且均匀"的理想值，真实 K8s 里负载均衡不是绝对均匀。设第 i 个实例分到的流量比例 `p_i`（`Σp_i = 1`），它会在集群总流量达到 `q / p_i` 时就开始拒绝，于是：

```
集群有效容量 = q / max(p_i)
```

4 个 Pod、最忙那台拿到 35%：`1000 / 0.35 ≈ 2857 QPS`，比理想的 4000 少 28%。更糟的是**误拒**：若按"总数/N"均分改成每实例 250，最忙那台在总流量 `250 / 0.35 ≈ 714 QPS` 就开始返回 429，而此时集群才用了 `714 / 1200 ≈ 60%` 的下游容量——**限流比下游先满，白白丢了 40% 的吞吐**。

还有一层最容易被忽略的漂移：**N 不是常数**。滚动发布时实例从 4 扩到 6，若阈值仍写在每台机器各自的配置里，总放行量从 4000 悄悄变成 6000；缩容到 3 又变成 3000。判据因此可以写死：

> 只要"限流阈值"这个数字出现在**每个实例各自的配置文件**里，它就不是全局限流，而是一个会随发布次数漂移的量。

把三种偏差摆在一起：

| 偏差来源 | 算式 | 现场数字 | 后果 |
|---|---|---|---|
| 实例数放大 | `N × q` | 4 × 1000 = 4000 | 超下游 3.3 倍 |
| 流量不均 | `q / max(p_i)` | 1000 / 0.35 ≈ 2857 | 集群有效容量缩水 28% |
| 扩缩容漂移 | `N(t) × q` | 4→6 实例：4000→6000 | 阈值随发布变化 |

正确做法 5.2 已给：**入口按接口/租户做集群限流（总量要准），应用内按资源做单机限流（保护自己就够，不用准）**。集群限流用 Redis + Lua 原子计数（5.4 会给 Lua），把 `N × q` 里的 N 从算式里彻底消掉。

## 5.3　状态：规则不在配置中心，就是在眼泪里

Sentinel 的规则默认**只存在客户端内存**。Dashboard 推送的是运行时状态，重启即失效。这是最高频的"限流突然失效"原因。

必须做持久化，三种方式：

```java
// ① 推模式（推荐）：Nacos / Apollo 作为规则源，客户端监听变更
@Configuration
public class SentinelNacosConfig {

    @PostConstruct
    public void init() throws Exception {
        ReadableDataSource<String, List<FlowRule>> ds = new NacosDataSource<>(
                properties.getServerAddr(), GROUP_ID, DATA_ID,
                source -> JSON.parseObject(source, new TypeReference<List<FlowRule>>() {}));
        FlowRuleManager.register2Property(ds.getProperty());
    }
}
```

```
② 拉模式：客户端定时轮询配置中心（简单，有延迟）
③ 本地文件：规则写文件，重启加载（适合静态规则，不能动态调）
```

判断是否踩了这个坑，有个简单方法：**重启一个实例，看限流还生不生效。** 如果重启后规则消失而没人察觉，说明你从来没有真正验证过限流——只是"配置过"。

### 【必读】四种算法的判据对照

5.2 说"滑动窗口 / 令牌桶 / 漏桶"，但没给怎么选。把四种算法横着摆开，每格给判据而不是定义：

| 算法 | 临界突刺 | 允许突发 | 突发容量 | 存储/依赖 | 典型实现 | 什么时候选它 |
|---|---|---|---|---|---|---|
| 固定窗口 | ❌ 有（临界 2 倍） | 有限 | 窗口内全额 | 1 个计数器 | `INCR + EXPIRE` | 内部低风险接口，能容忍边界突刺 |
| 滑动窗口 | ✅ 无 | 有限 | 窗口内全额 | ZSET 每请求一条记录，内存高 | Redis ZSET + Lua、Sentinel `LeapArray` | 要精确、请求量不大 |
| 令牌桶 | ✅ 无 | ✅ 明确支持 | `burstCapacity` | 2 个字段 + Lua | Gateway `RedisRateLimiter` | **网关限流主流**，兼顾平滑与突发 |
| 漏桶 | ✅ 无 | ❌ 不允许 | 队列深度 | 队列 | 匀速排队、消息消费 | "可以慢但不能失败"，削峰填谷 |

固定窗口的"临界双倍"必须算一次才知道有多危险：限 100 次/秒，在第 59.9 秒打满 100 次、第 00.1 秒又打满 100 次，`0.2` 秒内放进 200 次，**瞬时速率是阈值的 10 倍**（200 / 0.2s = 1000/s）。若下游按 100 QPS 配容量，这两波就能把它打穿。滑动窗口用 ZSET 删掉窗口外记录解决了它，代价是每请求一次写、内存随窗口内请求数线性增长；Sentinel 的 `LeapArray` 用环形数组复用桶（默认 1 秒切 2 个 500ms 桶），是精度与内存的折中。

令牌桶的两个参数必须一起配，配错比不配更隐蔽：

```yaml
# ✅ Gateway 令牌桶：桶容量 ≥ 补充速率，经验值 1.5~2 倍
spring.cloud.gateway.routes[0].filters[0].args:
  redis-rate-limiter.replenishRate: 1000     # 每秒放 1000 个令牌（≈ 压测上限 × 0.7）
  redis-rate-limiter.burstCapacity: 2000     # 桶最多存 2000，允许的突发
  redis-rate-limiter.requestedTokens: 1
```

```lua
-- ✅ 滑动窗口 Lua：三步必须原子，分开执行并发下两个请求都读到"还剩 1 个"
local key, window, limit, now = KEYS[1], tonumber(ARGV[1]), tonumber(ARGV[2]), tonumber(ARGV[3])
redis.call('ZREMRANGEBYSCORE', key, 0, now - window)      -- 清窗口外旧记录
if redis.call('ZCARD', key) < limit then
    redis.call('ZADD', key, now, now .. '-' .. math.random())
    redis.call('EXPIRE', key, window)
    return 1                                              -- 放行
end
return 0                                                  -- 拒绝
```

> 为什么必须 Lua：判据是"检查令牌 + 扣减令牌"两步之间不能有其它请求插进来。分开执行时两个并发请求都读到"还剩 1 个"、都放行，限流直接失效——**这是"限流规则配了却没限住"的第四种形态**，前三种在 5.1（维度、位置、状态）。

一个反常识点来自 Sentinel 的 Warm Up：**预热只在流量"从低到高"时生效**，持续高流量下预热早就完成了，起不到保护作用。它是给冷启动（缓存未热、连接池未建）用的，不是给突发流量用的——把 Warm Up 当突发保护配，是选错了流控效果。

## 5.4　位置：限流要挡在最外层，也要挡在最里层

限流不是一道闸，是三道：

```
① 接入层（Nginx/LB）     —— 挡洪水：按 IP/连接数，防 DDoS 式流量
② 网关（Gateway）         —— 挡业务：按接口/租户/AppId，做配额
③ 应用内（Sentinel 资源） —— 挡自己：保护线程池、DB 连接、下游调用
```

只做 ②、不做 ③ 的后果：网关限了 1000 QPS，但每个请求在下游要放大成 5 次调用，下游承受 5000 QPS——**入口限流不等于下游安全**。

只做 ③、不做 ② 的后果：无效请求（鉴权失败、参数错误）也要先打到应用，白白消耗线程。

```yaml
# Gateway 路由级 + 接口级，两层都要
spring:
  cloud:
    gateway:
      routes:
        - id: order-service
          uri: lb://order-service
          predicates:
            - Path=/api/order/**
          filters:
            - name: RequestRateLimiter
              args:
                redis-rate-limiter.replenishRate: 1000     # 令牌桶填充速率
                redis-rate-limiter.burstCapacity: 1500     # 桶容量（允许的突发）
                key-resolver: "#{@apiKeyResolver}"          # ← 限流维度：按 API Key
```

`key-resolver` 这一行决定了"限谁"：按 IP、按用户、按 API Key、按接口路径——**维度选错，限流就等于没做**。按 IP 限流在多租户 NAT 场景下会误杀整个出口 IP。

### 【进阶】Sentinel 与网关层限流的实现差异

5.3/5.4 把算法讲清了，但"在哪限"和"用哪个组件限"是两件事。同一个 1000 QPS 阈值，放在 Gateway 和放在应用内 Sentinel，走的是两条完全不同的链路：

```
Gateway（RedisRateLimiter）              应用内（Sentinel）
请求 → KeyResolver 取维度                请求 → Entry → Slot Chain
     → ReactiveStringRedisTemplate            ├ NodeSelector / ClusterBuilder
     → Redis 执行 Lua 令牌桶（原子计数）      ├ StatisticSlot（LeapArray 滑动窗口）
     → 放行 / 429                             ├ SystemSlot → FlowSlot → DegradeSlot
     ↑ 每次请求一次 Redis 往返                └ 本地判断，零网络往返
     ↑ 天然集群总量（集中计数）               ↑ 默认单机计数，集群需 Token Server
```

| 维度 | Gateway `RequestRateLimiter` | 应用内 Sentinel |
|---|---|---|
| 统计位置 | Redis 集中计数 | 进程内 `LeapArray` |
| 算法 | 令牌桶（Lua 原子） | 滑动窗口（可配 QPS / 线程数） |
| 阈值维度 | 集群总量，天然准 | 默认单机，`clusterMode` 才接 Token Server |
| 限谁 | `KeyResolver`：IP / API Key / 路由 id | 资源名 + `origin`（需 `RequestOriginParser`） |
| 额外能力 | 只有限流 + 429 | 熔断降级 / 热点参数 / 系统保护 / Warm Up / 匀速排队 |
| 网络开销 | 每请求一次 Redis 往返，Redis 成为依赖 | 无 |
| 规则持久化 | 配置即规则（yml / 配置中心） | ❗默认内存，重启即丢，必须挂 Nacos（5.3） |
| 失败模式 | Redis 挂了要**快速失败**，不能无限等 | 无外部依赖 |

选型判据一句话：**"总量要准、维度要细、在入口挡无效请求"→ 网关层；"保护自己的线程池 / DB 连接、要熔断和热点参数"→ 应用内 Sentinel**。5.4 那道三道闸里，② 和 ③ 正好对应这两行，缺一不可：只做 ②，网关限了 1000 QPS 但每个请求在下游放大成 5 次调用；只做 ③，鉴权失败的请求也要先打到应用白耗线程。

两个叠加时的坑必须提前说清：**别同时上两套网关限流**（`sentinel-gateway` 与 `RequestRateLimiter` 二选一，两个都上会双重限流、实际阈值取更小那个）；**Feign 侧别手写 `@SentinelResource`**（`feign.sentinel.enabled=true` 后自动建资源，手写会重复建、统计对不上）；**`blockHandler` 与 `fallback` 不是一回事**（规则拦截走前者，业务异常走后者）。

```java
// ✅ 两个都配，语义分开：限流是可预期的，业务异常是意外的
@SentinelResource(value = "queryOrder", blockHandler = "blocked", fallback = "failed")
public Order query(Long id) { return orderService.get(id); }

// ❌ 只配 fallback：限流时不走它，BlockException 直接冒泡成 500
@SentinelResource(value = "queryOrder", fallback = "failed")
public Order queryBad(Long id) { return orderService.get(id); }

public Order blocked(Long id, BlockException e) {          // 签名 = 原方法 + BlockException
    throw new BizException(429, "请求过于频繁，请稍后重试");
}
public Order failed(Long id, Throwable t) { return Order.defaultOf(id); }
```

这段 ❌/✅ 对照是本章最该记住的一条：**"规则没限住"和"限住了但没兜住"是两种事故**，后者返回 500 比不限流还糟，因为它把可预期的拒绝伪装成了系统故障。

## 5.5　限流、熔断、降级：三个词别混着用

这三个经常被当成一件事说，实际解决不同问题：

| 机制 | 触发条件 | 作用对象 | 效果 |
|---|---|---|---|
| **限流** | 流量达到阈值（**主动**） | 自己 | 拒绝多余请求，保护自己 |
| **熔断** | 下游错误率/慢调用率超阈值（**被动**） | 下游依赖 | 快速失败，给下游喘息 |
| **降级** | 熔断打开 / 限流拒绝 / 超时 | 业务功能 | 返回兜底数据，保核心链路 |

三者关系是：**限流保护自己，熔断保护链路，降级保护体验。**

一个常见错误配置：只配了限流、没配熔断。结果下游挂掉之后，请求全部超时（而不是快速失败），线程被占满——限流还没触发，服务已经死了。

### 【必读】限流 / 熔断 / 降级的判据表

5.5 已经给过一张定义表，这里补一张**判据表**——排障时看的不是"它们是什么"，是"现在该触发哪一个、触发了没有、怎么恢复"：

| 机制 | 触发信号（看哪个指标） | 主动性 | 作用对象 | 恢复方式 | 不做会怎样 | 误判点 |
|---|---|---|---|---|---|---|
| 限流 | 入口 QPS / 并发线程数 ≥ 阈值 | 主动 | 自己（入口） | 流量回落即自动恢复，无状态 | 洪水直接打到应用 | 把"单机阈值"当全局（5.3） |
| 熔断 | 下游慢调用比例 / 异常比例 ≥ 阈值 | 被动 | 对某个下游的调用 | 状态机 Closed→Open→Half-Open，靠探测恢复 | 下游挂了请求仍逐个超时，线程占满 | 用小样本触发（见下） |
| 降级 | 限流拒绝 / 熔断打开 / 超时 / 业务异常 | 结果 | 业务功能与体验 | 随触发条件消失而结束 | 用户看到 500 / 空白页 | 只配 fallback 不配 blockHandler（5.5） |

熔断的"小样本误判"值得算一次。Sentinel 慢调用/异常比例熔断里 `minRequestAmount` 是统计窗口内的最小请求数：若窗口内只有 2 个请求、1 个失败，失败率就是 50%；阈值恰好设 50% 且 `minRequestAmount=1` 时，**一个偶发失败就会打开熔断**。所以这条参数不是可选项：

```
最小样本判据：阈值 50% 时取 minRequestAmount = 20，
则窗口内至少 20 个请求才允许判定，2 个请求的 50% 不再触发
```

三者关系 5.5 写过"限流保护自己、熔断保护链路、降级保护体验"，补一句时序：**限流在请求进来时、熔断在调用下游时、降级在前两者触发之后**。串起来才是完整链路，缺任何一环，故障都会从缺口漏过去。5.5 那个"只配限流没配熔断"的坏味道，用这张表读就是：限流看的是入口 QPS，下游挂掉时入口 QPS 并没超，限流永远不会触发——**它俩看的根本不是同一个指标**。

一个反常识点：多数人以为"熔断打开 = 服务降级了"，实际熔断只是**停止调用下游**，返回什么由降级决定；没配降级时熔断打开的表现是"快速抛异常"，可能比不限流更早把 500 打到用户脸上。**熔断是止损动作，降级才是体验动作，两者必须各自独立配置。**

## 5.6　网关自身的坑：它不是万能的

网关在链路上是**单点**，它自己也会出问题：

**① 网关超时比下游超时长，等于没超时**

```yaml
# 网关等 60 秒，下游 5 秒超时 —— 网关这层形同虚设
spring:
  cloud:
    gateway:
      httpclient:
        response-timeout: 3s        # 必须 < 下游总耗时
        connect-timeout: 1000
```

**② 网关的连接池也会耗尽**（第四章同样适用）。Gateway 用 Reactor Netty，默认连接池有限，高并发下同样排队。

**③ 在网关做重活**：鉴权时查一次 Redis、查一次用户库、调用一次权限服务——网关从"转发"变成了"业务处理"，它的 RT 直接叠加到所有请求上。**网关里只做 O(1) 的校验**，查库的事交给专门的鉴权服务并加缓存。

**④ 跨域与鉴权的顺序**：`CorsWebFilter` 必须在鉴权 Filter 之前，否则预检请求 `OPTIONS` 会被鉴权拦掉，前端拿到的错误是"跨域失败"——**而真正原因是 401**。这个错误信息误导过很多人。

### 【必读】用压测把限流阈值变成会失败的断言

5.3 说"重启一台看规则还在不在"，这补一条更强的：**用恒定速率压测，把阈值算成一个可验证的数字**。工具用 wrk2 / Gatling 的恒定 RPS 模式（第十二章压测篇），不能用默认尽力打满模式——否则服务被限流后客户端自动降速，429 比例会被掩盖。

```bash
# ① 恒定 2000 RPS 打 30 秒，限流阈值设 1000 QPS
wrk2 -t8 -c200 -d30s -R2000 --latency \
     -H 'X-Client-App: stress' http://gateway/api/orders | tee lim.log

# ② 统计 429 比例：总请求 2000×30 = 60000，期望约 30000 被拒
grep 'Non-2xx' lim.log
# 期望 ≈ 30000；接近 0 → 限流没生效（回到 5.1 三种形态）
#       ≈ 60000 → key-resolver 维度错，把压测流量全挡了

# ③ 同时验"规则持久化"：滚动重启一个网关实例后再跑一遍
wrk2 -t8 -c200 -d10s -R2000 --latency http://gateway/api/orders | grep 'Non-2xx'
# 期望与 ② 同量级；429 掉到 0 → 规则内存态、重启即丢（5.3）
```

把期望写成算式，压测结果才有判据：`拒绝数 ≈ (R − 阈值) × 时长 = (2000 − 1000) × 30 = 30000`，误差超过 10% 就说明维度、状态或位置三者里有一个错了。**这比"配完看一眼 Dashboard"强，因为它验的是流量真的被挡住，不是规则真的被显示出来。**

最后把会漂移的点列出来，升级时逐条重验：

| 结论 | 适用版本 | 升级要重验什么 |
|---|---|---|
| Gateway `RequestRateLimiter` + `RedisRateLimiter` | Gateway 3.x / 4.x（Boot 2.7 / 3.x） | 4.x 起参数名与 `KeyResolver` 的响应式写法 |
| Sentinel 规则默认内存态、需 Nacos 持久化 | Sentinel 1.8 / 2.x | 各版本 `DataSource` 接口包名可能变 |
| `blockHandler` / `fallback` 语义分工 | Sentinel 全系 | 稳定 |
| Hystrix 已停止维护，新项目用 Resilience4j / Sentinel | 2020 起 | Boot 3.x 新项目优先 Resilience4j |
| Resilience4j 配置前缀 | Spring Cloud 2023.0.0 前后不同 | `resilience4j.circuitbreaker` → `spring.cloud.circuitbreaker.resilience4j`，文档常滞后 |
| Redis 7 单线程执行 Lua 保证原子 | Redis 2.6+ / 7.x | 稳定，但要给 Redis 配连接超时与快速失败 |

> 限流最贵的不是配错数字，是**从来没验证过它真的拦住过流量**。一次带期望值的压测，能把 5.1 那三种"限流形同虚设"的形态在上线前全部逼出来。

## 5.7　自检清单

- [ ] 限流阈值是**集群维度**的，不是"每实例 × N"
- [ ] 规则持久化在配置中心，重启后自动恢复（**验证方法：重启一台，看规则还在不在**）
- [ ] 限流维度明确：按 IP / 用户 / API Key / 接口，且写进了文档
- [ ] 三道闸都有：接入层、网关、应用内资源
- [ ] 熔断独立配置，不依赖限流
- [ ] 网关 `response-timeout` 小于下游总耗时
- [ ] 网关内没有查库/远程调用的重逻辑
- [ ] `CorsWebFilter` 顺序在鉴权之前，`OPTIONS` 放行
- [ ] 被限流的请求有明确响应（429 + 重试建议），不是空 200

## 5.8　一句话总结

> 限流不是"配一个数字"，是回答三个问题：**限谁、在哪限、规则存在哪。**
> 三个都答对了才叫限流，答错一个就是心理安慰。
