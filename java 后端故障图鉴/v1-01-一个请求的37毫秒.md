# 第一章　一个请求的 37 毫秒

> 卷一 · 请求进来

**本章要回答**：一个请求从网线进来，到响应出去，中间到底经过了多少个"可以静默出错"的地方？

**本章你能带走**
- 一张把 37ms 拆成六段的表，每段都标了"证据在哪"
- 一个判定技巧：`$request_time` 与 `$upstream_response_time` 的差值，能立刻区分"网络慢"和"应用慢"
- 一条原则：**没有观测点的链路，等于没有链路**

**难度构成**：本章主线【必读】；含【进阶】深挖 1 处；章末「延伸」小节放支线深挖与知识库指针。
---

## 1.1　现场：接口"慢了"，但所有人都说不是自己慢

一次典型的扯皮：

> 前端："接口 3 秒才返回。"
> 后端："我们服务日志里 RT 只有 80ms。"
> 运维："Nginx 没报错，负载不高。"
> DBA："慢查询日志是空的。"

四个人说的都是真话。**这四句话拼在一起，恰好说明请求在某个没人观测的环节被卡了 3 秒。**

后来查出来：Nginx 到上游的 keepalive 连接数配了 16，而 QPS 峰值是 400。请求在 Nginx 的 upstream 连接队列里排队——**这段时间既不在 Nginx 的 `$upstream_response_time` 里，也不在应用的 access log 里**。它属于"没人负责的一段"。

这就是本章要解决的问题：把一条链路画清楚，标出每一段的证据来源。**你没法优化一段你看不见的耗时。**

### 【必读】现场复盘：谁都没撒谎，差的那 2.9 秒归谁

把 1.1 那四句话摊开，四个人报的是四个不同区间的数：

| 谁 | 报的数 | 实际量的是哪一段 | 为什么没撒谎 |
|---|---|---|---|
| 前端 | 3 秒 | ①→⑥ 全程 | 用户体感就是全程，含排队 |
| 后端 | 80ms | ⑤⑥ 应用内 span | APM 只给它埋了这两段 |
| 运维 | 负载不高 | Nginx CPU / 连接数 | 排队不吃 CPU，只吃队列 |
| DBA | 慢查询为空 | ⑥ SQL 执行 | 请求根本没到 SQL |

四句话拼起来恰好把六段全覆盖了一遍，唯独第 ② 段没有任何人负责——**它不在前端的视野里（前端只看到总时长），不在后端的 span 里（还没进进程），不在 Nginx 的负载指标里（排队不耗 CPU），也不在数据库的慢查询里（SQL 没执行）**。这就是"没有观测点的链路等于没有链路"最具体的样子：不是没人看，是每一处都在看，但每处看到的都不包含它。

**① 先算清排队的量级，别急着调代码。** 现场 upstream keepalive 配了 16，峰值 400 QPS、单次上游处理 83ms，按 Little's law 稳态需要 `L = 400 × 0.083 ≈ 33` 个并发连接。池子只有 16 个，一半的请求必须在连接队列里等。等待时间不服从"处理时间"，它服从 `(L − 16) / 16 × 83ms ≈ 88ms` 起步，并随队列堆积迅速放大到秒级——实测 2.9 秒与"池子小了一半 + 队列堆积"完全吻合。**排队时间是容量的函数，不是代码的函数**：把 keepalive 从 16 调到 64，前端体感立刻回到毫秒级，Java 代码一行没改。第四章会讲同一个公式在 HTTP 连接池与 Hikari 连接池上的两个版本，第七章会讲它怎么被事务里的远程调用放大成全系统排队。

**② 加线程、加机器在这类故障上是负收益。** 现场有人第一反应是"Tomcat 线程池打满，加到 400"。但线程是被"等上游连接"占住的，服务速率由 16 个 keepalive 连接决定，与线程数无关。把 200 加到 400，只是把排队队伍拉长一倍，队伍里每个人多等一倍时间，吞吐一点没变。第七章 7.1 那张"三个组都在喊冤"的表讲的是同一件事：**等锁 / 等连接型故障，加线程等价于给排队的队伍扩容，不改变服务速率。** 真正能改变服务速率的，只有缩短每个请求占用共享资源的时间，或者把共享资源本身调大。

**③ 一个反常识点：CPU 低不代表没堵。** 多数人以为"CPU 40%、负载不高"就说明服务还很空，实际排队型故障的典型特征正是**资源闲、队列满**：线程在 `WAITING`、连接在队列里、请求在 `acceptCount` 里，CPU 当然低。反过来，真正算力打满时 CPU 会先上去。所以排查时看到"RT 暴涨但 CPU 不动"，方向应该立刻转向"它在等什么"，而不是"它算得慢不慢"。这条判据在第 4 章 4.1、第 7 章 7.6 会各出现一次，是全书复用频率最高的一条。

**④ 最小改动与验收。** 现场最终只改了两个地方：Nginx `keepalive` 16 → 64，`log_format` 打全四个 upstream 变量。前者止血，后者让这段排队从"人人看不到的 2.9 秒"变成"`rt=3.021 urt=0.083` 这一行谁都能算的差值"。**没有观测点的优化只能靠猜，有了观测点的优化只需要一行减法。** 这也解释了为什么本章把"建证据"排在"谈优化"前面（1.4）：排障能力的天花板不是经验，是手上有没有那一列数据。

> 复盘结论只有一句：四个人都没错，错的是链路里有一段没有任何人的名字。把六段里每一段都指派给一个指标，这类扯皮下次就不会发生。

**⑤ 这条链路和后面四章的分工。** 把六段预算表往后翻，第二章到第五章恰好各认领一段：第二章管第 ⑥ 段里"下游超时与重试"，讲一个下游抖动怎么被放大成全站雪崩；第三章管跨语言边界，讲第 ④ 段往里传参与往外传参时类型系统怎么失效；第四章管连接池，把第 ② 段那个"排队"从 Nginx 搬进应用进程再讲一遍；第五章管入口，讲第 ② 段之前的限流为什么常常形同虚设。**六段里最贵的那几段，都是"应用自己测不到"的段**——这不是巧合：能被测到的段，早就被各种 APM 和框架日志覆盖了；剩下没人负责的段，才需要专门用一章讲清楚它的证据从哪来。

所以这一章真正交付的不是 37 毫秒这个数字，是一套分配责任的方法：每一段都要有一个指标名字、一个能取到它的命令、一个越界时该读的数。缺任何一样，那一段就会在下次故障里重新变成"四个人都说不是自己慢"的 2.9 秒。第六章讲事务静默失效时那句"最贵的 bug 是让数据悄悄错掉的 bug"，在观测领域有个孪生版本：**最贵的耗时是没有任何 span 承载的耗时**——它不报错、不告警、不进任何人的面板，只在用户体感里存在。

**当时怎么误判的**：第一反应是"应用代码慢了"或"网络抖动"——先把 APM 的接口 P99 翻出来看，80ms 干干净净，又把 DBA 的慢查询日志翻了一遍，也都是空的，两端都排除了。中间还走了条弯路：有人盯着 Nginx 的 error log 找"超时报错"，结果日志一个字都没有（排队不报错），又拿 DevTools 的 TTFB 去减 `$request_time`，减出一串没物理意义的数字，差点把方向带偏到"前端/DNS 问题"。真正扭转方向的是把 `$request_time` 和 `$upstream_response_time` 摆在同一行相减：差值 2.938 秒，明明白白落在"Nginx 到上游之间排队"。教训就一句：这类"两边都正常、用户却慢"的故障，第一现场永远是 Nginx 那个差值，不是任何一端的日志。

## 1.2　六段拆解

一个 Spring Boot 应用的请求，实际会经过这些地方：

```
① 客户端 ──TCP/TLS──▶ ② Nginx/SLB ──▶ ③ Tomcat(Acceptor/线程池)
                                              │
                                              ▼
                                    ④ Filter 链 → DispatcherServlet
                                       → Interceptor → Controller
                                              │
                                              ▼
                                    ⑤ AOP(事务/缓存) → Service → ORM
                                              │
                                              ▼
                                    ⑥ 数据库 / Redis / 下游 HTTP
```

对应的时间花在哪、去哪儿找证据：

| # | 阶段 | 典型耗时 | 证据来源 | 异常征兆 |
|---|---|---|---|---|
| ① | 客户端 → 入口 | 5–60ms | 浏览器 DevTools 的 TTFB − Nginx `$request_time` | 差值大 = 客户端网络/DNS/TLS |
| ② | Nginx 排队 + 转发 | 0–2000ms | `$request_time − $upstream_response_time` | **差值大 = 连接池/队列，不是应用** |
| ③ | Tomcat 接收 | 0–50ms | `maxThreads` 打满、`acceptCount` 队列 | 线程池满，请求在 `acceptCount` 排队 |
| ④ | Filter/Dispatcher | 1–5ms | 链路追踪 span、`HandlerInterceptor` 埋点 | 过滤器里做了 DB 查询/远程调用 |
| ⑤ | 业务 + AOP | 5–500ms | 方法级埋点（Micrometer `@Timed`） | 事务/锁/远程调用 |
| ⑥ | 存储与下游 | 1–3000ms | 慢查询日志、连接池指标、Feign 指标 | 见卷三、卷四 |

**37 毫秒的健康请求大概长这样**：网络 8ms + Nginx 1ms + Tomcat 1ms + 框架 2ms + 业务 5ms + MySQL 20ms。任何一段突然涨到 10 倍，就是那一章要讲的故事。

### 【必读】一个立刻能用的判定

```nginx
log_format timed '$remote_addr "$request" $status '
                 'rt=$request_time urt=$upstream_response_time '
                 'ua=$upstream_addr';
```

一次慢请求打出来是这样：

```
rt=3.021 urt=0.083
```

`rt` 3 秒、`urt` 83 毫秒。**应用只花了 83ms，剩下 2.9 秒全在 Nginx 到应用之间**。这时该查的是：upstream 连接池大小、keepalive 配置、Tomcat `acceptCount`、容器网络，而不是 Java 代码。

反过来 `rt=3.021 urt=3.010`，才轮到后端解释。

> 这一行日志的价值，超过了多数 APM 的默认视图——因为它**天然把"排队"和"处理"分开了**。

### 【必读】把 37 毫秒钉成一张预算表

"37 毫秒"不是一次现场测量，是一条健康链路的**预算**。把它拆开，每一段都要能回答两个问题：正常该花多少，超了去哪儿找证据。做不到这两点，那段就是链路上的盲区。

| # | 阶段 | 健康预算 | 证据字段 / 命令 | 越界时先读哪个数 |
|---|---|---|---|---|
| ① | 客户端→入口 | 8ms | curl `time_namelookup / time_connect / time_appconnect` | `time_appconnect − time_connect` 大 = TLS 握手慢 |
| ② | Nginx 排队+转发 | 1ms | `$request_time − $upstream_response_time` | 差值大 = upstream 连接池/队列（**不是应用**） |
| ③ | Tomcat 接收 | 1ms | `maxThreads` / `acceptCount`、`$upstream_connect_time` | 该值突然变大 = accept 队列排队 |
| ④ | Filter/Dispatcher | 2ms | 链路追踪入口 span、`HandlerInterceptor` 埋点 | span 里出现 DB/HTTP 子调用 = 过滤器做了重活 |
| ⑤ | 业务 + AOP | 5ms | 方法级 `@Timed`、事务 span 与 SQL span 的差 | 事务耗时 ≫ SQL 之和 = 代码占着连接（第七章） |
| ⑥ | 存储与下游 | 20ms | 慢查询日志、`hikaricp.connections.acquire`、Feign 指标 | `acquire` 大 = 排队借连接（第四章） |

合计 `8+1+1+2+5+20 = 37ms`。这张表的用法不是记数字，是记**差值**：任何一段翻十倍，总耗时就从 37ms 涨到 370ms 量级，而涨幅落在哪一段，取决于你手上有哪一列的证据。现场那次"前端 3 秒、后端 80ms"，就是第 ② 段涨到了 2900ms，而它恰好是表里唯一"应用自己看不到"的一段——Nginx 记得到，Java 记不到。

用 Little's law 还能把它算成容量（公式与符号见第 4 章）。第 ② 段的 upstream keepalive 连接数配了 16，峰值到达率 `λ = 400/s`，单次上游处理 `W = 0.083s`（就是日志里那个 `urt`），稳态需要的并发连接：

```
L = λ × W = 400 × 0.083 ≈ 33 个
```

池子只有 16 个，缺的 17 个只能在连接队列里等。按 `等待 ≈ (L − 池容量) / 池容量 × W` 粗估，单请求就要多等约 `0.088s`；再叠加队列本身的堆积，实测那 2.9 秒与"池子小了一半"完全对得上。**这也是现场把 keepalive 从 16 调到 64 之后，前端体感直接回到毫秒级、而 Java 代码一行没改的原因**：排队是容量的函数，不是代码的函数（第四章、第七章会反复用到这个换算）。

### 【必读】判据落地：一份能算的 log_format 与一行日志

上面那个判据要真能用，得先把日志配全。多数团队只打了 `$request_time`，于是差值算不出来。下面这份可以直接贴进 `nginx.conf` 的 `http` 块：

```nginx
log_format timed escape=json
    '{"time":"$time_iso8601","remote":"$remote_addr","req":"$request",'
    '"status":$status,"rt":$request_time,'
    '"urt":$upstream_response_time,"uct":$upstream_connect_time,'
    '"uht":$upstream_header_time,"uaddr":"$upstream_addr"}';

upstream app_pool {
    server 10.0.0.11:8080;
    server 10.0.0.12:8080;
    keepalive 64;                # ← 现场就是这里配了 16
}
server {
    access_log /var/log/nginx/access_timed.log timed;
    location /api/ {
        proxy_pass http://app_pool;
        proxy_http_version 1.1;
        proxy_set_header Connection "";   # 开 keepalive 必须清掉，否则连接不复用
    }
}
```

四个变量的含义必须记准，否则相减会减错：

| 变量 | 从哪到哪 | 不含什么 |
|---|---|---|
| `$request_time` | 读到客户端第一个字节 → 响应写完 | 不含 DNS/TCP/TLS（那些在 Nginx 之前） |
| `$upstream_response_time` | 与上游**建连成功** → 收完上游响应 | 不含排队等 keepalive 连接的时间 |
| `$upstream_connect_time` | 发起建连 → 建连成功 | 不含上游处理时间 |
| `$upstream_header_time` | 建连成功 → 收到上游响应头 | 不含响应体传输 |

于是有一组可算的差值（同一行日志，单位都是秒）：

```
排队等连接   ≈ $request_time − $upstream_response_time − 读请求体 − 回写响应体
上游到首字节 = $upstream_header_time − $upstream_connect_time
上游纯处理   ≈ $upstream_response_time − $upstream_connect_time
```

真实的一行（现场脱敏后）：

```json
{"time":"2026-03-11T09:04:07+08:00","remote":"10.2.3.4","req":"GET /api/sku/1024","status":200,"rt":3.021,"urt":0.083,"uct":0.001,"uht":0.079,"uaddr":"10.0.0.11:8080"}
```

逐项算：`3.021 − 0.083 = 2.938s`，`0.083 − 0.001 = 0.082s`（上游真在处理），`0.079 − 0.001 = 0.078s`（首字节几乎就是全部处理时间）。上游只干了 82ms；GET 请求体为空、响应体几百字节，回写不可能到秒级——**所以这 2.9 秒只能落在"排队等 upstream 连接"**。反过来，若这行是 `rt=3.021 urt=3.010`，差值只有 0.011s，才轮到后端解释自己的 3 秒。

把判据变成一条能天天跑的命令，别靠人肉翻日志：

```bash
# escape=json 那版直接交给 jq：筛出"应用很快、整体很慢"的行，按差值倒序
jq -r 'select((.rt - .urt) > 1.0) | "\(.rt - .urt) \(.rt) \(.urt) \(.uaddr) \(.req)"' \
   /var/log/nginx/access_timed.log | sort -rn | head -20
```

输出里若持续出现 `rt` 大而 `urt` 小的行，就是排队，不是慢代码。**这一行日志的价值，超过了多数 APM 的默认视图——因为它天然把"排队"和"处理"分开了。**

## 1.3　应用内部：每一层都可能静默改语义

进了应用之后，请求依次经过 Filter → DispatcherServlet → Interceptor → Controller → AOP → Service。这些层看起来只是"分发"，实际每一层都能悄悄改变行为：

| 层 | 能静默改变什么 | 典型事故 |
|---|---|---|
| Filter | 编码、请求体（`ContentCachingRequestWrapper` 读完就空） | 过滤器里读了 body，Controller 拿到空字符串 |
| Filter | 线程绑定（MDC、ThreadLocal、安全上下文） | 异步 Servlet 里 traceId 丢失 |
| DispatcherServlet | 参数绑定失败被吞成 `null` | `@RequestParam` 少传参数不报错，进了业务变成 NPE |
| Interceptor | 提前 `return false`，请求静默中断 | 登录校验拦截器返回 false 但没写响应体，前端拿到空 200 |
| AOP | 事务、缓存、异步、自定义切面 | 第六章整章在讲这个 |
| ORM | 事务边界、N+1、字段映射 | 卷三 |

其中最容易骗人的是 **Interceptor 静默中断**：

```java
// ❌ 不放行也不写响应：前端收到 200，body 为空
@Override
public boolean preHandle(HttpServletRequest req, HttpServletResponse resp, Object handler) {
    if (!checkToken(req)) {
        return false;              // 拦截了，但没告诉任何人为什么
    }
    return true;
}

// ✅ 拦截必须有明确响应
if (!checkToken(req)) {
    resp.setStatus(HttpServletResponse.SC_UNAUTHORIZED);
    resp.setContentType("application/json;charset=UTF-8");
    resp.getWriter().write("{\"code\":401,\"msg\":\"token invalid\"}");
    return false;
}
```

这类"静默"和第六章的事务静默失效是同一种病：**框架按契约工作了，只是那个契约不是你以为的那个。**

### 【进阶】为什么 APM 默认视图看不到排队

这是本章最反常识、也最费排查时间的一点：**多数人以为 APM 上显示"接口 P99 80ms"，就是这个请求从进来到出去的全部耗时；实际 APM 只测了进程内被埋点的那几段，而排队发生在埋点开始之前。**

OpenTelemetry Java agent、SkyWalking、Zipkin 这类工具，默认给 Servlet 入口建一个 span，起点是容器把请求交给 Filter 链的那一刻：

```
客户端 ──① DNS/TCP/TLS──▶ Nginx ──② 排队等 keepalive 连接──▶ Tomcat
                                                    │
                       ③ accept 队列 / 线程池排队 ───┤
                                                    ▼
        ┌──────── APM 第一个 span 从这里开始 ────────┐
        │ Filter → DispatcherServlet → Controller → SQL│
        └─────────────────────────────────────────────┘
                                                    │
              ④ 借连接池 HikariPool.getConnection() 常被折叠进 SQL span ─┘
```

①②③ 全在第一个 span 之外。它们的时间去哪了？被算进了两处，但**都没有独立的名字**：一是 APM 的"客户端 / 服务端差值"（如果你同时接了 RUM 或 `curl` 计时），二是 `$request_time − $upstream_response_time` 这个 Nginx 差值。默认视图按"服务 / 端点"聚合 P99，画的是 span 自己的 duration，天然不含进程外排队；更麻烦的是，第 ④ 段"借 Hikari 连接"在很多 agent 里被折叠进 SQL span 或干脆不建子 span，于是连应用内排队也看不出来。

于是现场那句话有了精确解释：后端 APM 报 80ms，因为它量的恰好是 ⑤⑥ 两段；前端报 3 秒，因为它量的是 ①→⑥ 全程；**两者都真，差的那 2.9 秒是 ②③，而 APM 默认视图里根本没有承载它的 span**。要看见它，得手动补三处埋点：Nginx 侧打全四个 upstream 变量、Tomcat 侧暴露 `acceptCount` 队列深度、应用侧给 `getConnection()` 单独打一个 span（或用 `hikaricp.connections.pending` 指标）。第七章 7.6 讲"事务耗时 > SQL 耗时之和"用的是同一个思路：**APM 默认不采集的差值，才是最该自己埋的指标。**

> 没有观测点的链路，等于没有链路——具体含义是：一段耗时如果没有任何 span / 指标 / 日志字段承载它，它在监控上就恒等于 0。

### 【必读】一次完整的取证顺序

把本章的判据压成五步，从"前端报慢"到"钉死是哪一段"，每步两分钟内能出结论（顺序照抄第七章 7.6 的取证范式）：

```bash
# ① 先在客户端把 3 秒拆开，确认时间不在本机 DNS/TLS
curl -o /dev/null -s -w \
  'dns=%{time_namelookup} tcp=%{time_connect} tls=%{time_appconnect} ttfb=%{time_starttransfer} total=%{time_total}\n' \
  https://api.example.com/api/sku/1024
# 判据：time_appconnect 小、time_starttransfer 大 → 时间花在服务端处理/排队

# ② 看 Nginx 差值，确认是不是 upstream 排队
jq -r 'select((.rt - .urt) > 1.0) | "\(.rt - .urt) \(.urt) \(.uaddr)"' \
   /var/log/nginx/access_timed.log | sort -rn | head -10

# ③ 看 Tomcat / 连接池是不是在排队
curl -s http://localhost:8080/actuator/metrics/tomcat.threads.busy
curl -s http://localhost:8080/actuator/metrics/hikaricp.connections.pending

# ④ 抓线程栈，确认线程停在哪儿（等连接 / 等下游 / 真在算）
jstack -l <pid> | grep -A 15 '"http-nio-8080-exec-' | head -60

# ⑤ 用 APM 做差值：endpoint duration 与 SQL span 之和的差，落在哪个自建 span 上
```

常见的一次误判值得写下来：**第 ③ 步看到 `tomcat.threads.busy` 打满，就断定"应用算力不够"去扩容。** 现场恰恰相反——线程是"等连接池 / 等上游"占住的，加到 400 个只是把排队队伍拉长一倍（第七章 7.1 那张"三个组都在喊冤"的表讲的是同一件事）。**先看线程停在什么方法上，再决定加不加机器。**

## 1.4　观测：先建证据，再谈优化

排障能力的天花板不是你的经验，是你手上有没有证据。三件事按性价比排序：

**① 入口一个 traceId，全链路串起来**

```java
// Filter 里生成/透传，MDC 里放一份给日志用
String traceId = Optional.ofNullable(req.getHeader("X-Trace-Id"))
        .orElse(UUID.randomUUID().toString().replace("-", ""));
MDC.put("traceId", traceId);
try {
    chain.doFilter(req, resp);
} finally {
    MDC.remove("traceId");          // 线程池复用，必须清
}
```

日志格式里带上 `%X{traceId}`。有了这个，一个用户报障能直接捞出他那一次请求在所有服务里的日志——**没有 traceId 的微服务，排障等于盲人摸象**。

**② 慢日志分级，而不是只打"超过 1 秒"**

```java
long cost = System.nanoTime() - start;
if (cost > 1_000_000_000L) {
    log.warn("SLOW uri={} cost={}ms", uri, cost / 1_000_000);   // 进告警
} else if (cost > 200_000_000L) {
    log.info("slow-ish uri={} cost={}ms", uri, cost / 1_000_000);  // 只做趋势
}
```

**③ 关键路径打点，别只打接口总耗时**

接口总耗时 800ms，可能 700ms 花在一个 `for` 循环里的 200 次单查上。总耗时告诉你"慢"，打点才告诉你"慢在哪"。

### 【必读】版本区间与一处补充

先修 1.2 表格里一处**看着对、其实经不起算**的表述：第 ① 行把"浏览器 DevTools 的 TTFB − Nginx `$request_time`"当成"客户端网络 / DNS / TLS"的证据。这个减法不成立。DevTools 的 TTFB 从"发起请求"计时到"收到响应首字节"，`$request_time` 从"Nginx 读到第一个字节"计时到"响应写完"——**起点早了一截，终点又早了一截，两个不同区间相减没有物理意义**。

```bash
# ❌ 错：两个不同区间相减，差值既不是 DNS 也不是 TLS
#    DevTools.TTFB − $request_time

# ✅ 对：curl 的四个时间点共享同一起点，做差才有意义
curl -o /dev/null -s -w \
  'dns=%{time_namelookup} tcp=%{time_connect} tls=%{time_appconnect} ttfb=%{time_starttransfer} total=%{time_total}\n' URL
# tcp−dns = DNS；tls−tcp = TLS 握手；ttfb−tls = 服务端到首字节（含排队）；total−ttfb = 回传
```

`time_namelookup`、`time_connect`、`time_appconnect`、`time_starttransfer` 是相对同一起点的累计值，做差才有意义。这也是全书反复出现的一条：**差值能当判据，前提是两项共享同一个时间原点。** Nginx 那组 `$request_time / $upstream_*` 之所以能减，正是因为它们都以"Nginx 收到第一个字节"为原点。

版本区间（下表结论建议在自己的版本上验一遍，Nginx 变量与 APM 埋点范围都会随版本漂移）：

| 结论 | 生效版本 | 升级时要重验什么 |
|---|---|---|
| `$request_time` / `$upstream_response_time` | Nginx 1.x 全系 | 多个 upstream 时 `urt` 是逗号分隔的多个值，相减前要先取对应段 |
| `$upstream_connect_time` / `$upstream_header_time` | Nginx 1.9.1+ | 老版本没有这两个变量，`log_format` 会报 `unknown variable` |
| `log_format escape=json` | Nginx 1.11.8+ | 之前只能手工转义，JSON 日志里的引号要自己处理 |
| OTel Java agent 默认从 Servlet Filter 起 span | 1.x / 2.x | 部分版本提供 `hikari` 细粒度 instrumentation，需显式开启；默认不含 accept 队列 |
| Actuator `hikaricp.connections.pending` | Boot 2.x / 3.x | 3.x 走 Micrometer 统一前缀，字段名以 `/actuator/metrics` 实际输出为准 |

书里凡涉及"默认是多少"的结论，都建议在自己的版本上打印一次再采信——**默认值是给 demo 用的，而且 demo 也在换版本。**
