# 第十章　并发下的集合与可见性

> 卷二 · 业务跑起来

**本章要回答**：`ConcurrentModificationException` 为什么单线程也会抛？为什么加了 `synchronized` 还是读到旧值？

**本章你能带走**
- 一个反直觉的事实：**CME 和并发无关**
- 一个最阴险的 bug 类型：`equals`/`hashCode` 不成对，不报错、只丢数据
- 一条判断：`volatile` 管可见性，不管原子性

**难度构成**：本章主线【必读】；含【进阶】深挖 2 处；章末「延伸」小节放支线深挖与知识库指针。

## 10.1　现场：发布后用户数据"串了"

一次上线后，客服陆续报"我明明看的是张三的订单，点进详情变成李四的"。

日志里没有异常，数据库是对的，接口返回也是对的——**只有在特定路径下才串**。

最后定位到一段缓存代码：

```java
// ❌ 用 HashMap 做本地缓存，多线程读写
private final Map<Long, User> cache = new HashMap<>();

public User get(Long id) {
    User u = cache.get(id);
    if (u == null) {
        u = userMapper.selectById(id);
        cache.put(id, u);          // 并发 put：可能触发扩容
    }
    return u;
}
```

`HashMap` 在并发 `put` 时，JDK 7 会形成环形链表导致 CPU 100%（经典的"并发扩容死循环"）；**JDK 8 改成了尾插，不再死循环，但依然会丢数据、丢 entry、甚至 `get` 到 null 后返回错误的引用。**

JDK 8 修复了"死循环"，很多人以为"那就安全了"——**没有，它只是从"卡死"变成了"悄悄错"**，而后者更难查，因为不报错。

这类 bug 的共性：**它不崩，它只是让数据变得不可信。**

**当时怎么误判的**：客诉「张三的订单点开变李四」，第一反应是「缓存读串了或者序列化有问题」，于是在缓存层加日志、换 JSON 工具，都是白查；又怀疑「是不是数据库里就存错了」，拉 SQL、对账流水，数据又都是对的——这条「查库」是完全走弯的死线索，因为问题根本不在存储。真正扭回来的，是有人注意到这段代码用的是 `HashMap` 做本地缓存，且读写都在多线程下，换成 `ConcurrentHashMap` 后串数据消失。教训很硬：这类「不报错、只错数据」的并发 bug，测试环境几乎复现不出来，只能靠规约（共享 Map 一律用并发容器）防，不能靠「我先查查」。

## 10.2　CME 和并发没有关系

这是最常被误解的一条。

```java
// ❌ 单线程，照样抛 ConcurrentModificationException
// 注意：列表里要留一个「被删元素之后」的元素（这里 "d"）。
// 否则删完直接到末尾、没机会再调 next()，foreach 会静默结束、不抛 CME
List<String> list = new ArrayList<>(List.of("a", "b", "c", "d"));
for (String s : list) {
    if (s.equals("b")) {
        list.remove(s);
    }
}
// Exception in thread "main" java.util.ConcurrentModificationException
```

原因不是"另一个线程改了"，而是：

- `foreach` 编译成 `Iterator`
- `Iterator` 每次 `next()` 前检查 `modCount == expectedModCount`
- `list.remove()` 让 `modCount++`，`expectedModCount` 没变
- 检查失败 → 抛 CME

注意：`next()` 只在"还有下一个元素"时才会被调用。若被删元素之后已经没有剩余元素（例如刚好删的是迭代末尾那个），循环会直接结束，连 `next()` 都没机会再调，自然不抛 CME——这正是很多人以为"我试过，没抛"的原因；把列表多留一个元素（如上面示例的 "d"），它就会稳定抛出。

**这是 fail-fast 设计，不是并发错误。** 名字里的 "Concurrent" 误导了一代人。

```java
// ✅ 三种正确写法
// ① Iterator.remove
Iterator<String> it = list.iterator();
while (it.hasNext()) {
    if (it.next().equals("b")) it.remove();
}

// ② removeIf（JDK 8+，最简洁）
list.removeIf(s -> s.equals("b"));

// ③ 收集后批量删
List<String> toRemove = list.stream().filter(s -> s.equals("b")).toList();
list.removeAll(toRemove);
```

反过来说：**真正的并发修改，`ArrayList` 不一定抛 CME，而是给你一个错的结果。** CME 是"运气好的情况"——它至少让你知道了。

### 【进阶】modCount 与 expectedModCount：把 CME 钉到源码上

10.2 给了一段单线程复现，但"`modCount` 对不上就抛"这句话值得落到源码。它不是并发检测，是一次普通的整数比较：

```java
// AbstractList：结构性修改计数器
protected transient int modCount = 0;

// ArrayList.Itr（迭代器）
private class Itr implements Iterator<E> {
    int expectedModCount = modCount;          // 创建迭代器时快照一次

    public E next() {
        checkForComodification();
        ...
    }
    final void checkForComodification() {
        if (modCount != expectedModCount)
            throw new ConcurrentModificationException();
    }
    public void remove() {
        ...
        expectedModCount = modCount;          // 只有迭代器自己删，才同步回去
    }
}
```

`foreach` 编译后就是 `Iterator` 遍历。`list.remove(s)` 走的是 `ArrayList` 的 `fastRemove`，它只做 `modCount++`，**不会去改任何一个已存在迭代器的 `expectedModCount`**；等下一次 `next()` 调 `checkForComodification()`，两个整数不等，异常抛出。这就是"单线程也 CME"的全部机制，和"几个线程"没有任何关系。反过来，`Iterator.remove()` 在删完后把 `expectedModCount = modCount` 同步了一遍，所以 10.2 的三种正确写法里它安全，`removeIf`（JDK 8+，内部用迭代器删）也安全。

```text
创建 Itr：expectedModCount = modCount = 3
list.remove(x)：modCount → 4，expectedModCount 仍是 3
next() → checkForComodification()：4 != 3 → ConcurrentModificationException
```

顺带把"视图"这条线接上：`subList` 返回的 `SubList` 也沿用了同一套 `modCount` 快照，所以对原列表做一次结构性修改，视图再 `get(0)` 就抛 CME（10.3）。**CME、`subList` 失效、`Arrays.asList` 定长，看着是三个坑，底层是同一套"结构变更计数 + 快照比对"**。

再补两个常被问到的点。`modCount` 是 `int`，极端频繁的结构修改会溢出回绕，理论上能让 `modCount` 恰好又等于 `expectedModCount`，把一次本该抛的 CME 吞掉——这也是 Javadoc 强调"不要依赖 fail-fast 保证"的原因之一，虽然工程上几乎遇不到。更实际的是 `CopyOnWriteArrayList`：写操作时复制整个底层数组，迭代器永远遍历那个旧快照，因此它的迭代器**从不抛 CME**，代价是写放大与读到旧数据。判据是读写比：读远多于写、且能容忍短暂旧值（监听器列表、白名单）才用，写密集场景它的 `O(n)` 复制会把 CPU 打满。它和 `ConcurrentHashMap` 一样，解决的是"不崩"，不是"强一致"。

## 10.3　视图陷阱：`Arrays.asList` 与 `subList`

```java
// ❌ UnsupportedOperationException
List<String> list = Arrays.asList("a", "b");
list.add("c");
```

`Arrays.asList` 返回的是 `java.util.Arrays$ArrayList`——一个**定长视图**，不是 `java.util.ArrayList`。只支持 `set`/`get`，不支持 `add`/`remove`。而且它**和原数组共享底层存储**：

```java
String[] arr = {"a", "b"};
List<String> list = Arrays.asList(arr);
list.set(0, "x");
System.out.println(arr[0]);      // "x" —— 原数组被改了
```

```java
// ✅ 要可变就包一层
List<String> list = new ArrayList<>(Arrays.asList("a", "b"));
```

`subList` 同理，它是**视图不是拷贝**：

```java
// ❌ 对原列表结构修改后，视图立刻失效
List<String> sub = list.subList(0, 10);
list.add("x");
sub.get(0);        // ConcurrentModificationException
```

```java
// ✅ subList 后立即拷贝
List<String> sub = new ArrayList<>(list.subList(0, 10));
```

这两个坑的共同点：**你在用一个"看起来是集合、实际是窗口"的东西。** 它不会在你写代码时提醒你，只在运行时用异常（或更糟，用错误数据）告诉你。

### 【必读】fail-fast 只是"尽力而为"，不是并发保证

10.2 结尾说"CME 是运气好的情况"，这里要再收紧一次。**反常识点：多数人以为 `ConcurrentModificationException` 是并发修改的保护网，实际它是单线程迭代器给自己的一个 best-effort 自检，从来不是并发控制手段。** `ArrayList` 的 Javadoc 写得很直白：fail-fast 行为"无法给出任何硬性保证"，只能"尽最大努力"抛，不能拿来写正确性依赖。

为什么并发下靠不住？三条：① `modCount` 是普通 `int`、不是 `volatile`，一个线程改了，另一个线程不保证立刻看到；② 读写之间没有 happens-before 边（见 10.5、JMM 篇），迭代器可能压根没观察到那次修改；③ 就算抛了，也是在**已经读到脏数据之后**才抛。于是真实并发修改 `ArrayList` 的典型结果不是 CME，而是 `size` 不对、元素丢失、或 `get` 到半写入的引用——**不抛异常，只给错数据**，和 10.1 的 `HashMap` 是同一副面孔。

| 场景 | 会不会抛 CME | 判据 |
|---|---|---|
| 单线程 foreach 里 `list.remove()` | 几乎必抛 | `modCount` 与快照不等，且同一线程一定看得到 |
| 单线程用 `Iterator.remove()` | 不抛 | 删完同步了 `expectedModCount` |
| 多线程并发改 `ArrayList` | 不保证，常常不抛 | `modCount` 非 volatile、无 HB 边，检测本身不可靠 |
| 想靠 CME 保护并发正确性 | ❌ 错误用法 | 它只是调试期提示，不是同步原语 |

一句话：**能在测试环境复现的 CME 是"运气好"，真正上线的并发 bug 往往一声不吭。** 要并发安全就换 `ConcurrentHashMap` / `CopyOnWriteArrayList`，别指望一个异常来兜底（10.7 自检清单第一条）。

### 【必读】三种"看起来是 List"的东西：asList / subList / List.of 对照表

10.3 讲了 `Arrays.asList` 和 `subList`，但还差一个常一起踩的 `List.of`（JDK 9+）。把三者横着摆开，每格给"能不能"而不是定义，用时照着判：

| 写法 | 底层是什么 | `set` 改元素 | `add` / `remove` | 能存 null | 与原集合共享存储 | 原集合结构改了之后 |
|---|---|---|---|---|---|---|
| `Arrays.asList(arr)` | `java.util.Arrays$ArrayList` 定长视图 | ✅ | ❌ `UnsupportedOperationException` | ✅ | ✅ 改一个另一个变 | 视图仍可用（是数组视图） |
| `list.subList(a,b)` | `ArrayList$SubList` 视图 | ✅ | ✅ 会写回原列表 | ✅ | ✅ | ❌ 立刻 CME |
| `List.of(...)` | 不可变 `ImmutableCollections.ListN` | ❌ | ❌ | ❌ 构造期就 NPE | ❌ 独立 | 无关（本就不可变） |
| `new ArrayList<>(...)` | 真正的 `java.util.ArrayList` | ✅ | ✅ | ✅ | ❌ 拷贝 | 互不影响 |

```java
// ❌ 三个一行代码的翻车
List<String> a = Arrays.asList("a", "b"); a.add("c");       // UnsupportedOperationException
List<String> b = new ArrayList<>(List.of("a", "b", "c")).subList(0, 2);
b.get(0);                                                    // 若原列表后来被动过 → CME
List<String> c = List.of("a", null);                         // NullPointerException

// ✅ 一律先拷贝成真正可变的 ArrayList，再谈增删改
List<String> safe = new ArrayList<>(Arrays.asList("a", "b"));
List<String> slice = new ArrayList<>(source.subList(0, 10));
```

**共同点：它们都是"看起来是集合、实际是窗口或只读快照"。** `List.of` 尤其容易骗人——它连 `set` 都不让改，也不收 `null`，放进老代码里"只是想把几个值凑成 List"，结果在 `add` 处炸。记住一条就够：**只要后面要动，就 `new ArrayList<>(...)` 包一层**，这是四个陷阱里唯一通用的解法。

视图还有两个不显眼、但线上真出过事的坑。一是 **subList 会强引用原列表**：一个 100 万元素的大列表取 `subList(0,10)` 后只留着这 10 个元素的视图，视图内部仍持有整个大数组的引用，于是那 100 万个对象一个都回收不掉——这是"明明只用了几个元素却 OOM"的典型，`new ArrayList<>(sub)` 拷贝同时也是在切断这条引用链。二是 `Collections.unmodifiableList` 包装的仍是**原列表的视图**：它只挡住通过包装对象的写，原引用照样能改，改完包装对象读到的也跟着变，和 `List.of` 那种真正的不可变副本不是一回事。判据只有一句：**只要还想"独立使用"，就拷贝，不要包装。**

## 10.4　最阴险的一种：`equals` / `hashCode` 不成对

```java
// ❌ 只重写 equals
public class User {
    private Long id;
    private String name;

    @Override
    public boolean equals(Object o) { ... }   // 没重写 hashCode
}
```

后果：

```java
Map<User, String> map = new HashMap<>();
map.put(new User(1L, "张三"), "A");
map.get(new User(1L, "张三"));      // null —— 取不出来
```

因为 `HashMap` 先用 `hashCode` 定位桶，再在桶内用 `equals` 比较。`hashCode` 没重写，两个"逻辑相等"的对象 hash 不同，落进**不同的桶**，`equals` 根本没机会被调用。

**这个 bug 不抛异常、不报错、不打日志，只是"存进去取不出来"。** 排查时人通常先怀疑 SQL、怀疑缓存、怀疑事务，最后才想到对象相等性。

规则很简单：**`equals` 和 `hashCode` 必须成对重写**。用 IDE 生成，或者用 Lombok 的 `@EqualsAndHashCode`（注意 `@Data` 已经包含它，但继承场景要显式配 `callSuper`）。

顺带一个 BigDecimal 的变体：

```java
new BigDecimal("1.0").equals(new BigDecimal("1.00"));      // false（比 scale）
new BigDecimal("1.0").compareTo(new BigDecimal("1.00"));   // 0（只比值）
```

放进 `HashSet` 会出现"两个相等的金额都在里面"。**金额比较大小时永远用 `compareTo`。**

### 【必读】HashMap 是怎么把数据"静默丢掉"的

10.4 说"`hashCode` 没重写，落进不同的桶"，把这句落到源码，才知道"静默"二字从哪来。`HashMap` 存、取都先算一次桶下标：

```java
// HashMap#hash：高 16 位混入低 16 位，减少碰撞
static final int hash(Object key) {
    int h; return (key == null) ? 0 : (h = key.hashCode()) ^ (h >>> 16);
}
// putVal / getNode 里定位桶：
//   (n - 1) & hash        n 是 table 长度，必为 2 的幂
```

`getNode` 的比较顺序是：先比 `hash`，`hash` 不等直接跳过；只有 `hash` 相等才轮到 `equals`。两个"逻辑相等"但没重写 `hashCode` 的对象，继承的是 `Object.hashCode()`（通常和对象地址相关），`hash` 大概率不同，于是——

```text
put(new User(1,"张三"))  → hash = H1 → 桶 5      存进 table[5]
get(new User(1,"张三"))  → hash = H2 → 桶 9      去 table[9] 找，空的 → 返回 null
```

`equals` 从头到尾**没有被调用的机会**，因为它在"同一个桶内"才生效。这也解释了为什么这个 bug 不抛异常、不打日志：`get` 返回 `null` 是完全合法的 API 行为，调用方只当"缓存没命中"。

```java
// 可运行验证：打印出来，比讲十遍管用
User u1 = new User(1L, "张三"), u2 = new User(1L, "张三");   // 只重写了 equals
System.out.println(u1.equals(u2));                    // true
System.out.println(u1.hashCode() == u2.hashCode());   // false ← 病根
Map<User, String> m = new HashMap<>();
m.put(u1, "A");
System.out.println(m.size() + " / " + m.get(u2));    // 1 / null ← 存进去取不出
```

判据只有一条：**`equals` 相等的两个对象，`hashCode` 必须相等**，且两者用同一组字段（IDE 生成，或 Lombok `@EqualsAndHashCode`，继承场景显式 `callSuper = true`）。把这段验证留在单测里，比在 CR 里靠人眼盯注解靠谱得多。

把 10.1 那个现场也接到源码上：JDK 8 的 `HashMap` 把扩容从头插改成尾插，确实消掉了 JDK 7 的环形链表死循环，但并发 `put` 依旧不安全——两个线程同时触发 `resize`、各自建新 table，后写回的覆盖前一个，已迁移的 entry 直接丢失；`++size` 也不是原子的。所以"JDK 8 修好了"的准确说法是**从"卡死"降级成"丢数据"**，而不是"并发安全"。正解只有一个：共享 Map 一律 `ConcurrentHashMap`，且记住它的 `get` / `put` 各自线程安全，但"先 `get` 判空再 `put`"这种复合检查仍不是原子的，要用 `computeIfAbsent`。**复合操作要原子，靠的是把检查与写入合成一次调用，不是把每一步都换成线程安全的类**——这条和 10.1 现场那段 `if (u == null) { ...; cache.put(...) }` 正好对上。

## 10.5　可见性：`volatile` 管什么

```java
// ❌ 这个循环可能永远不退出
private boolean running = true;

public void run() {
    while (running) {          // 线程可能一直读到缓存的 true
        doWork();
    }
}
public void stop() { running = false; }
```

两个线程，一个读一个写，`running` 没有同步措施。**读线程可能永远看不到写线程的修改**——因为 JMM 允许线程把变量缓存在工作内存（寄存器/CPU cache）里。

```java
// ✅ volatile 保证可见性
private volatile boolean running = true;
```

但 `volatile` **只保证可见性和有序性，不保证原子性**：

```java
// ❌ volatile 不能解决竞态
private volatile int count = 0;
public void incr() { count++; }        // 读-改-写三步，中间可被打断
```

要原子性，用 `AtomicInteger` 或加锁。

一个必须知道的关联：**双重检查锁里的 `volatile` 不能省**。

```java
// ✅ 单例的正确写法
private static volatile Singleton instance;      // volatile 不可省

public static Singleton getInstance() {
    if (instance == null) {
        synchronized (Singleton.class) {
            if (instance == null) {
                instance = new Singleton();
            }
        }
    }
    return instance;
}
```

`instance = new Singleton()` 不是原子的，分三步：分配内存 → 初始化 → 赋值引用。没有 `volatile` 时，编译器/CPU 可能重排成"分配 → 赋值 → 初始化"，于是另一个线程可能拿到**一个引用不为 null、但字段还没初始化的对象**。这是 JMM 里最经典的一个例子，也是面试题里唯一值得背的一个。

### 【必读】volatile 的两层语义与 happens-before：它凭什么能发布别的变量

10.5 说"`volatile` 管可见性、不管原子性"，这句对，但只说了一半。`volatile` 其实给了两层语义，第二层才是它真正值钱的地方：

| 语义 | 保证什么 | 对应机制 | 判据 |
|---|---|---|---|
| 可见性 | 写立即刷回主内存、使其他线程副本失效；读强制从主内存取 | 读写插入内存屏障 | 一个写线程、多个读线程的状态标志 |
| 有序性（禁重排） | volatile 写之前的普通写不会被重排到写之后；读之后的普通读写不会上浮 | `StoreStore`/`StoreLoad`/`LoadLoad`/`LoadStore` 屏障 | 双重检查锁、安全发布 |
| 原子性 | ❌ 只保证单次读/写，`count++` 这种读-改-写不管 | 无互斥 | 见下一节反例 |

第二层的正式名字叫 happens-before（HB）。JMM 里最常用的一条是：**对 volatile 字段的写，happens-before 后续对该字段的读**；再加上程序顺序与传递性，就得到"volatile 写之前的所有普通写，对 volatile 读之后的所有普通读可见"。八条常用 HB 规则里，日常推理用得最多的是这五条：

| HB 规则 | 内容 |
|---|---|
| 程序顺序 | 同一线程内，前面的操作 HB 后面的操作 |
| 监视器锁 | 对同一把锁的 unlock HB 后续 lock |
| volatile | volatile 写 HB 后续对该字段的读 |
| 线程启动 | `Thread.start()` HB 新线程中的任何操作 |
| 传递性 | A HB B 且 B HB C ⇒ A HB C |

这也补正 10.5 里一处不够严谨的比喻：把"工作内存"直接说成"寄存器 / CPU cache"容易误导，它是 JMM 的**抽象**，涵盖缓存、寄存器、写缓冲以及编译器优化，不是某个具体硬件部件。真正决定可见性的从来不是"变量放在哪"，而是**两个线程之间有没有一条 HB 边**。`SafePublication` 里 `ready` 加 volatile 之所以能让 `data = 42` 被看到，靠的正是这条"写 HB 读 + 传递性"，而不是 volatile 有什么广播魔法。

### 【进阶】一段 JMM 反例：volatile 为什么不能替代锁

**反常识点：多数人以为 `volatile` 是"轻量级的 synchronized"，能顺手替代锁；实际它一点互斥都不提供，凡是需要"读旧值、算新值、写回"的复合操作，加了 volatile 照样丢数据。**

```java
// ❌ volatile 保不住 i++：读-改-写三步，中间可被别的线程插进来
private volatile int count = 0;
public void incr() { count++; }

// ✅ 要原子性，用原子类（或加锁）
private final AtomicInteger count = new AtomicInteger();
public void incr() { count.incrementAndGet(); }
```

`count++` 在字节码里是 `getfield → iconst_1/iadd → putfield` 三步。volatile 只保证每次 `getfield` 读到的是最新值，却拦不住两个线程**同时读到同一个最新值**、各自加一、再各自写回——两次自增只落了一次。下面这段能跑的验证，把"看着没问题的代码"直接证伪：

```java
@Test
void volatileIsNotAtomic() throws Exception {
    for (int round = 0; round < 5; round++) {
        VolatileCounter c = new VolatileCounter();
        ExecutorService pool = Executors.newFixedThreadPool(8);
        for (int i = 0; i < 8; i++)
            pool.submit(() -> { for (int j = 0; j < 10_000; j++) c.incr(); });
        pool.shutdown(); pool.awaitTermination(1, TimeUnit.MINUTES);
        System.out.println(c.count);   // 期望 80000，实际常见 5xxxx~7xxxx，且每轮不同
    }
}
```

换成 `AtomicInteger` 后稳定输出 80000。想看更硬的理论结论，可以用 `jcstress` 跑无锁用例——普通单元测试几乎测不出可见性 bug，这类工具才是为 JMM 准备的。

更要命的是"跨多个变量的不变式"。就算每个字段都是 volatile，`if (a + b == 100)` 这类约束也守不住，因为两个字段之间没有任何一起变的保证：**volatile 保护的是单次访问，锁保护的是一段临界区**。要"一起变"，就得用同一把 `synchronized`、或把状态封进不可变对象整体替换。这条边界和 10.1 的 `HashMap`、10.4 的 `equals/hashCode` 是同一种教训——不报错、只错数据的 bug，靠规约和单测防，别靠"我加了 volatile"的自我安慰。

把 volatile 和锁摆在一起，选型就不必背了：

| 需求 | 用什么 | 判据 |
|---|---|---|
| 一个状态标志，一写多读 | `volatile boolean` | 只读不依赖旧值 |
| 单个变量的原子累加 | `AtomicInteger` / `LongAdder` | 读-改-写要一气呵成 |
| 多个变量要"一起变" | 同一把 `synchronized` / `ReentrantLock` | 存在跨字段不变式 |
| 安全发布一个构造好的对象 | `final` 字段或静态初始化器 | 构造期 `this` 不逃逸 |

最后一行接 10.5 的双重检查锁：`volatile` 在那里防的是"引用已赋值、对象没初始化"的重排，属于**有序性**那一层，跟可见性、原子性都不同。同一个关键字在三个场景里干三件事，正是它最容易被误用的根源。再给一条版本与工具的边界：`volatile` 的语义由 JSR-133（Java 5 起）定死，JDK 8 / 17 / 21 一致，不会随版本漂移；**会漂移的是你自己的代码有没有建立 HB 边**，怀疑可见性问题时用 `jcstress` 压，别用 `Thread.sleep` 试——sleep 不建立任何 HB 关系，加一行打印"就好了"只是 synchronized 的副作用掩盖了问题。

## 10.6　`SimpleDateFormat`：共享即出错

```java
// ❌ 静态共享：多线程下解析出错、抛 NumberFormatException
private static final SimpleDateFormat SDF = new SimpleDateFormat("yyyy-MM-dd");
```

`SimpleDateFormat` 内部持有 `Calendar`，`parse`/`format` 会改它的状态。并发调用会互相污染：

- 解析出**错误的日期**（不抛异常，最可怕）
- 抛 `NumberFormatException` / `ArrayIndexOutOfBoundsException`

```java
// ✅ JDK 8+ 一律用 DateTimeFormatter（不可变、线程安全）
private static final DateTimeFormatter FMT = DateTimeFormatter.ofPattern("yyyy-MM-dd");
```

如果必须用 `SimpleDateFormat`（老代码），两条路：`ThreadLocal` 包一层，或者每次 `new`（开销可接受，别为省一个对象引入并发 bug）。

（换成 `DateTimeFormatter` 之后仍有两个边界——严格模式 `ResolverStyle.STRICT` 与年份用 `uuuu` 而非 `yyyy`——见章末「延伸」。）

## 10.7　自检清单

- [ ] 多线程共享的 `HashMap` / `ArrayList` 全部换成了 `ConcurrentHashMap` / `CopyOnWriteArrayList`
- [ ] 没有在 `foreach` 里 `add`/`remove`，用 `removeIf` 或 `Iterator.remove`
- [ ] `Arrays.asList` 的结果没有直接 `add`/`remove`；`subList` 后没有再动原列表
- [ ] 所有放进 `HashMap`/`HashSet` 的类都成对重写了 `equals` + `hashCode`
- [ ] 金额比较用 `compareTo`，不用 `equals`
- [ ] 跨线程共享的标志位是 `volatile`
- [ ] 计数器用 `Atomic*`，不用 `volatile int` 自增
- [ ] 双重检查锁的实例字段带 `volatile`
- [ ] 没有静态共享的 `SimpleDateFormat`

## 10.8　一句话总结

> 并发 bug 分两种：**报错的**（CME、NPE）和**不报错的**（丢数据、串数据、读到旧值）。
> 前者靠经验，后者只能靠规约——因为它在测试环境几乎不会出现。
