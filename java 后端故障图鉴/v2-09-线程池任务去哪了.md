# 第九章　线程池：任务去哪了

> 卷二 · 业务跑起来

**本章要回答**：异步任务"提交成功了"，为什么什么都没发生？服务为什么 CPU 只有 10% 却完全无响应？

**本章你能带走**
- 三个默认值炸弹（无界队列 / 无限线程 / 默认拒绝静默）
- 一条几乎没人注意的真相：**`max` 参数在队列很大时永远是摆设**
- 一个高频事故模型：`submit()` + 不 `get()` = 异常人间蒸发

**难度构成**：本章主线【必读】；含【进阶】深挖 2 处；章末「延伸」小节放支线深挖与知识库指针。
---

## 9.1　现场：两种"假死"

同一个服务，两周内出了两次事故，症状完全相反。

**第一次：OOM。**

```
java.lang.OutOfMemoryError: Java heap space
```

dump 下来，80% 的堆是 `LinkedBlockingQueue$Node` 链。原因：一个导出功能在促销日被点了 3000 次，任务全堆在队列里，每个任务持有 Excel 上下文。

**第二次：CPU 10%，线程 200 个全 BLOCKED，接口全超时。** 服务像死了一样，但 CPU 几乎不动。

第一次是"任务太多"，第二次是"线程全卡住"。看起来是两个问题，**其实是同一个问题的两面：你从来没有真正控制过这个池子。**

**当时怎么误判的**：第一次 OOM，第一反应是「导出功能写得太重、Excel 上下文没释放」，顺着堆 dump 去查大对象，方向沾边却没摸到根——根是无界队列把任务无限堆积。第二次更迷惑：服务像死了一样，可 CPU 只有 10%，于是先去查 GC、查下游 RT，都「正常」，这条「CPU 不高就是没忙」差点把人带偏。真正扭回来的，是 `jstack` 一拉，四十多个线程齐刷刷停在 `FutureTask.get` 上——有人在无超时地 `get()` 一个再也不会返回的下游。这一下把方向从「查 CPU / 查 GC」扭回「查线程在等什么」：`CPU 低 + 线程全 BLOCKED` 几乎可以判定为「有人在无超时地等」。

## 9.2　三个默认值炸弹

### 【必读】炸弹一：`Executors` 的工厂方法

```java
// ❌ 队列容量 = Integer.MAX_VALUE（等价无界）
ExecutorService pool1 = Executors.newFixedThreadPool(8);
ExecutorService pool2 = Executors.newSingleThreadExecutor();

// ❌ 最大线程数 = Integer.MAX_VALUE（来多少建多少）
ExecutorService pool3 = Executors.newCachedThreadPool();
```

`newFixedThreadPool` 用的是 `new LinkedBlockingQueue<Runnable>()`——**不传容量时容量是 `Integer.MAX_VALUE`**。生产者比消费者快时，任务无限堆积：

- 每个任务对象持有上下文（请求参数、闭包、大数据）
- 堆慢慢涨，直到 `OOM: Java heap space`
- MAT 打开 dump，看到的是 `LinkedBlockingQueue$Node` 占掉七八成堆

`newCachedThreadPool` 是另一个方向的炸法：`maximumPoolSize = Integer.MAX_VALUE` + `SynchronousQueue`（不存任务），来一个建一个线程。每线程默认栈 1MB，几千个线程先触发：

```
java.lang.OutOfMemoryError: unable to create new native thread
```

**这个 OOM 和堆大小无关**，加 `-Xmx` 一点用没有。它受 OS 线程数（`ulimit -u`）和容器 pids limit 约束。

> 阿里开发手册把"禁用 Executors 创建线程池"列为【强制】，原因就是这两个。

### 【必读】炸弹二：队列太大，`max` 成了摆设

```java
// ❌ 看起来配了 max=16，实际线程数永远停在 8
new ThreadPoolExecutor(8, 16, 60L, TimeUnit.SECONDS,
        new LinkedBlockingQueue<>(100_000));
```

线程池的提交流程是固定顺序，**不是"先开到 max"**：

```
1. 运行线程 < core        → 建核心线程执行
2. 核心满了               → 进队列排队          ← 卡在这里
3. 队列也满了             → 才建非核心线程到 max
4. 线程到 max 且队列满    → 拒绝策略
```

队列 10 万，意味着第 3 步几乎永远到不了。**你配的 `max=16` 是一个永远不会被使用的数字。**

想让 `max` 生效，队列必须有界且**相对小**——小到"队列满了以后应该扩线程"这件事真的会发生。典型值：`core=8, max=16, queue=200`。

### 【必读】炸弹三：默认拒绝策略会"静默丢"

```java
// ❌ DiscardPolicy：丢任务，不报错，不告警，无痕迹
new ThreadPoolExecutor(8, 8, 0, SECONDS, new ArrayBlockingQueue<>(100),
        new ThreadPoolExecutor.DiscardPolicy());
```

四个策略的取舍：

| 策略 | 行为 | 什么时候用 | 风险 |
|---|---|---|---|
| `AbortPolicy`（默认） | 抛 `RejectedExecutionException` | 大多数场景，**快速失败** | 调用方没 catch 会抛到用户 |
| `CallerRunsPolicy` | 提交者线程自己执行 | 需要背压、任务可降级为同步 | **提交者是 Tomcat/Netty IO 线程时会拖死容器** |
| `DiscardPolicy` | 静默丢弃 | 几乎不适用 | 丢数据且无痕迹，最危险 |
| `DiscardOldestPolicy` | 丢队首再试 | 允许丢旧数据的日志类 | 同样静默 |

`CallerRunsPolicy` 的坑值得单独说：它在"线程池是自己业务线程"的场景下是优雅的背压；但如果提交动作发生在 **Tomcat worker 线程**里，被拒绝的任务会被这个 worker 同步执行——**容器的 IO 线程被拖去做业务，吞吐直接塌。** 用之前先问：谁在提交？

### 【进阶】execute() 的三分支：把"max 是摆设"钉到源码上

9.2 用四句话概括了提交顺序，但"队列满了才扩到 max"到底由哪几行代码决定，值得摊开看一次。`ThreadPoolExecutor#execute` 的主体不过二十来行，全部压在一个 `ctl` 变量上：

```java
public void execute(Runnable command) {
    if (command == null) throw new NullPointerException();
    int c = ctl.get();
    if (workerCountOf(c) < corePoolSize) {            // 分支① 建核心线程
        if (addWorker(command, true)) return;
        c = ctl.get();
    }
    if (isRunning(c) && workQueue.offer(command)) {    // 分支② 入队
        int recheck = ctl.get();
        if (!isRunning(recheck) && remove(command)) reject(command);
        else if (workerCountOf(recheck) == 0) addWorker(null, false);
    }
    else if (!addWorker(command, false))               // 分支③ 扩到 max
        reject(command);                               // 分支④ 拒绝
}
```

`ctl` 是一个 `AtomicInteger`：高 3 位存运行状态，低 29 位存工作线程数，`workerCountOf(c)` 就是 `c & CAPACITY`。把这条判定画成流程，三分支的边界一目了然：

```text
                       execute(command)
                             │
          workerCountOf(c) < corePoolSize ?
              │ 是                       │ 否
              ▼                          ▼
   addWorker(command, true)     isRunning && workQueue.offer()
   建核心线程，任务直接跑          │ 入队成功          │ offer 返回 false
                                  ▼                    ▼
                          recheck 一次状态      addWorker(command, false)
                          必要时补个空 worker    用 maximumPoolSize 判定
                                                   │ 仍失败
                                                   ▼
                                            handler.reject()
```

关键在分支②：`offer` 一旦成功就返回了，**根本走不到分支③**。所以"max 生效"的源码级条件不是"线程数到了 core"，而是"`offer` 返回 false，也就是队列满了"。队列传 `new LinkedBlockingQueue<>(100_000)`，意味着要往里堆满十万个任务才会触发扩容；而在那之前，8 个核心线程早已停在那里不动了。`addWorker` 的第二个布尔参数才是两个阈值的分水岭：`true` 拿 `corePoolSize` 比，`false` 拿 `maximumPoolSize` 比——同一个方法，两把尺子。

**反常识点**：多数人以为线程池"先扩线程、再排队"，标准的 `ThreadPoolExecutor` 恰恰相反，是"先入队、后扩线程"。设计意图是优先复用已有线程、避免频繁创建销毁。真正"先扩到 max 再入队"的是 Tomcat 的 `TaskQueue`：它改写了 `offer()`，在线程数还小于 max 时故意让入队失败，把 `execute` 逼进分支③，好让 Web 请求优先多开线程而不是排队。**同一个 `execute`，换一个队列实现，扩容行为就翻了过来**——所以背下"四步流程"不如记住"`offer` 卡在哪一步"。

顺手算一笔：core=8、单任务 20ms，8 个线程满负荷吞吐是 `8 / 0.02 = 400 任务/秒`。要让十万容量的队列堆满、触发分支③，生产者得长期以远高于 400/s 的速率灌入且十分钟不回落；现实里队列还没堆到那个量级，堆内存先被任务对象撑爆了。**"max 生效"和"OOM"在赛跑，超大队列让 OOM 稳赢**（9.2 炸弹一的源码解释）。

补一句容易被跳过的：`ctl` 的高 3 位还压着线程池的五个状态（RUNNING、SHUTDOWN、STOP、TIDYING、TERMINATED），低 29 位才是 workerCount。分支② 入队成功后那段 `recheck` 不是冗余——从 `offer` 到 `recheck` 之间，另一个线程可能已经调了 `shutdown()`；此时要把刚入队的任务 `remove` 掉并走拒绝，否则任务会永远躺在队列里没人执行。这也解释了为什么"入队"和"确认池还活着"必须分成两步写。一个判据：**队列里的任务数，只有在池处于 RUNNING 时才等于"待执行数"**；一旦开始关闭，`getQueue().size()` 就不再代表任何承诺——9.5 要求把 `queued` 接进监控，前提正是池还活着。

顺带把 `execute` 与 `submit` 在源码上的分岔点说清：`submit` 最终也调 `execute(futureTask)`，三分支一步没少。所以"submit 的任务排队 / 被拒绝"和 execute 完全同构，差别只在异常去向（9.3）。**池参数、队列、拒绝策略对两种提交一视同仁，别以为换了 submit 就能绕开容量模型。**

## 9.3　事故模型：`submit()` 吞掉了异常

这是"任务执行了但什么都没发生"的第一大根因，也是第二次事故的直接原因。

```java
// ❌ 异常人间蒸发
Future<?> f = pool.submit(() -> riskyCall());
// 没有 f.get() → riskyCall 抛的异常被封装进 Future，永远没人看
```

两种提交方式的异常行为**完全不同**：

| 方法 | 异常去向 | 结果 |
|---|---|---|
| `execute(Runnable)` | 抛给线程的 `UncaughtExceptionHandler` | 至少进日志 |
| `submit(...)` | **封装进返回的 Future** | 不 `get()` 就永远消失 |

```java
// ✅ 方案一：任务内兜底（最省事，推荐）
pool.execute(() -> {
    try {
        riskyCall();
    } catch (Throwable t) {
        log.error("async task failed", t);
        throw t;
    }
});

// ✅ 方案二：get 带超时，集中处理
try {
    Result r = future.get(3, TimeUnit.SECONDS);
} catch (TimeoutException e) {
    future.cancel(true);
    return fallback();
} catch (ExecutionException e) {
    log.error("task failed", e.getCause());     // 真正的异常在这里
}
```

顺带一个高频致命写法：

```java
// ❌ get() 不带超时 = 永久阻塞许可
Result r = future.get();     // 下游假死 → 当前线程永远 BLOCKED
```

第二次事故就是这么来的：40 个业务线程全卡在 `get()` 上，等一个再也不会返回的下游。**CPU 低、线程 BLOCKED、接口全超时**——这个组合几乎可以判定为"有人在无超时地等"。`jstack` 一看，40 个线程停在 `FutureTask.get`。

### 【必读】submit 的异常存进了哪里：FutureTask#setException 与 get() 的交接

9.3 那张表说异常"封装进返回的 Future"，但"封装"这个词太笼统。`AbstractExecutorService#submit` 先把任务包成 `FutureTask`（`newTaskFor` → `new FutureTask<>(callable)`），再交给 `execute`。**池子里跑的从来不是你写的 Runnable，是 `FutureTask`**。异常就是在这一层被截住的：

```java
// FutureTask#run（简化）
public void run() {
    try {
        Callable<V> c = callable;
        if (c != null && state == NEW) {
            V result; boolean ran;
            try { result = c.call(); ran = true; }
            catch (Throwable ex) { result = null; ran = false; setException(ex); }  // ★
            if (ran) set(result);
        }
    } finally { /* runner = null; 处理中断 */ }
}

protected void setException(Throwable t) {
    if (UNSAFE.compareAndSwapInt(this, stateOffset, NEW, COMPLETING)) {
        outcome = t;                                    // 异常存进 outcome 字段
        UNSAFE.putOrderedInt(this, stateOffset, EXCEPTIONAL);
        finishCompletion();                             // 唤醒阻塞在 get() 的线程
    }
}
```

`setException` 只做三件事：把 `Throwable` 放进 `outcome` 字段、把状态从 `NEW` 推到 `EXCEPTIONAL`、唤醒等待者。**它不打印、不抛出、不通知任何日志框架**——异常此刻变成了一个躺在对象字段里的普通引用。真正把它变回异常的是 `get()`：

```java
// FutureTask#get → awaitDone → report
private V report(int s) throws ExecutionException {
    Object x = outcome;
    if (s == NORMAL) return (V) x;
    if (s >= CANCELLED) throw new CancellationException();
    throw new ExecutionException((Throwable) x);        // ★ 包一层才抛出
}
```

```text
submit(task) → FutureTask(task) → execute(futureTask) → worker 调 futureTask.run()
      c.call() 抛异常 → setException(t): outcome = t, state = EXCEPTIONAL
      ├─ 无人 get()        → outcome 无人读，随 Future 被 GC，异常彻底消失
      └─ 有人 get(timeout) → report() → throw new ExecutionException(t)
```

一句话：**异常不是"被打了日志"，是被存进了一个字段；`get()` 不是"触发计算"，是把 `outcome` 里的 `Throwable` 包成 `ExecutionException` 重新抛出来**。这也正是 9.3 里 `e.getCause()` 才是真异常的原因——`ExecutionException` 只是那层包装纸。这个"包一层就没人看得见根因"的形态，第 11 章讲自定义异常丢 `cause` 时还会原样再见一次。

### 【必读】afterExecute 的正确写法：用 submit 时 t 恒为 null

顺着上面的链路，能拆掉一个流传很广的误判。**多数人以为给线程池重写 `afterExecute(Runnable r, Throwable t)` 就能兜住所有异常，实际上只要任务是 `submit` 提交的，`t` 永远等于 null。** 原因就在 `runWorker()`：只有 `task.run()` 直接抛出的 `Throwable` 才会作为第二个参数传进 `afterExecute`；而 `FutureTask.run()` 早把异常 `catch` 掉、塞进 `outcome` 了，压根没往 `runWorker` 外面抛。于是钩子拿到的 `r` 是那个 `FutureTask`，`t` 却是空的。

```java
// ❌ 以为能拿到异常：submit 的任务，t 恒为 null，什么都不会打
@Override protected void afterExecute(Runnable r, Throwable t) {
    super.afterExecute(r, t);
    if (t != null) log.error("task failed", t);
}

// ✅ 官方 Javadoc 范例：识别 Future，主动 get() 把异常"钓"出来
@Override protected void afterExecute(Runnable r, Throwable t) {
    super.afterExecute(r, t);
    if (t == null && r instanceof Future<?>) {
        try {
            ((Future<?>) r).get();
        } catch (CancellationException ce) {
            t = ce;
        } catch (ExecutionException ee) {
            t = ee.getCause();                  // 取回真正的异常
        } catch (InterruptedException ie) {
            Thread.currentThread().interrupt(); // 恢复中断标志
        }
    }
    if (t != null) log.error("uncaught in async task", t);
}
```

这里的 `get()` 不带超时是安全的：任务既然走到了 `afterExecute`，说明 `run()` 已经结束、状态已是终态，`get()` 会立刻返回，不会阻塞。它和 9.3 那句"`get` 必须带超时"并不矛盾——那条约束的是**还没跑完**的 Future，这条读的是**已经跑完**的 Future。

顺带修正 9.3 表格里一处偏乐观的说法：`execute` 的异常写的是"抛给 `UncaughtExceptionHandler`，至少进日志"。更准确的是——默认 `ThreadFactory` 只把它打到 `System.err`，是否落进应用日志取决于容器怎么重定向标准错误；**而 `submit` 的异常连 `UncaughtExceptionHandler` 都到不了**，因为它被 `FutureTask.run()` 吞在了内部。所以"配了 handler 就高枕无忧"是假象：handler 能兜住的只有 `execute` 提交的任务。

结论是兜底要成对做：任务内 `try-catch` 记日志（9.3 方案一）管 `execute`，`afterExecute` 里主动 `get()` 管 `submit`，需要返回值的场景再加带超时的 `get`。三条各管一段，缺一条就有一段静默。

## 9.4　ThreadLocal：串台比泄漏更可怕

线程池复用的副作用，是两个：

**① 内存泄漏**

`ThreadLocalMap` 的 `Entry` 继承 `WeakReference<ThreadLocal>`：**key 是弱引用，value 是强引用**。ThreadLocal 对象被回收后 key 变 null，但 `线程 → ThreadLocalMap → Entry → value` 这条强引用链还在。线程是池化的长驻对象，**线程不死，value 不释放**。

**② 数据串台（更危险）**

```java
// ❌ 不 remove：下一个请求可能读到上一个用户
private static final ThreadLocal<LoginUser> CTX = new ThreadLocal<>();

public void handle(Request req) {
    CTX.set(req.getUser());
    service.process();        // 抛异常时 remove 被跳过
    CTX.remove();             // 而且不在 finally 里 = 等于没写
}
```

worker 处理完请求 A 归还池中，下个请求 B 复用同一线程，`CTX.get()` 读到的是 A 的用户。**表现为"偶发拿到别人的登录态/租户 ID"——这是数据事故，不是性能问题。**

```java
// ✅ 唯一正确写法
public void handle(Request req) {
    try {
        CTX.set(req.getUser());
        service.process();
    } finally {
        CTX.remove();          // 必须 finally
    }
}
```

`InheritableThreadLocal` 也救不了跨线程池传值：它只在**线程创建那一刻**从父线程拷贝一次，而 worker 早就创建好了，之后父线程改值它看不到。跨池传递用阿里开源的 `TransmittableThreadLocal`（TTL），它通过装饰 `Runnable`/线程池在**提交时快照、执行时回放**。

```java
ExecutorService ttlPool = TtlExecutors.getTtlExecutorService(pool);
```

### 【进阶】一段能跑出串台的复现：一个线程的池就够了

9.4 说"下一个请求可能读到上一个用户"，这句话最好用一段能跑的测试钉死，别停在口头。单线程池把"复用"变成必然，不需要压测、不需要并发：

```java
@Test
void threadLocalLeaksAcrossRequests() throws Exception {
    ExecutorService pool = Executors.newSingleThreadExecutor();  // 只有 1 个 worker，必复用
    ThreadLocal<String> CTX = new ThreadLocal<>();

    pool.submit(() -> CTX.set("用户A")).get();          // 请求 A：set 后故意不 remove
    String seenByB = pool.submit(() -> CTX.get()).get(); // 请求 B：什么都没 set，直接读

    assertEquals("用户A", seenByB);   // ✅ 断言成立：B 读到了 A 的上下文
    pool.shutdown();
}
```

这个测试**故意让断言通过**——它证明的不是"代码对"，而是"漏洞真实存在"。把 `CTX.set` 换成登录态、租户 ID 或 traceId，就是 9.4 说的那类数据事故。再加一段对照，证明 `finally remove` 确实补上了缺口：

```java
// ✅ 对照：加上 finally，第二条任务读到 null
pool.submit(() -> { try { CTX.set("用户A"); } finally { CTX.remove(); } }).get();
assertNull(pool.submit(() -> CTX.get()).get());
```

线上怀疑串台时，取证顺序是：`jstack -l <pid> | grep "order-async-"` 先看池子里 worker 的数量和名字（9.5 坚持命名前缀就是为了这一刻），再用 `jmap -dump:format=b,file=heap.hprof <pid>` 配 MAT 看 `ThreadLocalMap$Entry` 里 value 的类型与数量。**能稳定复现的串台反而好查，线上几乎都是偶发的**——因为它取决于"上一次请求有没有走到 finally"，而这跟异常路径有关：恰恰是出错的那次请求漏了 `remove`，下一位用户才中招。

### 【必读】TransmittableThreadLocal 的边界：传引用、要装饰、不包治百病

先补正 9.4 一处只说了一半的话：原文讲 `InheritableThreadLocal` "之后父线程改值它看不到"。更危险的另一半是——**worker 复用时，它会一直攥着上一次任务创建那一刻拷贝的旧值**，也就是"串台"同样适用于它。线程池里的 worker 只在首次创建时从父线程拷一次，之后父线程怎么改都与它无关，它停在了一个陈旧帧上。所以那句话该读成：`InheritableThreadLocal` 在线程池下不是"看不到新值"，是"永远停在一个旧值上"。

TTL（`TransmittableThreadLocal`）靠"提交时快照、执行时回放、执行后恢复"三拍解决，但有三个边界，用之前必须清楚：

| 边界 | 具体是什么 | 判据 |
|---|---|---|
| 必须装饰 | 要么 `TtlExecutors.getTtlExecutorService(pool)` 装饰池，要么 `TtlRunnable.get(task)` 装饰任务 | 两者都不做，TTL 退化成普通 `InheritableThreadLocal` |
| 装饰要在最外层 | 快照发生在被装饰的 `Runnable` 被提交那一刻 | 中间若又被别的包装类套了一层原始 `Runnable`，快照链就断了 |
| 传的是引用 | 快照保存的是对象引用，不是深拷贝 | value 若可变（`Map`、`User`），子线程改字段，父子看到的是同一个对象 |

第三条最容易被当成 bug：想隔离，就得自己存不可变快照。另外 TTL 只管"任务提交"这一条路径，`parallelStream` 用的 `ForkJoinPool`、`CompletableFuture` 默认池、JDK 21 虚拟线程、第三方库自起的线程，各有各的装饰方式，别假定一个 `getTtlExecutorService` 全覆盖。

这条线索和另外两章是同一根线：第 6 章 Q5 讲"换线程 = 换事务"，根因正是 `TransactionSynchronizationManager` 用 `ThreadLocal<Map<DataSource, ConnectionHolder>>` 把连接绑在线程上——**事务上下文和这里的登录态，是同一个 ThreadLocal 机制的两副面孔**，线程池一复用就一起失效。第 7 章那次"事务里做远程调用"的池子若要传上下文，踩的也是它。至于"多开线程能否救场"，第 4 章连接池与第 7 章第③点已经给了答案：先满的往往不是线程池，是 Hikari 默认只有 10 个连接的连接池。

泄漏与串台该怎么区分，给一条取证判据：串台是"值不对"，通常能靠日志里的用户 ID 对上；泄漏是"老年代缓慢上涨"，MAT 里看 `ThreadLocalMap$Entry` 的数量只增不减。前者加 `finally remove` 就好，后者还要查是不是把大对象（一次查询的全量结果、整个请求体）塞进了 ThreadLocal——`remove` 只解绑引用，塞进去的对象若还被别处持有，一样回收不掉。**两者都靠 `remove` 收口，但一个是数据事故、一个是容量事故，别混着查。** 另外 `InheritableThreadLocal` 的泄漏更隐蔽：值会随子线程创建一路拷贝，父线程早已结束，那批拷贝还挂在各条 worker 上。

TTL 还有一条部署边界值得写进 CR：`TtlExecutors.getTtlExecutorService(pool)` 返回的是**包装后的 ExecutorService**，如果框架（某些 RPC / 任务调度库）内部又拿原始 `pool` 去提交，装饰就绕过去了。稳妥做法是"对外只暴露装饰后的那个实例"，并把断言加进单测：提交一个任务，断言子线程 `TTL.get()` 等于主线程设置的值。**跨线程传值这类问题，靠约定守不住，得靠一条会失败的断言。**

## 9.5　一个可用的池子长什么样

```java
ThreadPoolExecutor bizPool = new ThreadPoolExecutor(
        8,                                          // core：CPU 密集 ≈ 核数，IO 密集按阻塞系数放大
        16,                                         // max：队列有界时才有意义
        60L, TimeUnit.SECONDS,
        new ArrayBlockingQueue<>(200),               // 有界：堆积上限可见
        new ThreadFactoryBuilder()
                .setNameFormat("order-async-%d")     // jstack 里一眼认出
                .setUncaughtExceptionHandler((t, e) -> log.error("uncaught {}", t.getName(), e))
                .build(),
        (r, executor) -> {                           // 自定义拒绝：告警 + 落补偿
            alert.send("order-async rejected");
            rejectMapper.insert(r.toString());
            throw new RejectedExecutionException("order-async saturated");
        });

// 提交处兜底：绝不让任务无声消失
try {
    bizPool.execute(() -> doAsync(task));
} catch (RejectedExecutionException e) {
    log.warn("pool saturated, degrade to sync", e);
    doAsync(task);                                   // 或丢进 MQ 延时重试
}
```

三个必须暴露的指标：

```java
Metrics.gauge("pool.active",  bizPool, ThreadPoolExecutor::getActiveCount);
Metrics.gauge("pool.queued",  bizPool, p -> p.getQueue().size());
Metrics.gauge("pool.completed", bizPool, ThreadPoolExecutor::getCompletedTaskCount);
```

**`pool.queued` 是唯一能提前预警的指标。** 队列水位持续上涨，比 OOM 早几分钟到几十分钟；而 `active` 打满只是"现在很忙"，未必出事。

### 【必读】线程数不是拍脑袋：CPU 密集 / IO 密集的估算式

9.5 的样例池写了 `core=8`，这个 8 从哪来？《Java Concurrency in Practice》给的估算式（Goetz）是：

```text
N_threads = N_cpu × U_cpu × (1 + W/C)

N_cpu = Runtime.getRuntime().availableProcessors()    CPU 核数
U_cpu = 目标 CPU 利用率（0~1）
W/C   = 等待时间 / 计算时间
```

| 任务类型 | W/C | 取 U_cpu | 结果 | 判据 |
|---|---|---|---|---|
| CPU 密集（加解密、序列化、计算） | ≈ 0 | 1 | `≈ N_cpu`，工程上常写 `N_cpu + 1` | 几乎没有阻塞，多开只会增加上下文切换 |
| IO 密集（查库、调 RPC、写文件） | 远大于 0 | 1 | `N_cpu × (1 + W/C)` | 大部分时间挂在等，要靠多线程把 CPU 填满 |

举一个能算的：一次任务计算 10ms、等下游 90ms，`W/C = 9`，8 核、目标打满 CPU，则 `N_threads = 8 × 1 × (1 + 9) = 80`。业务含义是——**要吃满 8 个核，得有 80 个线程同时在"等"**，因为每个线程 90% 的时间是挂起的。把 core 设成 8，CPU 只会用到约 10%，这正是 9.1 第二次事故"CPU 只有 10% 却无响应"的另一种成因：不一定是卡死，也可能是线程数压根不够把等待时间填满。

队列容量同样能算，别拍 `200`。按 Little's law `L = λ × W`（定义与符号见第 4 章）：峰值 `λ = 1000 任务/秒`、允许排队 `W = 0.2 秒`，稳态队列长度 `L = 200`。设 200 刚好容纳这一波突发；设 10 万等于放弃背压（9.2 炸弹一），设 10 又会让拒绝策略频繁触发。**队列是"能容忍排多久"的量化结果，不是随手填的整数。**

三条边界比公式本身重要。① `W/C` 要**实测**：用 APM 拉一次任务里 IO 等待与 CPU 时间的占比，公式给起点、压测定终点。② 线程池再大也突破不了下游容量：80 个线程抢 Hikari 默认 10 个连接，多出的 70 个只是在 `getConnection()` 上排队（第 4 章、第 7 章第③点），**线程数要和下限最紧的那层对齐**。③ 版本区间：JDK 21 起 IO 密集可用 `Executors.newVirtualThreadPerTaskExecutor()`，虚拟线程不池化、不设 core/max，改用 `Semaphore` 限下游并发；但上面的估算式对 JDK 8/11/17 的平台线程池仍然成立。Spring Boot 3.x 默认跑在 JDK 17+，别把虚拟线程的结论照搬回平台池。

把估算和拒绝策略连起来看，才是完整的容量模型。仍用上面的 `λ=1000/s`、服务率 `μ=8/0.02=400/s`：一旦 `λ>μ`，队列按 `λ-μ=600/s` 的速度线性增长，200 的队列 `200/600≈0.33 秒` 就满，之后全靠拒绝策略决定命运。`AbortPolicy` 快速失败把压力还给上游，`CallerRunsPolicy` 让提交线程自己跑、相当于把 `λ` 压回 `μ` 附近（这正是它叫"背压"的原因），而 `DiscardPolicy` 让 `λ` 表面依旧 1000/s、只是悄悄丢掉 600/s。**三者里只有背压真正改变了到达率，另两个只是改变了"谁承担损失"**（第 7 章 Little's law 的同一个式子）。

最后给一张把三者对齐的表，配池时横着过一遍：

| 配置项 | 由什么决定 | 配错的典型症状 |
|---|---|---|
| core / max | `N_cpu × U_cpu × (1+W/C)` + 下游最紧的容量 | CPU 低但 RT 高（线程不够），或大量超时（线程多于连接池） |
| 队列容量 | `L = λ × W`，W 是能容忍的排队时长 | 无界 → OOM；过小 → 拒绝策略频繁触发 |
| 拒绝策略 | 提交方是谁、能不能背压 | `CallerRunsPolicy` 用在 IO 线程 → 容器吞吐塌 |

## 9.6　自检清单

- [ ] 没有用 `Executors.*` 建池，全部手动 `new ThreadPoolExecutor`
- [ ] 队列有界，且大小与 core/max 匹配（队列太大 = max 失效）
- [ ] 线程有命名前缀（出事时 `jstack` 能认出来）
- [ ] 拒绝策略明确，不是 `DiscardPolicy`；用了 `CallerRunsPolicy` 的确认过提交方不是 IO 线程
- [ ] 所有 `submit` 要么 `get`，要么任务内 try-catch
- [ ] 所有 `get` 都带超时
- [ ] 所有 `ThreadLocal` 都在 `finally` 里 `remove`
- [ ] 跨线程池传上下文用 TTL，不用 `InheritableThreadLocal`
- [ ] 暴露了 `active / queued / completed` 三个指标

## 9.7　一句话总结

> 线程池不是"把任务扔出去就不管"的管道，它是一个**有容量上限、有拒绝语义、有异常去向**的系统。
> 你不定义这三件事，它就替你定义——而它的默认值，是按 demo 的规模写的。
