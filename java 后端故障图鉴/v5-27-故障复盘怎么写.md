# 第二十七章　一次故障复盘该怎么写

> 卷五 · 上线之后

**本章要回答**：复盘写完，除了归档，还能留下什么？

**本章你能带走**
- 一份可直接套用的复盘模板（一页纸 + 五个部分）
- 一个区分：**触发因素 / 直接原因 / 深层原因**，混在一起就找不到改进点
- 一条判据：**改进项如果不能被验证，就等于没写**

**难度构成**：本章主线【必读】；含【进阶】深挖 0 处；章末「延伸」小节放支线深挖与知识库指针。
---

## 27.1　现场：两份复盘

同一个故障，两份复盘。故障是第六章那个超卖：库存扣了，订单没写，多扣 347 件。

**第一份（真实存在过的写法）：**

> **故障描述**：11 月 8 日预售活动期间，出现库存超卖，影响约 300 单。
> **原因分析**：开发同学在实现时对 Spring 事务机制理解不够深入，未使用正确的事务写法。
> **改进措施**：1. 加强代码评审；2. 组织 Spring 事务培训；3. 提高开发人员质量意识。
> **责任人**：张三

**第二份：**

> **影响**：9:04–10:31，共 347 次扣减无对应订单，涉及 312 个用户，潜在资损 0 元（已拦截发货），客诉 6 起。
> **时间线**：见下（精确到分钟，含三次误判）
> **触发因素**：营销服务 9:00 起 RT 从 20ms 涨到 900ms（当日上线了新功能）。
> **直接原因**：`deductStock` 通过 `this` 自调用，`@Transactional` 从未生效。
> **深层原因**：① 团队缺少"事务边界"的评审项；② 监控只按 HTTP 状态码统计错误，业务失败不可见；③ 库存与订单无常量对账。
> **改进项**：见下（6 项，含验证方式与 owner）

差别不在文笔，在**能不能据此行动**。

第一份的三条改进措施，没有一条可以被验证。"加强评审"——怎么算加强了？"组织培训"——培训完怎么知道有效？"提高意识"——这是一个无法证伪的句子。

**而它的"原因分析"其实是一句责难**：把系统性问题归到"某人不熟悉"。下次换一个人，同样的 bug 会再来一次——因为环评项、监控盲区、对账缺失，一个都没变。

### 【必读】两份复盘逐项对照：差在能不能据此行动

27.1 摆了两份复盘，说"差别不在文笔"。把这句话拆成可以逐格打勾的对照，才知道差在哪儿：

| 维度 | 第一份 | 第二份 | 能不能据此行动 |
|---|---|---|---|
| 影响 | "影响约 300 单" | 9:04–10:31、347 次扣减、312 个用户、6 起客诉、资损 0 元 | 第一份无法定优先级 |
| 时间线 | 无 | 精确到分钟，含三次判断与两次判断修正 | 第一份无法还原决策路径 |
| 原因 | "对事务机制理解不够深入" | 触发 / 直接 / 深层三层分开 | 第一份把系统问题归到个人 |
| 改进项 | 加强评审、组织培训、提高意识 | 6 项，含验证方式、Owner、期限 | 第一份三项全不可验证 |
| 责任人 | 张三（一个人） | 每项一个 Owner + 期限 | 第一份是追责，不是分工 |
| 同类风险 | 未提 | 明确"发现一处，扫一遍全站" | 第一份只修了这一个 bug |

第一份那三条改进措施，用 27.5 的判据逐条量一下就露馅了：**"加强代码评审"没有验收动作，"组织培训"没有可观测的结果，"提高质量意识"是一个无法证伪的句子**。它们不是"写得不够细"，是**在语法上就不可能被完成**——你没法给"提高意识"打勾。

更关键的是它的"原因分析"。把"事务没生效"写成"某人不熟悉 Spring 事务"，等于把一次系统性失效压缩成一次个人失误；下次换个人写，`this.xxx()` 自调用、`final` 方法、`catch` 吞异常、`@Async` 叠加（第 6 章）还会再来一遍，因为**评审项、监控口径、对账机制一个都没变**。第二份的深层原因三条——无评审项、错误率只按 HTTP 状态码、无对账——每一条都指向一个能被改掉的机制。

> 一个反常识点：**复盘写得越像检讨，可行动的信息越少。** 检讨的终点是"谁负责"，复盘的终点是"下次在哪一步能拦住"。第 6 章那个 `isActualTransactionActive()` 之所以值钱，不是因为它高深，是因为它是个布尔值——**能回答"是/否"的东西，才能写进验证方式那一列**。

**当时怎么误判的**：写第一份复盘时，第一反应是"这是张三对 Spring 事务理解不深、质量意识不足"——直接把系统性失效压缩成个人失误，连查都没查就归了责。中间还走了一条死路：以为"加强代码评审、组织事务培训、提高质量意识"三条已经是合格改进项，逐项对着"能不能打勾验证"量一遍才发现它们语法上就不可能完成，全是愿望不是动作。真正扭转方向的是把原因拆成"触发 / 直接 / 深层"三层——深层原因落到了"CR 无事务边界检查项、错误率只按 HTTP 状态码、库存订单无对账"这些能被改掉的机制上。教训：复盘追流程不追人，能问"下次在哪一步拦住"的复盘才值钱，能问"谁负责"的只是在写检讨。

## 27.2　三层原因，必须分开

这是复盘里最容易混、也最影响改进质量的一步。

| 层次 | 定义 | 例子 | 对应的改进 |
|---|---|---|---|
| **触发因素** | 让问题从"存在"变成"发生"的那件事 | 营销服务当天变慢 | 通常**不需要改**，它只是时机 |
| **直接原因** | 代码/配置层面"哪里错了" | 自调用导致事务未生效 | 修代码 + 加静态检查 |
| **深层原因** | 为什么这个错误**能上线、能运行 47 分钟没被发现** | 无评审项、监控盲区、无对账 | **这才是复盘的产出** |

**只写直接原因，改进项就只能是"改代码"——而代码永远会再写错。**

第六章那个故障，如果只改代码（改成跨 Bean 调用），下次换个姿势（`final` 方法、`catch` 吞异常、`@Async` 叠加）还会中招。**真正的修复是"把这类错误的识别成本降到最低"**：CR 检查项、静态扫描、监控口径、对账。

一条实用的提问方式：

> **"如果下个月新来的同事写了同样的代码，我们能不能在它上线前拦住？"**
> 答不上来，说明深层原因没找到。

### 【必读】三层原因的判据：一句话该归哪一层

27.2 给了定义和例子，但真写的时候，最难的是"这句话该放哪层"。给一组判据问句，写完全文逐句过一遍：

| 层次 | 判据问句 | 答"是"就归这层 | 反例（容易放错） |
|---|---|---|---|
| 触发因素 | 去掉它，这个 bug 还在不在？ | "还在，只是没被触发" | 把"营销服务变慢"写成根因——它只是时机 |
| 直接原因 | 改掉这一处代码，这次还会不会发生？ | "这一次不会了" | 只写"改代码"，就停在这儿 |
| 深层原因 | 换个人、换个写法，同样的错能不能再次上线且长时间没人发现？ | "能" | 把"没评审项"写成"开发不细心" |

三个问句是有顺序的：**先确认"去掉触发因素问题仍在"**，才能把触发因素和直接原因分开；**再确认"改这一处只解决这一次"**，才能把直接原因和深层原因分开。27.1 那次超卖，若把"营销服务 9:00 RT 涨到 900ms"当根因，改进项就会变成"让营销服务别变慢"——可营销服务下次上新功能还会慢，而库存照样会多扣。

深层原因的标准写法也有一条判据：**它必须指向一个"能被改掉的机制"，而不是一种"人的状态"**。

```text
❌ 深层原因：开发人员对事务边界不敏感、质量意识不足
✅ 深层原因：CR checklist 无「事务边界」项；
            错误率只按 HTTP 200/5xx 统计，业务失败不可见（第 11 章）；
            库存与订单无常量对账，错误只能靠客诉发现（第 6 章）
```

三条都能对应到 27.5 里的一条改进项，且每条都有验证方式。**写不出"对应哪条改进项"的深层原因，多半还没挖到位。**

## 27.3　时间线：写"我们以为"，不只写"发生了什么"

普通的时间线只记录系统事件：

```
14:22 商品服务 RT 上涨
14:24 订单服务大量超时
14:28 网关 502
14:35 定位到问题
14:40 修复上线
```

**这种时间线没有复盘价值**，因为它只记录了"系统做了什么"，没记录"人做了什么判断"。

有价值的时间线，每一段都带当时的判断和依据：

```
14:22  商品服务 RT 从 20ms → 800ms（监控无告警，未超过阈值）
14:24  订单服务出现 Read timed out（值班同学判断：下游抖动，等自愈）
14:29  超时率超过 10%，决定扩容订单服务（判断：容量不足）
14:31  扩容无效，P99 继续上涨（判断修正：不是容量问题）
14:35  查到 Feign 默认 1s 超时（判断：超时配置问题）
14:38  调整超时到 8s，情况恶化（判断再次修正：超时放大线程占用）
14:44  回滚超时配置 + 熔断，流量恢复
```

**"判断"和"判断修正"是时间线里最值钱的部分**，因为它是下一次排障的路线图。它同时暴露了两件事：

- 哪些判断是对的（可以固化成手册）
- 哪些判断是错的（需要补什么信息才能判断对）

**没有"误判"的复盘，通常意味着有人在美化自己。**

### 【必读】时间线模板：把「我们以为」单独立一列

27.3 给了两段示例，但没给能直接套用的表头。普通时间线只有"时间 / 事件"两列，缺的正是**人当时怎么想**。把「我们以为」和「依据」各自单独立一列，判断才有被复核的可能：

```markdown
| 时间 | 系统事件 | 我们以为 | 依据 | 后来发现 | 判断修正 |
|---|---|---|---|---|---|
| 14:22 | 商品 RT 20→800ms | 下游抖动，等自愈 | 未超告警阈值 | 是超时配置被放大 | 应看线程占用而非 RT |
| 14:29 | 超时率 >10% | 容量不足 | 历史经验 | 扩容无效 | 不是容量问题 |
| 14:35 | 查到 Feign 默认 1s | 超时配置太小 | 配置面板 | 调大后更糟 | 超时放大了线程占用 |
| 14:44 | 回滚 + 熔断 | —— | —— | 流量恢复 | 根因是超时×重试（第 2 章） |
```

```markdown
<!-- ❌ 两列时间线：只记系统做了什么，人做了什么判断全丢 -->
| 时间 | 事件 |
|---|---|
| 14:22 | 商品服务 RT 上涨 |
| 14:40 | 修复上线 |

<!-- ✅ 六列时间线：判断与判断修正都可复核 -->
| 时间 | 系统事件 | 我们以为 | 依据 | 后来发现 | 判断修正 |
```

六列里最值钱的是「依据」和「判断修正」两列：**依据**让当时的判断可被理解（不是"他们怎么这么蠢"，是"他们手上有这些信息"）；**判断修正**暴露的是"还缺什么信息才能判断对"，直接对应 27.5 里的监控类改进项。27.3 说"没有误判的复盘，通常意味着有人在美化自己"——六列模板让美化变难，因为「我们以为」和「后来发现」并排放着，删掉前者，时间线就缺一格。



## 27.4　影响面：量化到"钱"和"人"

"影响约 300 单"是不够的。要回答四个数：

```
影响时长：  9:04 – 10:31（87 分钟）
影响用户：  312 人（其中 6 人发起客诉）
影响业务：  347 次扣减无订单，3,000 单正常
资损：      0 元（已拦截发货）/ 或 12,400 元（需赔付）
```

**为什么要算到钱**：因为它决定了改进项的优先级。资损 0 元的事故和资损 50 万的事故，投入的资源完全不同。而"影响 300 单"这个说法，无法做这个判断。

还有一个常被忽略的维度：**同类风险的存量**。"这次是 A 接口，那 B、C 接口有没有同样的问题？"——**发现一处，就要扫一遍全站。** 这一条能防止"修了一个，漏了十个"。

### 【必读】影响面：把「钱」和「人」写成算式

27.4 说"影响约 300 单是不够的"。把四个数写成可复算的算式，改一个输入就能重算，也能和财务、客服对数：

```text
① 影响人时 = 受影响用户数 × 平均阻断时长
            = 312 人 × (87 分钟 × 不可下单占比 0.6)
            ≈ 312 × 52 分钟 ≈ 270 人·小时

② 资损 = 需赔付订单数 × 客单价 × 赔付比例 + 履约成本
        = 347 × 265 元 × 0.10 + 0（已拦截发货）
        ≈ 9,196 元
   若未拦截发货：347 × 265 × 1.0 = 91,955 元（全额货值）

③ 客诉率 = 客诉数 / 受影响用户数 = 6 / 312 ≈ 1.9%

④ 错误预算消耗 = 故障时长 / 月度允许不可用时长
              = 87 分钟 / (30×24×60 × 0.001) = 87 / 43.2 ≈ 2.0 倍
```



为什么非要算到钱？因为改进项之间要排序。资损 0 元（已拦截）和资损 9 万（未拦截）是同一种故障的两个结局，投入的资源完全不同；而"影响 300 单"这个说法，既看不出拦截动作的价值，也算不出赔付敞口。**27.4 那句"为什么算到钱：因为它决定改进项的优先级"，落到实处就是上面这四行算式**。

补一个 27.4 提到但没展开的维度——**同类风险存量**也要量化：`扫描范围 = 全站 @Transactional 方法数`，命中 `this.xxx()` 自调用组合 N 处，逐个确认；这一条能防止"修了一个，漏了十个"。算式写进 27.5 的改进项验证方式里，就是"扫描出 N 处，N 处全部确认或修复"。

## 27.5　改进项：三类，且必须可验证

```markdown
| # | 类型 | 改进项 | 验证方式 | Owner | 期限 |
|---|---|---|---|---|---|
| 1 | 止血 | 修复自调用，改跨 Bean 调用 | 灰度后对账 24h 无差异 | @张三 | 已完成 |
| 2 | 止血 | 库存与订单增加小时级对账 | 人为构造 1 条差异，告警能触发 | @李四 | 11-10 |
| 3 | 根治 | 全站扫描 `this.xxx()` 自调用 + `@Transactional` 组合 | 扫描出 N 处，逐个确认 | @张三 | 11-15 |
| 4 | 根治 | 所有 `@Transactional` 补 `rollbackFor` | 静态检查规则上线，CI 拦截 | @王五 | 11-20 |
| 5 | 预防 | 错误率统计改为按业务 `code` 而非 HTTP 状态码 | 人为抛异常，看错误率是否上涨 | @李四 | 11-12 |
| 6 | 预防 | CR 模板增加「事务边界」检查项 | 抽查 10 个 MR，全部填写 | @张三 | 11-09 |
```

**"验证方式"这一列是关键。** 它把"我们要加强 XX"变成"我们怎么知道加强了"。

三类的区别：

- **止血**：让当前问题不再发生（通常当天完成）
- **根治**：让"这一类"问题不再发生（需要改流程/工具）
- **预防**：让"下一类"问题能被更早发现（监控/对账/演练）

**只有止血的复盘是不合格的**，因为它是"修了这个 bug"，不是"减少了一类 bug"。

### 【必读】改进项三类都要可验证，以及五个反模式的真实写法

27.5 那张六行表已经把"验证方式"列出来了。把它抽象成一条判据：**每条改进项都要能回答"谁、在什么条件下、做什么动作、看到什么结果算完成"**。四种验证方式基本覆盖全部场景：

| 验证方式 | 适合哪类改进 | 可打勾的结果 |
|---|---|---|
| 对账 / 差异注入 | 止血（数据正确性） | 人为构造 1 条差异，告警能触发 |
| 演练 / 故障注入 | 预防（降级、熔断） | 注入依赖延迟 500ms，成功率降幅 <5% |
| CI / 静态检查拦截 | 根治（写法规约） | 扫描出 N 处，CI 对违规写法构建失败 |
| 监控 / 告警复核 | 预防（可观测性） | 人为抛异常，错误率曲线确实上涨 |

三类改进项各配一种主验证方式：**止血**用对账，**根治**用 CI 拦截，**系统性（预防）**用演练和监控。27.5 说"只有止血的复盘不合格"，补一句判据：**一张改进项表里如果四行全是"改代码 + 人工验证"，说明深层原因没挖到**。

```text
❌ 加强代码评审、组织 Spring 事务培训、提高开发人员质量意识
✅ CR 模板增加「事务边界」检查项；抽查 10 个 MR，全部填写该栏
✅ 静态检查规则上线，@Transactional 缺 rollbackFor 时 CI 构建失败
```

差别就在一句：**前者是愿望，后者有动作、有样本数、有失败条件**。"抽查 10 个 MR 全部填写"能被证伪——抽到第 3 个没填就失败了，这才是可验证。

把这条判据交给机器：下面这段挂进 CI，改进项表格缺字段就构建失败。第 23 章的取证脚本、第 26 章的压测断言，到这里收束成同一件事——能被机器执行的规约，才不会在第三次事故时被人省略。

```bash
awk -F'|' '/^\| [0-9]+ / { n++; if ($5 ~ /^ *$/ || $6 ~ /^ *$/ || $7 ~ /^ *$/) bad++ }
           END { printf "改进项 %d 条，缺字段 %d 条\n", n, bad; exit (bad>0) }' review.md
```



最后把 27.6 五个反模式各抄一句"真实写法"，都出自第一份复盘那种语感，附一句改法：

| 反模式 | 一句真实写法 | 改成 |
|---|---|---|
| 归因到人 | "张三对事务机制理解不深入" | "CR 无事务边界检查项，自调用写法能上线" |
| 不可验证 | "后续加强代码评审力度" | "抽查 10 个 MR，全部填写事务边界栏" |
| 无 owner | "研发团队后续跟进" | "@李四，11-10 前完成" |
| 只止血 | "已修复该接口的自调用问题" | 追加"全站扫描 N 处同类写法，逐个确认" |
| 过度追责 | "本次事故由当事人承担主要责任" | 删除；改为"复盘不追人追流程" |



## 27.6　五个反模式

| 反模式 | 例子 | 问题 |
|---|---|---|
| **归因到人** | "某同学理解不深" | 换个人还会犯，系统性缺陷没修 |
| **不可验证** | "加强评审""提高意识" | 无法判断是否完成 |
| **无 owner** | "研发团队" | 集体负责 = 无人负责 |
| **只止血** | 只改代码，不改流程 | 同类问题必然复发 |
| **过度追责** | 谁写的谁背锅 | 下次没人敢报故障，隐瞒比故障更贵 |

最后一条尤其重要：

> **复盘的目标是让系统更可靠，不是让人更小心。**
> 如果复盘的后果是"谁出事谁挨骂"，那么下一次的故障会被瞒到无法隐瞒为止。

## 27.8　最后：这本书在讲什么

二十七章下来，那些最贵的故障其实只有五个母题：

**一、你以为执行了，其实没执行。**
事务没开（第六章）、锁没生效（第八章）、切面被绕过、`@Transactional` 加在 `final` 方法上。**框架按契约工作了，只是那个契约不是你以为的那个。**

**二、你以为传过去了，其实变形了。**
Long 变成 800（第三章）、时区差 8 小时、金额 `0.10` 变 `0.1`、Feign 丢参数。**跨边界的时候，类型系统和语义都会失效。**

**三、你以为很快，其实在排队。**
连接池（第四章）、线程池（第九章）、行锁（第七章）、MQ 积压（第二十章）、Nginx upstream。**"慢"的绝大部分不是"算得慢"，是"等得慢"——而"等"不出现在任何下游的监控面板上。**

**四、你以为处理一次，其实处理了两次（或零次）。**
消息重复（第十九章）、重试重复下单（第二章）、幂等缺失。**"至少一次"是异步世界的默认语义。**

**五、你以为监控看得见，其实它瞎了。**
错误率 0 但客诉 40 单（第十一章）、`send success` 但消息丢了（第十八章）、`4096M->4096M` 的 Full GC（第二十五章）。**你的可观测性，只覆盖了你想到的那些维度。**

这五个母题的共同点：

> **系统没有报错，是你在用错误的假设读它。**

所以这本书能给你的，不是 27 个答案，是一套提问方式：

- 这个注解，真的执行了吗？我怎么证明？
- 这个值，跨过边界之后还是它吗？
- 这 3 秒，是算的还是等的？
- 这件事，会发生几次？
- 如果它错了，我多久能知道？

**能问出这五个问题的人，不需要这本书。**
