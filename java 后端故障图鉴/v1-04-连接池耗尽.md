# 第四章　连接池耗尽：堵死的不是数据库

> 卷一 · 请求进来

**本章要回答**：为什么下游监控显示 20ms，我的接口却是 3 秒？

**本章你能带走**
- 一个数字：`HttpClient` 默认单路由连接数是 **2**
- 一个估算公式：`perRoute ≥ QPS × RT(秒) × 1.5`
- 一条认知：**"排队时间"不出现在任何下游的监控里，所以它永远是最先被忽略的那一段**

**难度构成**：本章主线【必读】；含【进阶】深挖 1 处；章末「延伸」小节放支线深挖与知识库指针。
---

## 4.1　现场：下游很快，我很慢

现象非常标准，几乎每个团队都遇过一次：

- 订单服务调用库存服务的接口，P99 从 80ms 涨到 2.8s
- 库存服务自己的监控：RT 30ms，CPU 30%，没有慢 SQL
- 订单服务日志：大量 `Timeout waiting for connection from pool`
- 中间件团队说"我们没问题"，业务团队说"我们也没问题"

**两边都对。请求根本没发出去。**

`Timeout waiting for connection from pool` 这句话的字面意思就是：**我在等一个连接，没等到**。所谓"调用下游花了 2.8 秒"，其中 2.7 秒是在自己进程的池子里排队。

> 记住这个判据：**如果下游的 RT 监控正常，而调用方的 RT 异常，先怀疑连接池，不要怀疑网络。**

### 【必读】两边监控都正常的那 2.7 秒去哪了

4.1 说"两边都对，请求根本没发出去"，这句值得再拆一层，因为它是全书复用最多的一类误判。把那 2.8 秒按归属切开：

| 时间段 | 花在哪 | 谁的监控里有 | 谁会为它负责 |
|---|---|---|---|
| 0–2.7s | 在调用方进程里排队等池连接 | 只有调用方的 `pending` 指标 | 没人（默认不采集） |
| 2.7–2.8s | 网络往返 + 下游处理 | 下游 RT、调用方 HTTP 指标 | 下游团队 |

下游团队看自己的 RT 是 30ms，是对的；调用方看接口 P99 是 2.8s，也是对的。**2.7 秒的排队发生在请求离开调用方进程之前，它既不算"下游耗时"，也不算"网络耗时"，更不算"应用处理"**——所以在下游的监控面板上恒等于 0，在调用方的接口总耗时里却占了大头。第一章 1.2 那个 `$request_time − $upstream_response_time` 判据讲的是同一件事，只是排队发生在 Nginx 而不是 HttpClient 池：

```
排队时间 = 调用方总 RT − 下游 RT − 网络 RTT
         = 2800ms − 30ms − 约 1ms ≈ 2769ms
```

**① 一个立刻能用的判据**：如果下游 RT 监控正常、而调用方 RT 异常，**先怀疑连接池，不要怀疑网络**。反过来，若调用方与下游 RT 一起涨，才轮到查下游或网络。这条判据不需要任何新工具，只需要把两处的 P99 摆在同一张图上相减——和第七章 7.6 用"事务 span 总耗时 − SQL span 之和"定位事务里的远程调用，是同一个减法。

**② 为什么"排队"永远是最先被忽略的一段。** 因为它不产生日志、不产生异常、不消耗 CPU，只消耗"等待"。多数监控体系采集的是**事件**（一次 SQL、一次 HTTP、一次 GC），而排队是"什么都没发生"的一段时间；没有事件，就没有 span，没有 span，默认视图里就看不到。要让它显形，只能主动埋两类数据：池子的 `pending` 计数（4.6）和 `acquire` 耗时 P99。**pending > 0 是比接口 P99 早 1~3 分钟的信号**，因为排队总是先发生、后传导到 RT。

**③ 一个反常识点：调大池子往往不是最优解，甚至不是正确解。** 多数人看到"等连接"就把 `maxTotal` 从 20 调到 200，症状确实缓解了，但 4.3 那三个上限会依次找上门：下游的线程池、数据库的 `max_connections`、以及每个连接占用的内存。更关键的是，**如果池子是被"事务里做远程调用"占满的（4.5、第七章），调大池子只是让更多请求一起挤在下游的慢接口上**，故障从"调用方排队"变成"下游被打挂"。这类场景真正的解法是缩短每个请求占用连接的时间，而不是增加连接数量。判别方法也简单：看 `active` 是随流量起伏（容量不足）还是持续顶满不回落（泄漏 / 长事务占用，4.6 的五步取证）。

**④ 现场的最小修复与验收**。那次最终改了三处：`defaultMaxPerRoute` 按 `500 × 0.2 × 1.5 = 150` 重算、加 `validateAfterInactivity` 防半开连接、把 `pending` 指标接进告警。压测复现时用恒定速率（4.7 的 wrk2 命令）再打一遍，`pending` 归零、P99 从 2.8s 回到 90ms。**修复只动了配置，但因为有了 `pending` 这个观测点，下一次池子再满时不用再靠两边团队互相举证。**

> 接口慢只有三种可能：算得慢、等得慢、走得慢。连接池属于"等"，而"等"从来不出现在下游的监控面板上——这句话的具体含义，就是上面那张表里"谁会为它负责"那一列写着"没人"。

**当时怎么误判的**：第一反应是"下游库存服务慢了/挂了"——可库存服务自己的监控 RT 30ms、CPU 30%，活得好好的；又去查网络，ping 和 RTT 都正常，也排除了。走了条死路：有人一头扎进库存服务的慢 SQL 和 GC，想把"下游"治好，方向全反了；还有人抓了订单服务的 jstack，却只盯着"有没有死锁"看，没注意大批线程都停在 `ConcurrentBag.borrow` 等连接，把真线索放过去了。真正扭转方向的是订单服务日志里那行 `Timeout waiting for connection from pool`，再对着池子的 `pending` 指标一看——2.7 秒全在调用方自己进程里排队，根本没发出去。教训：下游监控正常、调用方却异常时，先怀疑连接池，别怀疑网络。

## 4.2　罪魁祸首：1990 年代的默认值

```java
// Apache HttpClient 的默认值是给示例代码用的
CloseableHttpClient client = HttpClients.createDefault();
// 等价于：
// maxTotal = 20
// defaultMaxPerRoute = 2      ← 单下游只能同时 2 个连接
```

`defaultMaxPerRoute = 2` 意味着：对同一个下游，同一时刻最多 2 个请求在跑，其余全部排队。

算一下：下游 RT 200ms，2 个连接 → 理论吞吐 **10 QPS**。而你的接口有 500 QPS。剩下的 490 QPS 全在排队，排 49 秒——实际上早就超时了。

同类默认值还有：

| 客户端 | 默认 | 问题 |
|---|---|---|
| Apache HttpClient 4 | `maxTotal=20`、`perRoute=2` | 单下游 2 并发 |
| OkHttp | `maxIdleConnections=5`、`keepAlive=5min` | 并发高时频繁建连 |
| RestTemplate（Simple） | 无连接池，每请求新建连接 | 无复用，TIME_WAIT 堆积 |
| HikariCP | `maximumPoolSize=10` | 对高并发服务偏小（但默认值本身合理） |
| Tomcat | `maxThreads=200`、`acceptCount=100` | 200 线程打满后请求在 acceptCount 排队 |

## 4.3　池子该多大：一个能算的公式

```
单路由连接数 ≥ 目标 QPS × 下游 RT(秒) × 安全系数(1.5)
```

例：500 QPS × 0.2s × 1.5 = **150**。

这是利特尔法则（Little's Law）的直接应用：`并发数 = 到达率 × 停留时间`，写成标准式就是 `L = λ × W`。本书把 Little's law 的"主场"定在本节，符号统一如下，其它章只引用、不重推：

| 符号 | 含义 | 在本章 |
|---|---|---|
| `L` | 系统内平均在途/并发数 | 需要的连接数 |
| `λ`（lambda） | 平均到达率（如 QPS） | 请求到达的速率 |
| `W` | 平均停留/服务时间 | 单次请求占用连接的时长 |

连接数就是 `L`。同一个 `L = λ × W` 会反复出现：线程池队列长度（第 9 章）、锁等待占用的连接与线程（第 14 章）、雪崩放大（第 2 章）、GC 停顿期间的请求堆积（第 25 章）——公式与符号一律以本节为准。连接数就是"并发数"。连接数就是"并发数"。

```java
// ✅ 按公式估算，并暴露监控
PoolingHttpClientConnectionManager cm = new PoolingHttpClientConnectionManager();
cm.setMaxTotal(300);                        // 所有下游加起来
cm.setDefaultMaxPerRoute(150);              // 单个下游
cm.setValidateAfterInactivity(TimeValue.ofSeconds(2));   // 复用前校验，防半开连接

CloseableHttpClient client = HttpClients.custom()
        .setConnectionManager(cm)
        .evictExpiredConnections()
        .evictIdleConnections(TimeValue.ofSeconds(30))
        .build();
```

`setValidateAfterInactivity` 这一行不能省。下游重启、LB 悄悄掐掉空闲连接之后，池子里会留下"看起来活着、实际已死"的连接。第一次用它就报 `Connection reset`——而这类错误是**偶发**的，最容易被当成"网络抖动"糊过去。

### 【必读】但池子不是越大越好

三个上限必须一起看：

1. **下游的容量**。给 10 个调用方各配 300 连接，下游就要承受 3000 并发——它可能只有 200 个线程。**你只是把排队从自己进程挪到了下游。**
2. **数据库的连接上限**。MySQL `max_connections` 默认 151。10 个实例各配 50 = 500，直接打满。
3. **内存**。每个连接有缓冲区，几百个连接不算多，但也没必要。

> 池大小是一个**跨团队的约定**，不是单方面的调参。定下来要写进容量文档：这个服务对下游的最大并发是多少。

### 【进阶】Hikari 池容量公式：从 Little's law 推到默认值 10

4.3 给了 HTTP 侧的 `QPS × RT × 1.5`，这一节补数据库侧。HikariCP 官方 wiki 的"About Pool Sizing"给了一条经验公式：

```
connections = (core_count × 2) + effective_spindle_count
```

它不是拍脑袋，可以从"一次服务里 CPU 干活与等 IO 的比例"推出来。设一次 SQL 的服务时间 `W = C + I`（C 是 CPU 时间，I 是等磁盘/网络的时间），单核要跑满需要同时有 `W / C = 1 + I/C` 个连接在工作；N 核就是：

```
L ≥ N × (1 + I/C)
```

机械盘时代 `I/C` 很大，经验上约等于 `N × 2 + 磁盘可并行数`（每个 spindle 同时只能服务一个 IO）。代进现场那台 4 核、SSD 的机器（`effective_spindle_count ≈ 1`）：

```
L = 4 × 2 + 1 = 9  →  取 10
```

**这就是 `maximumPoolSize` 默认值 10 的由来——多数人以为它是"给小项目随便定的保守值"，实际它是按当年一台 4 核机器的磁盘并行度算出来的。** 换句话说，默认值不是让你照抄的，是让你按自己机器的 `N` 和 `I/C` 重算的。

另一条更贴合业务的推法用 Little's law：`L = λ × W`。目标 1000 QPS、单事务内 SQL 累计 `W = 8ms`：

```
L = 1000 × 0.008 = 8 个连接（纯数据库时间）
+ 事务里其它开销、峰值余量 ×1.5  →  12~15
```

两条路殊途同归：**池子大小 = 并发数，而并发数由"到达率 × 服务时间"决定，与"我想开多少"无关。** 4.3 那个 HTTP 公式 `QPS × RT × 1.5` 其实是同一个 `L = λ × W` 换了个名字。

实测方法比公式更重要，因为 `I/C` 你测不准：

```bash
# ① 阶梯调池：maximumPoolSize 依次取 10/20/40/80，每档恒定速率压 3 分钟
for p in 10 20 40 80; do
  echo "=== pool=$p ==="
  wrk2 -t8 -c200 -d180s -R1000 --latency http://localhost:8080/api/order | tee "pool_$p.log"
  curl -s http://localhost:8080/actuator/metrics/hikaricp.connections.pending >> "pool_$p.log"
done
```

判据写在曲线上，不写在配置里：

| 观察 | 结论 |
|---|---|
| `pending > 0` 且 P99 随池增大而下降 | 池子确实不够，继续加 |
| 加池后 QPS 不再涨、P99 反而升 | 已过拐点，瓶颈转到下游（下游 `Threads_running` / 锁竞争） |
| `active` 持续等于 max 且不回落 | **不是容量不足，是泄漏**（4.4、下一节取证） |
| `hikaricp.connections.timeout > 0` | 已经有人在报障了 |

池子不是越大越好，这句能算：10 个实例各配 80 连接 = 800，MySQL `max_connections` 默认 151，直接打满；就算调大上限，InnoDB 并发线程、锁竞争、上下文切换也会让 QPS 在某个点后掉头向下。**池大小是跨团队的约定，不是单方面调参**（4.3 已写过，这里给出它的量化上限）。

## 4.4　另一条路径：连接泄漏

池子够大了还是耗尽？那是漏了。

```java
// ❌ 拿了不还
CloseableHttpResponse resp = client.execute(req);
String body = EntityUtils.toString(resp.getEntity());
// resp 没 close → 连接被这个响应对象一直持有

// ✅ try-with-resources
try (CloseableHttpResponse resp = client.execute(req)) {
    return EntityUtils.toString(resp.getEntity());
}
```

数据库侧同理，但 Spring 帮我挡了大部分（`@Transactional` 会正确释放）。真正容易漏的是**手动 `getConnection()`** 和**流式查询未关闭**：

```java
// ❌ 手动拿连接，异常路径漏 close
Connection c = dataSource.getConnection();
Statement s = c.createStatement();
ResultSet rs = s.executeQuery("select ...");
// 抛异常 → 三个都没关 → 连接永久占用
```

判断是否泄漏，看两个指标：**活跃连接数持续等于 max，且不回落**；**租借时长 P99 持续上涨**。有这两个就是泄漏，不是容量不足。

### 【必读】四个 timeout 各管一段

4.4 讲"借连接要等多久"，但 Hikari 里有四个名字都带 timeout 的配置，管的完全不是一回事。调错一个，症状会变得更难懂（第七章 7.4 第四步列的是**跨组件**的四个超时，这一节是**同一个池内部**的四个）：

| 配置 | 默认值 | 谁在等 | 超时后发生什么 | 约束 |
|---|---|---|---|---|
| `connectionTimeout` | 30000ms | 业务线程等池里空出连接 | 抛 `SQLTransientConnectionException`，**根本没进事务** | 最小 250ms |
| `validationTimeout` | 5000ms | 借出前探活连接 | 判定不可用，丢弃再借 | 必须 `< connectionTimeout` |
| `idleTimeout` | 600000ms | 空闲连接留多久 | 回收超出 `minimumIdle` 的空闲连接 | 仅当 `minimumIdle < maximumPoolSize` 生效 |
| `maxLifetime` | 1800000ms | 一条连接无论多忙能活多久 | 退役，关闭重建 | 必须 `< 链路里最短的空闲断连阈值` |

```yaml
spring:
  datasource:
    hikari:
      maximum-pool-size: 20
      minimum-idle: 10                 # < max，idleTimeout 才生效
      connection-timeout: 3000        # 3s 借不到就失败，别让线程干等 30s
      validation-timeout: 1000        # 必须 < connection-timeout
      idle-timeout: 600000
      max-lifetime: 1740000           # 29min，见下方 wait_timeout 的坑
      keepalive-time: 120000          # 4.x+，定期探活，防中间设备静默掐连接
      leak-detection-threshold: 2000  # 下一节的取证开关，ms
```

几个必须知道的约束与反常识点：

- **`connectionTimeout` 超时抛的是 `SQLTransientConnectionException`，此时事务一次都没开。** 把它和 `@Transactional(timeout=3)` 混为一谈，会去查"事务为什么超时"而永远查不到——第七章 7.4 那张表里，这一行正是"根本没进事务"。
- **`idleTimeout` 不是"连接空闲 10 分钟就关"。** 默认 `minimumIdle = maximumPoolSize`，池子从不缩容，这个配置**默认不生效**。只有显式把 `minimumIdle` 调小，它才开始工作。
- **`maxLifetime` 要小于链路里最短的那个空闲超时。** MySQL `wait_timeout` 默认 28800 秒（8 小时），但云厂商 LB / 防火墙常把空闲连接 350 秒掐掉，而默认 `maxLifetime` 是 30 分钟——连接会"看起来活着、实际已死"，复用时偶发 `Connection reset`。这正是 4.3 强调 `validateAfterInactivity` 的数据库版。

```bash
# 取证：把两处超时摆在一起，取最小值定 maxLifetime
mysql -e "SHOW VARIABLES LIKE 'wait_timeout'; SHOW VARIABLES LIKE 'interactive_timeout'"
# 云厂商 SLB / NAT 空闲断连阈值 → 问网络组，常见 350s / 900s
```

> 多数人以为"超时配置就是别让请求等太久"，实际池里这四个 timeout 分属四个完全不同的时机：**借连接、探活、回收、退役**。把它们当同一个旋钮调，最常见的后果是 `validationTimeout > connectionTimeout`，Hikari 启动直接抛 `IllegalArgumentException` 拒绝配置——好在这是少数会明确报错、而不是静默出错的地方。

## 4.5　第三类：连接被"事务"占着不放

这类最隐蔽，因为池子配置完全正确。

```java
@Transactional(rollbackFor = Exception.class)
public void create(Order order) {
    orderMapper.insert(order);                    // ① 拿到连接，事务开启
    inventoryClient.deduct(order.getSku());       // ② HTTP 调用，可能 3 秒
    orderItemMapper.insertBatch(order.getItems()); // ③ 还用同一个连接
}
```

第 ② 步的三秒里，**数据库连接一直被第 ① 步占着，行锁也一直没释放**。

后果是双重的：

- 数据库连接池被"慢业务"占满 → 其他请求拿不到连接
- 行锁持有 3 秒 → 其他事务在这行上等锁 → 连锁排队

这就是第六章讲事务时反复强调的那句：**事务里不要做远程调用**。它不是"规范洁癖"，它直接决定连接池和行锁的吞吐。

### 【必读】连接泄漏的取证命令序列

池子配置全对、`pending` 却持续大于 0，就是漏了。别先调大池子——那只是把泄漏爆发的时间往后推。按下面五步走，从"现象"到"哪一行代码没还连接"，每步两分钟：

**① 先开泄漏检测，让池子自己报出借连接的代码位置**

```yaml
spring.datasource.hikari.leak-detection-threshold: 2000   # ms，生产可开，开销很小
```

超过 2 秒未归还，Hikari 打一条 WARN：`Connection leak detection triggered for ... on thread http-nio-8080-exec-7`，并附带**借连接时的堆栈**。这条堆栈直接指向 `getConnection()` 的调用点，是整条取证链里信息量最大的一行。注意边界：最小值 2000ms，且不能大于 `maxLifetime`。

**② 看指标，确认是"不回落"而不是"容量不足"**

```bash
curl -s http://localhost:8080/actuator/metrics/hikaricp.connections.active
curl -s http://localhost:8080/actuator/metrics/hikaricp.connections.pending
curl -s http://localhost:8080/actuator/metrics/hikaricp.connections.acquire

# 判据：active 持续 == maximumPoolSize 且不回落 = 泄漏；
#       随流量起伏 = 容量不足。timeout > 0 说明已经有人在报障了
```

**③ jstack 看线程停在哪儿**

```bash
jstack -l <pid> | grep -A 20 'HikariPool\|getConnection' | head -80
# 大量线程停在 ConcurrentBag.borrow / LockSupport.park → 在等连接
# 泄漏线程则停在业务方法（借了没还的地方），对照 ① 的堆栈找同一帧
```

**④ 数据库侧交叉验证**

```sql
SHOW PROCESSLIST;                       -- 大量 Sleep 且 Time 很长 = 借了没还/长事务
SELECT trx_id, trx_started, trx_mysql_thread_id, trx_query
  FROM information_schema.innodb_trx ORDER BY trx_started;  -- 老事务 = 4.5 那类
```

**⑤ 定位后回到代码**：手动 `getConnection()` 的异常路径、流式查询未关 `ResultSet`、`@Transactional` 里做了远程调用（4.5）。前三步是"确认漏了"，第四五步是"漏在哪"。**顺序反过来先抓 dump，会得到 200 个一模一样的 `WAITING`，看不出谁先谁后**（第七章 7.6 的取证顺序是同一条规矩）。

### 【必读】交叉引用：事务占连接对应第七章

4.5 结尾写"这就是第六章讲事务时反复强调的那句"，这里的章号需要修正：第六章（v2-06）讲的是**事务为什么没生效**（自调用、异常没逃出、传播行为），而"事务里不要做远程调用、行锁与连接被持有到远程返回"是**第七章**（v2-07）整章的主题，7.3 ③ 更是直接点名"先满的往往不是线程池，是连接池"。本书的交叉引用一律按卷二的实际章号走：

| 现象 | 该翻哪一章 |
|---|---|
| 连接池被"慢业务"占满 | **第七章** 7.2–7.4（事务边界 / 远程调用移出事务） |
| 事务压根没开 | 第六章（代理、五问定位法） |
| 多个事务互相等锁 | 第十四章（死锁与锁等待） |
| 池子容量与排队 | 本章 4.3、第一章 1.2（`$request_time` 差值） |

一处章号的误差看着很小，但排障时按它去翻第六章，会花半小时看"自调用与代理"，而真正要找的"把 HTTP 调用挪出事务"在第七章。**交叉引用不是装饰，它是排查路径的一部分**——这也是全书坚持用"第 N 章"把 27 章串起来的原因。

## 4.6　监控：三个必须暴露的指标

池子出事前一定有征兆，前提是你看了：

```java
// HttpClient：暴露到 Micrometer
Metrics.gauge("http.pool.leased", cm, m -> m.getTotalStats().getLeased());
Metrics.gauge("http.pool.pending", cm, m -> m.getTotalStats().getPending());
Metrics.gauge("http.pool.available", cm, m -> m.getTotalStats().getAvailable());
```

| 指标 | 含义 | 告警阈值 |
|---|---|---|
| `leased` | 已借出连接数 | 持续 > 80% max |
| `pending` | **在排队等连接的请求数** | **> 0 持续 1 分钟** |
| `available` | 空闲连接 | 持续 = 0 |
| `acquire 耗时 P99`（HikariCP `connectionAcquireMillis`） | 拿连接花了多久 | > 50ms |

`pending > 0` 是最有价值的信号——它意味着**已经有请求在排队了**，此时接口还没明显变慢，但再涨一点就雪崩。这个指标通常比接口 P99 早 1–3 分钟报警。

HikariCP 的指标名要记一下，因为它是 Spring Boot 默认连接池：

```
hikaricp.connections.active
hikaricp.connections.pending        ← 排队数
hikaricp.connections.acquire        ← 获取耗时
hikaricp.connections.timeout        ← 超时次数，> 0 就是事故
```

`hikaricp.connections.timeout > 0` 基本等同于"已经有人在报障了"。

### 【必读】用阶梯压测实测池容量（可运行）

公式给的是起点，验收要靠压测。把 4.4 的公式、4.6 的指标和第十二章压测篇的恒定速率模式合成一条能跑的命令序列：

```bash
# ① 压测前先把指标看板打开（/actuator/prometheus 盯 active/pending/acquire/timeout）
# ② 恒定速率梯度加压：R 固定、只升并发，干净地看出"排队从哪档开始"
for r in 200 400 800 1200; do
  echo "=== R=$r ==="
  wrk2 -t8 -c200 -d180s -R$r --latency http://localhost:8080/api/order | tee "r_$r.log"
  curl -s http://localhost:8080/actuator/metrics/hikaricp.connections.pending >> "r_$r.log"
  sleep 30        # 冷却，避免上一档的排队污染下一档
done
```

为什么必须用 `-R` 恒定速率：wrk 默认"发完立刻发下一个"，服务变慢时发压速率自动下降，排队被客户端自己怂掉掩盖（Coordinated Omission），测出来的 P99 偏乐观。恒定 RPS 才能模拟"真实流量不变、服务变慢"的容量语义。

判据（把 4.4 那张表写成验收条件）：

| 观察 | 结论 | 动作 |
|---|---|---|
| `pending` 从 0 变正的第一档 R | 池容量拐点 | 按 `L = λ × W` 重算 `maximumPoolSize` |
| 加池后 P99 继续降、QPS 继续涨 | 还没到拐点 | 继续 |
| 加池后 QPS 平台、下游 `Threads_running` 升高 | 瓶颈转到数据库 | 停手，别再加池 |
| `active` 不回落、`timeout > 0` | 泄漏不是容量 | 转 4.6 的取证序列 |

```java
// ✅ 把"pending > 0 持续 1 分钟"做成会失败的告警，而不是人工看板
Gauge.builder("hikaricp.connections.pending", pool,
              p -> p.getHikariPoolMXBean().getThreadsAwaitingConnection())
     .register(registry);
// 告警：pending > 0 持续 1min → 早于接口 P99 变慢 1~3 分钟（4.6 已写过这条）
```

> 一次只改一个变量：调 `maximumPoolSize` 时别顺手改 `connectionTimeout`，否则 P99 的变化分不清是池子大了还是等得久了。这也是第八章 8.6 升级迁移清单里"先在旧版本暴露问题，再升级"的同一个方法论。

## 4.8　一句话总结

> 接口慢，只有三种可能：**算得慢、等得慢、走得慢**。
> 连接池属于"等"，而"等"从来不出现在下游的监控面板上。
