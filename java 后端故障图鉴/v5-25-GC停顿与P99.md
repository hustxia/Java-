# 第二十五章　GC 停顿与 P99 毛刺

> 卷五 · 上线之后

**本章要回答**：平均 RT 只有 30ms，为什么 P99 是 2 秒？

**本章你能带走**
- 一个判据：**P99 毛刺 + 有规律的间隔 = 先看 GC，不要看代码**
- 三种 Full GC 触发原因，各自的解法完全不同
- 一条调参顺序：**先看对象生命周期，再调堆，最后才换收集器**

**难度构成**：本章主线【必读】；含【进阶】深挖 1 处；章末「延伸」小节放支线深挖与知识库指针。
---

## 25.1　现场：每 40 秒一次 2 秒抖动

一个接口的平均 RT 是 30ms，P50 是 25ms，P99 是 2100ms。监控图上是一条**周期性的尖刺**，大约每 40 秒一次。

第一反应是"某个下游接口慢"，于是查了所有 RPC、SQL——都正常，P99 都在 20ms 以内。

转折点是有人注意到：**尖刺的间隔非常规律。** 下游抖动不会这么规律，只有两种东西会：定时任务，或者 GC。

查 GC 日志：

```
[2026-11-08T14:02:11.203+0800][gc] GC(128) Pause Full (G1 Evacuation Pause) 4096M->4096M(4096M) 2143.221ms
```

`4096M->4096M` —— **回收前后堆占用完全一样**。

这是最危险的信号：**Full GC 了，但一个字节都没回收。** 说明老年代里全是活对象，堆已经满了。

### 【必读】4096M->4096M 比 OOM 更危险在哪

25.1 那行日志值得再算一遍，因为它是全书最容易被"看起来只是慢了点"放过的一行：

```text
GC(128) Pause Full ... 4096M->4096M(4096M) 2143.221ms
```

三个数字各说一件事：

| 片段 | 含义 | 判据 |
|---|---|---|
| `4096M->4096M` | 回收前 4096M，回收后 4096M | 回收量 = 0，老年代全是活对象 |
| `(4096M)` | 堆总容量 4096M | 已用 = 总量，堆 100% 满 |
| `2143.221ms` | STW 停顿 2.143 秒 | 整个 JVM 的应用线程被冻住 2.143 秒 |

**多数人以为"Full GC 没抛异常 = 还能撑"，实际是"回收 0 字节"比抛 OOM 更危险**：OOM 会让进程快速失败、被编排拉起、告警响；而这次 Full GC 什么都没回收，却让服务"看起来还在"，接下来每一次分配都会再触发一轮同样无效的 Full GC，系统进入"每次都停 2 秒、每次都回收 0 字节"的循环。

把 2.143 秒换成请求数。设入口 QPS = 2000：

```text
停顿期间被冻住的请求 = 2000 × 2.143 ≈ 4286 个
按 Little's law，L = λ × W（公式与符号见第 4 章）；λ=2000/s、W=2.143s → 瞬时堆积 4286 个请求
若 Tomcat 200 个线程，积压要靠这 200 个线程在恢复后逐步消化
```

这些请求不是"慢了 2 秒"，是**全被按在原地 2 秒，然后在恢复瞬间一起涌进来**——这正是第 26 章"尖峰流量"的一种，只不过尖峰是 GC 自己造的。更要命的是接下来：堆满 + 全是活对象 → 下一次分配几乎必然 `Promotion failed`（25.3）→ 又一轮 Full GC → 最终 `Java heap space`（第 24 章）。`4096M->4096M` 是这条链的第一帧，不是最后一帧。

> 判据一句话：**Full GC 后堆占用不降，就不要再调任何 GC 参数了**，直接去看"谁在持有这 4G"——那是第 24 章的 dump 和 25.6 的无界缓存。GC 线程在这期间会占满 CPU，取证动作按第 23 章的 `top -Hp` 走，别把 GC 线程当成业务热点。

把 2.143 秒再算到 P99 上，才知道它为什么能藏在"平均 RT 30ms"背后。设每分钟请求数 120,000（2000 QPS），每 40 秒一次 Full GC：

```text
受影响的请求 ≈ 2000 × 2.143 ≈ 4286 个
占该分钟比例 = 4286 / 120000 ≈ 3.6%
```

**P99 只取最慢的 1%，这 3.6% 全落在 P99 之后的分位里**，所以 P50（25ms）纹丝不动、平均值被稀释到 30ms，只有 P99 从 90ms 跳到 2100ms。这也是 25.2 说"P99 异常但 P50 正常"的原因：STW 制造的是**一小撮极端慢请求**，不是整体变慢。反过来说，若你的监控只画平均值和 P50，这次 2 秒停顿在图上是完全看不见的——第 26 章会把"看 P99 不看平均值"列为压测纪律，第 27 章则把"监控只覆盖了你想到的维度"列为最后一个母题。



**当时怎么误判的**：P99 飙到 2 秒时，第一反应是"某个下游接口慢了"——把 RPC、SQL 的 P99 全拉出来，都在 20ms 以内，排除。最耽误时间的是"会不会是某个定时任务或冷数据查询"：把调度平台翻了一遍、给慢接口逐个 `trace`，半天没找出一个能解释"每 40 秒一次"的元凶。转折是有人把尖刺的间隔标在监控上，发现它规律得像钟表——下游抖动不会这么准，只有定时任务和 GC 会。拉出 GC 日志一查，正是每 40 秒一轮 `Pause Full`。这一下把方向从"业务代码"扭回"JVM 内存"，后面的 dump 才对路。

## 25.2　P99 毛刺的四种来源

先排除，再优化。P99 异常但 P50 正常，只有四种可能：

| 来源 | 特征 | 判据 |
|---|---|---|
| **GC 停顿** | 周期性、所有接口同时抖动 | GC 日志里有长暂停 |
| 下游长尾 | 只在调用某个下游的接口上出现 | 分接口看 P99，会分化 |
| 锁竞争 | 并发高时出现，低并发正常 | 线程栈里有 BLOCKED |
| 线程池排队 | 与 QPS 正相关 | `active` 打满、`queued` 上涨 |

**GC 的独特之处：它让所有接口一起抖动。** 因为 Stop-The-World 停的是整个 JVM，不管你在处理什么请求。

所以判断方法很简单：

> **如果同一时刻、所有接口的 P99 一起飙，先看 GC。**
> **如果只有部分接口飙，看下游和锁。**

### 【必读】四种来源的判据要能落到一条命令上

25.2 那张表给的是"特征"，但特征要能落到一条可执行的判据上，否则排障时还是靠感觉。把四行各补一列"看什么、什么值算命中"：

| 来源 | 判据（看什么指标） | 什么值算命中 | 一条命令 |
|---|---|---|---|
| GC 停顿 | 同一时刻**所有接口** P99 一起飙 | 各接口 P99 曲线在时间轴上重合 | `grep 'Pause Full' gc.log`、`jstat -gcutil <pid> 1000` |
| 下游长尾 | 分接口看 P99，会分化 | 只有调某下游的接口飙，其余平稳 | APM 按 interface 分组；Arthas `trace` 逐段 |
| 锁竞争 | 低并发正常、高并发才出现 | 线程栈大量 `BLOCKED`，`thread -b` 有锁主 | `jcmd <pid> Thread.print -l` 后统计 `BLOCKED` 行数 |
| 线程池排队 | 与 QPS 正相关 | `active` 打满、`queued` 持续 > 0 | 看线程池 `active/queued` 指标 |

关键是第一行的验证方法：**把 P99 按接口分组画在同一张时间轴上**。GC 是 Stop-The-World，停的是整个 JVM，不管你在处理什么请求，所以所有接口的尖刺必然在同一秒出现；下游、锁、线程池排队都不会这么齐。这也是 25.2 那句"所有接口一起抖先看 GC"能落地的原因——它不是经验，是可证伪的判据。

一个反常识点在第四行：**线程池排队的 P99 毛刺，CPU 往往不高**。线程都在等，没人在算；如果这时你按第 23 章去 `top -Hp` 找热点线程，会一个 99% 的 nid 都找不到。找不到热点，本身就是"这不是 CPU 问题"的证据，方向该切回队列和连接池（第 4 章、第 9 章）。

"所有接口一起抖"要落地，得先把时间轴对齐到同一个桶。做法是给每个接口的 P99 按秒聚合成序列，再比两条曲线是否在同一秒起跳：

```text
接口 A P99(秒):  25 24 26 2100 25 24 ...
接口 B P99(秒):  22 23 24 2090 23 22 ...
                          ↑ 同一秒
若 A、B、C 在同一秒同时跳、且幅度相近 → GC / STW
若只有 A 跳、B/C 平稳                 → 下游长尾或 A 独有的锁
```

GC 的判据不是"都变慢了"，是**"变慢发生在同一秒、且幅度相近"**。定时任务也会制造周期性尖刺，但它只影响跑任务的那个接口；GC 不挑接口。把这一步做进监控看板，就不用每次靠肉眼盯曲线——**这也是 25.4 那张日志表里"墙钟时间"那一列的用途：它是和监控时间轴对齐的锚点**。



## 25.3　三种 Full GC，三种解法

### 【必读】① 老年代真的满了

```
Full GC 前 4096M → 后 3900M      ← 回收了一点，但很快又满
```

这是**容量不足或泄漏**。回到第 24 章：看 Full GC 后的基线是否抬升。

- 不抬升 → 容量不足，加堆或减少对象
- 逐步抬升 → 泄漏，查 dump

### 【必读】② 晋升失败（Promotion Failed）

```
[Full GC (Promotion failed) ...]
```

年轻代的对象要晋升到老年代，但老年代没有连续空间。原因通常是**老年代碎片化**，或 Survivor 太小导致对象过早晋升。

解法：加大 Survivor（`-XX:SurvivorRatio`）、减小 `-XX:MaxTenuringThreshold`（让对象早点晋升，减少复制成本），或直接换 G1（G1 按 region 管理，没有连续空间要求）。

### 【必读】③ 元空间 / 显式调用

```
[Full GC (Metadata GC Threshold) ...]      ← 元空间触顶
[Full GC (System.gc()) ...]                ← 有人手动调了
```

`System.gc()` 必须禁用：

```bash
-XX:+DisableExplicitGC
```

很多第三方库（尤其是 NIO/DirectByteBuffer 相关）会调 `System.gc()` 来回收直接内存。加上这个参数后，直接内存要靠 `-XX:MaxDirectMemorySize` 限制 + 正确的 `cleaner` 调用来释放。


（三种 Full GC 的完整判据表、System.gc() 的堆外链路与 CMS 版本区间，见章末附录。）
## 25.4　GC 日志怎么看

JDK 9+ 统一日志（JDK 17 的标准写法）：

```bash
-Xlog:gc*:file=/var/log/gc.log:time,uptime,level,tags:filecount=5,filesize=50m
```

关键几行：

```
[14:02:11] GC(128) Pause Young (Normal) (G1 Evacuation Pause) 2048M->512M(4096M) 32.441ms
[14:02:51] GC(129) Pause Full (G1 Evacuation Pause) 4096M->4096M(4096M) 2143.221ms
```

读法：

| 位置 | 含义 | 关注点 |
|---|---|---|
| `Pause Young` / `Pause Full` | 类型 | Full 是重点 |
| `2048M->512M` | 回收前 → 后 | **回收后不降 = 满** |
| `32.441ms` | 停顿时间 | Young > 200ms 或 Full > 1s 要处理 |
| `(G1 Evacuation Pause)` | 触发原因 | `Promotion failed` / `Metadata` / `System.gc()` |

三个关键指标（用 GC 日志分析工具或 `jstat`）：

```bash
jstat -gcutil <pid> 1000 20
#  F    YGC   YGCT     FGC    FGCT      GCT
# 12.3   842  12.441     3    6.423   18.864
```

- `FGC` 增长快 → Full GC 频繁
- `FGCT`（Full GC 总时间）占比超过 5% → 已经影响性能
- `GCT` / 运行时间 > 10% → 严重问题


（JDK 17 统一日志逐列拆解、tag 收窄与生效验证，见章末附录。）
## 25.5　调参顺序：别一上来就换 ZGC

最常见的错误：P99 高 → 直接上 ZGC。结果发现**吞吐掉了 20%，问题还在**（因为根因是内存泄漏，不是收集器）。

正确的顺序：

```
① 先确认对象生命周期
   短命对象多 → 年轻代大一点（-Xmn 或 G1 的 -XX:G1NewSizePercent）
   长命对象多 → 老年代要大，或查泄漏

② 再看堆总大小
   容器 limit 的 60~70%，留出元空间/直接内存/线程栈

③ 再看停顿目标
   G1：-XX:MaxGCPauseMillis=200（默认 200，别设太小，会导致频繁 Young GC）

④ 最后才换收集器
   低延迟（P99 敏感）→ ZGC / Shenandoah
   高吞吐（批处理）   → Parallel
   均衡（绝大多数）   → G1（JDK 9+ 默认）
```

各收集器的定位（JDK 17/21）：

| 收集器 | 停顿 | 吞吐 | 堆大小 | 适用 |
|---|---|---|---|---|
| Serial | 秒级 | 高 | < 100M | 小应用、单核 |
| Parallel | 百毫秒~秒 | **最高** | 中等 | 批处理、离线任务 |
| **G1** | 几十~几百毫秒 | 中高 | 4G~32G | **默认选择** |
| ZGC | **< 1ms**（JDK 21 分代 ZGC） | 中（略低） | 大堆 32G+ | P99 极敏感 |

ZGC 在 JDK 21 之后已经分代化，停顿基本在 1ms 以内，代价是吞吐略降、内存占用略高（需要预留染色指针和多视图映射空间）。**它是"已经优化到极致但还差那几十毫秒"时的最后一张牌**，不是第一张。

### 【必读】调参三段：先止血、再降分配速率、最后才换 ZGC

25.5 给了四步顺序，把它压缩成三段，按"改动代价从低到高"排，每段都有明确的退出条件：

```text
① 止血（几小时~当天）
   禁用 System.gc()、给缓存加 maximumSize、堵住一次性全量查询
   退出条件：Full GC 不再出现，P99 回到可接受区间
   不碰：堆大小、收集器、G1 内部参数

② 降分配速率（一周内，靠数据）
   用 JFR / async-profiler 火焰图找"谁在不停造对象"
   指标：分配速率 GB/s、Young GC 频率、晋升速率
   退出条件：同样流量下分配速率下降，Young GC 次数减少

③ 最后才换收集器（前两段做完仍不达标）
   只剩 GC 停顿本身、且 P99 对几十毫秒敏感，才考虑 ZGC
   换之前必须先有 ①② 的基线数字做对照
```

第 ② 段最容易被跳过，也最值钱。GC 停顿是"症状"，**对象分配速率才是病因**：设分配速率 `A`、堆有效容量 `H`、每次 Young GC 存活率 `s`，稳态下 Young GC 间隔近似 `T ≈ H×(1−s)/A`。`A` 翻倍，`T` 减半，GC 次数翻倍——调任何参数都不如把 `A` 降下来。25.6 那个无界缓存，本质就是 `s` 被推到接近 1、`H` 被吃满，于是 `T→0`。


（G1 关键参数"什么时候动、动错会怎样"的清单，见章末附录。）
版本区间必须记，否则照抄会翻车：**JDK 21 上 `-XX:+UseZGC` 默认仍是非分代，要显式加 `-XX:+ZGenerational`（JEP 439）；JDK 23 起分代成为默认（JEP 474），JDK 24 移除非分代模式（JEP 490），`ZGenerational` 参数作废**。知识库里有一处写"分代 ZGC 是 JDK 21 现代默认"，是错的——按 JEP 439，JDK 21 必须显式开启，本章以此为准。**多数人以为"换 ZGC 能解决所有延迟问题"，实际它只换掉 GC 停顿，换不掉锁竞争、慢 SQL、线程池打满（第 4、9、13 章）**，而且读屏障会带来几个百分点的吞吐损耗。它是"已经优化到极致、还差那几十毫秒"时的最后一张牌。

"一次只改一个变量"也有反面教材：有人同时把 `MaxGCPauseMillis` 从 200 调到 50、把堆从 8G 加到 12G、又换上 ZGC，一周后 P99 确实降了，**但没人知道是哪一步起的作用，也没人敢把这套参数复制到别的服务**。三个变量一起动，前后数字失去了可比性，等于把 25.6 那张对比表作废。正确做法是每段留一组基线数字：止血前后比停顿、降分配速率前后比 GB/s、换收集器前后比 P99 与吞吐；**任何一组数字变差，就只回退那一个变量**。第 26 章讲压测"找拐点"时同样要求每档只改并发这一个变量，道理完全一致。



## 25.6　一个真实案例的调参过程

回到开头的故事。`4096M->4096M`，说明堆满了没得回收。

排查顺序：

**① 先抓 dump 看是什么占了 4G**

MAT 打开，`Dominator Tree` 第一行：

```
com.demo.cache.LocalCache  →  3.2 GB
  └─ ConcurrentHashMap$Node[]  →  3.1 GB
```

**一个本地缓存没有设上限。**

```java
// ❌ 无界缓存
private final Map<String, Product> cache = new ConcurrentHashMap<>();
```

```java
// ✅ 有界 + 过期
private final Cache<String, Product> cache = Caffeine.newBuilder()
        .maximumSize(10_000)
        .expireAfterWrite(Duration.ofMinutes(10))
        .build();
```

**② 改完上线，`4096M->1200M`，Full GC 消失，P99 降到 90ms。**

**③ 再补一步：加监控。**

```java
Metrics.gauge("cache.size", cache, c -> c.estimatedSize());
```

**这就是完整链路**：P99 毛刺 → GC 日志 → dump → 找到无界缓存 → 改代码 → 加监控。全程没有调过一个 JVM 参数。

> **大多数"GC 问题"不是 GC 的问题，是代码的问题。** 调参只能缓解，改代码才能解决。


（一次调参该记的"故障当时/止血后/根治后"三列数字，见章末附录。）
## 25.7　自检清单

- [ ] GC 日志已开启（JDK 17 用 `-Xlog:gc*`），有滚动配置
- [ ] 有 Full GC 次数和停顿时长的告警（FGC > 0 就该看一眼）
- [ ] 知道自己的收集器和停顿目标
- [ ] 所有本地缓存都有 `maximumSize`
- [ ] 显式 `System.gc()` 已禁用（`-XX:+DisableExplicitGC`）
- [ ] P99 毛刺排查时，先看"是否所有接口同时抖"
- [ ] 调参前先看对象生命周期，不是先换收集器
- [ ] 堆不超过容器 limit 的 70%

## 25.8　一句话总结

> GC 停顿是"症状"，对象分配是"病因"。
> 你能调的是参数，但真正要改的是**谁在不停地造对象、谁在不停地留着它们**。

### 三种 Full GC 的判据表

25.3 按"解法"分了三类，排障时更该按"日志里出现什么"反查。三类加上两种常被漏掉的 G1 触发，凑一张判据表：

| 类型 | 日志关键字 | 回收前后特征 | 根因 | 首查动作 |
|---|---|---|---|---|
| 老年代满 | `Pause Full (G1 Evacuation Pause)` | `4096M->3900M`，回收一点又很快满 | 容量不足或泄漏 | 第 24 章看 Full GC 后基线是否抬升 |
| 晋升失败 | `Promotion failed` / `to-space exhausted` / `Evacuation Failure` | Young 后老年代放不下存活对象 | 老年代碎片、Survivor 太小、IHOP 太晚 | 加 `G1ReservePercent`、降 IHOP、查 Humongous |
| 元空间 / 显式调用 | `Metadata GC Threshold` / `System.gc()` | 与堆占用无关，突兀出现 | 元空间触顶、第三方库主动调 | `jcmd VM.metaspace`、`-XX:+DisableExplicitGC` |
| Humongous 分配失败 | `Humongous` 或大对象分配后紧接 Full | 超过单个 Region 一半的对象占满连续 Region | 大数组、大字符串、大缓存 Entry | 拆大对象、调 `G1HeapRegionSize` |
| 并发模式失败 | `Concurrent Mark` 未完成就 `Pause Full` | 并发标记跟不上晋升速度 | IHOP 太晚、并发线程不足 | 降 `InitiatingHeapOccupancyPercent` |

第 ③ 类里 `System.gc()` 有个必须讲清的链路，否则"禁掉它"会引出新问题：

```text
ByteBuffer.allocateDirect / Netty 申请堆外
   → Bits.reserveMemory() 发现超 MaxDirectMemorySize
   → 主动调用 System.gc()，指望触发 Cleaner 回收堆外块
   → 若加了 -XX:+DisableExplicitGC，这一步被吞掉
   → 堆外块只能等下一次自然 GC，泄漏被放大
```

所以 `-XX:+DisableExplicitGC` 不是"加了更安全"，它要**成对使用**：配 `-XX:MaxDirectMemorySize` 给堆外封顶，并确认 NIO/Netty 侧有正确的 `Cleaner` 或显式 `release()`。第 24 章 `Direct buffer memory` 那一行的兜底路径，断的就是这里。CMS 也要顺手提一句版本区间：JDK 9 起弃用（JEP 291）、JDK 14 移除（JEP 363），JDK 17/21 上传 `-XX:+UseConcMarkSweepGC` 只会打印 `Ignoring option ... support was removed` 并静默回退到默认收集器，不是"生效了"。

### JDK 17 统一日志逐列拆给你看

25.4 给了两行样例和一张简表，但 `-Xlog:gc*` 打出来的远不止这些。把一段完整输出摆开，逐列对齐：

```text
[2026-11-08T14:02:11.203+0800][12.483s][info][gc,start     ] GC(128) Pause Full (G1 Evacuation Pause)
[2026-11-08T14:02:11.205+0800][12.485s][info][gc,task      ] GC(128) Using 8 workers of 8 for full compaction
[2026-11-08T14:02:13.346+0800][14.626s][info][gc,heap      ] GC(128) Eden regions: 0->0(24)
[2026-11-08T14:02:13.346+0800][14.626s][info][gc,heap      ] GC(128) Old regions: 1024->1024
[2026-11-08T14:02:13.346+0800][14.626s][info][gc,metaspace ] GC(128) Metaspace: 262144K->262144K(524288K)
[2026-11-08T14:02:13.346+0800][14.626s][info][gc           ] GC(128) Pause Full (G1 Evacuation Pause) 4096M->4096M(4096M) 2143.221ms
[2026-11-08T14:02:13.346+0800][14.626s][info][gc,cpu       ] GC(128) User=15.2s Sys=0.1s Real=2.14s
```

| 列 | 例子 | 读法 |
|---|---|---|
| 墙钟时间 | `2026-11-08T14:02:11.203+0800` | 与监控尖刺对齐的锚点 |
| uptime | `12.483s` | 进程启动后第几秒，算"多久一次"用它 |
| level | `info` | 统一日志级别，`debug` 才出更细的 phase |
| tags | `gc,start` / `gc,heap` / `gc,cpu` | 决定这一行讲什么；`gc*` 表示全开 |
| GC 编号 | `GC(128)` | 一次回收的所有行靠它串起来 |
| 阶段与原因 | `Pause Full (G1 Evacuation Pause)` | `Pause` 即 STW；括号里是触发原因 |
| 堆变化 | `4096M->4096M(4096M)` | 前→后(总容量)，**回收量 = 前 − 后** |
| 停顿 | `2143.221ms` | 应用线程被冻住的时间 |
| CPU | `User=15.2s Sys=0.1s Real=2.14s` | `User/Real ≈ 7.1` 说明 8 个 GC 线程并行摊了 2.14 秒墙钟 |

最后一行很多人跳过，其实它是判"GC 线程有没有抢 CPU"的直接证据：`Real` 是墙钟停顿，`User` 是各 GC 线程 CPU 时间之和。`User/Real ≈ 并行线程数`；若 `User` 远小于 `Real`，说明 GC 线程在等 IO 或被 cgroup 限流（第 23 章 `cpu.stat` 里的 `nr_throttled`）。配置写法与版本区间：

```bash
# ✅ JDK 9+ 统一日志（JDK 17/21 标准写法），滚动保留 10×50M
-Xlog:gc*:file=/data/log/gc.log:time,uptime,level,tags:filecount=10,filesize=50m

# ❌ JDK 8 时代的写法，JDK 9 起已废弃
-XX:+PrintGCDetails -XX:+PrintGCDateStamps
```

`gc*` 里的 `*` 是通配标签，不是"只打 GC"；想少打一点可以用 `gc,heap`、`gc,pause` 精确组合。**日志必须常开**——JDK 9 起 `-Xlog` 的开销可忽略，出了事才开等于没有现场（第 24 章取证同理）。

`gc*` 是全开，生产上可以按目的收窄，少写几行不影响判据：

| tag 组合 | 会打什么 | 用在什么时候 |
|---|---|---|
| `gc*` | 全部，含 `gc,heap`、`gc,cpu`、`gc,phases` | 排障期、压测期 |
| `gc,heap` | 每次回收前后各代占用 | 常开，看基线是否抬升 |
| `gc,pause` | 只打 STW 停顿 | 只想做 P99 时间轴对齐时 |
| `gc+heap=debug` | Region 级明细 | 查 Humongous / Evacuation Failure |

```bash
# ✅ 常开最小集：堆变化 + 停顿，够算"回收量"和"基线"
-Xlog:gc,heap:file=/data/log/gc.log:time,uptime:filecount=10,filesize=50m
```

注意 tag 之间没有空格、`+` 表示加装饰器、`=` 后是 level；写错一个字符，日志会静默什么都不打，比没开更迷惑。**上线后用 `jcmd <pid> VM.flags | grep Xlog` 确认参数真的生效**，别只看启动脚本——这一条和 25.5"改完要用 `VM.flags` 验证"是同一件事。

### G1 关键参数"什么时候动、动错会怎样"清单

G1 关键参数按"什么时候动、动错会怎样"排，别一次改一组：

| 参数 | 管什么 | 什么时候动 | 动错的后果 |
|---|---|---|---|
| `MaxGCPauseMillis=200` | 停顿软目标 | P99 对停顿敏感，且日志确认停顿超标 | 设成 20ms，每次只敢收几个 Region，反而 `Evacuation Failure` → Full GC |
| `InitiatingHeapOccupancyPercent=45` | 并发标记启动的堆占比 | 老年代涨太快、并发标记来不及 | 调太低，并发标记频繁抢 CPU |
| `G1ReservePercent=10` | 预留 to-space | 出现 `to-space exhausted` | 调太高，可用堆变少 |
| `G1HeapRegionSize` | Region 大小（1~32M，2 的幂） | Humongous 对象多 | 乱调会让大对象判定变化，需实测 |
| `-Xmn` | 固定年轻代 | **G1 下不要动** | 直接关掉自适应，`MaxGCPauseMillis` 永远达不到 |

### 前后数字：一次调参该记哪几列

25.6 给了"4096M->1200M、P99 降到 90ms"两个数字，但一次能进复盘的调参记录不止这两个。把"故障当时 / 止血后 / 根治后"三列并排，才知道哪一步真正起了作用：

| 指标 | 故障当时 | 止血后（禁显式 GC + 限流） | 根治后（缓存加上限） |
|---|---|---|---|
| P50 / P99 / P999 | 25ms / 2100ms / 3800ms | 25ms / 460ms / 900ms | 24ms / 90ms / 160ms |
| Full GC 次数/小时 | 90 | 12 | 0 |
| 单次最长停顿 | 2143ms | 380ms | Young GC 42ms |
| Full GC 后老年代基线 | 4096M（不降） | 2800M | 1200M |
| 分配速率 | 1.8 GB/s | 1.8 GB/s | 0.6 GB/s |
| 本地缓存 size | 无限增长 | 无限增长 | 稳定 ≤ 10,000 |

三列之间的差别正好对应 25.5 的三段：止血把"停 2 秒"压到"停 380 毫秒"，但**分配速率一行没变、缓存还在涨**——这说明只买了时间，没改病因；根治那一列 `1.8 → 0.6 GB/s` 才是真正让 Full GC 消失的动作。这也是为什么 25.6 说"全程没有调过一个 JVM 参数"：三列里唯一显著变化的 JVM 侧数字（Full GC 次数、基线）都是被代码改动带着变的。

记录格式也有讲究：**看 P99 不看平均值**（第 26 章会展开），看"Full GC 后基线"看是否阶梯抬升（第 24 章），看 `User/Real` 看 GC 线程有没有被限流（第 23 章）。一次调参只改一个变量、压测条件完全相同、指标前后对比——这三条是 JVM 调优素材里反复强调的闭环，缺一条，数字就没有可比性。

> 把这张表贴进 27.5 的复盘改进项里，"验证方式"一栏就有了具体数字：不是"GC 好转了"，而是"Full GC 次数从 90 降到 0、P99 从 2100ms 降到 90ms、连续观察一个业务高峰无回升"。**能被数字复核的改进项，才是能被验证的改进项。**
