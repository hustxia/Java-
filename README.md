# book/ —— 成书选编层

这里不是知识库，是**一本书的稿件**。素材层仍是上一级目录的 276 篇文档，本目录只做「选取 + 改写 + 排序」。

## 为什么单独一层

知识库是**字典**：按技术分层，平行条目，随手可查。
书是**叙事**：按读者经历排序，有主线、有取舍、有删减。

同一份内容在两种形态下的组织方式不同，但**事实只有一个来源**。所以：

```
素材层  ../01-Java基础/ ... ../17-常见Bug与解决方案/     （不动，继续当知识库用）
   ↓ 选取 + 改写（不是复制粘贴）
选编层  book/v1-02-xxx.md                                （书稿，可自由删改润色）
   ↓ 渲染
产物    PDF / EPUB / 在线版                               （Quarto 一次出齐）
```

**铁律：不要在素材层里改成书的写法**。素材层要保持"可检索、条目化"；书稿里那些为了阅读节奏加的过渡句、复盘叙事、删掉的次要分支，都不该回灌到知识库。

## 稿件元信息约定

每章 md 顶部用 YAML front-matter 声明来源，供渲染脚本排序与追溯：

```yaml
---
book: true
volume: 2
chapter: 6
order: 2-06
title: 事务为什么会静默失效
sources:
  - 17-常见Bug与解决方案/03-Spring事务与AOP失效.md
  - 04-Spring生态/01-Spring Framework/事务管理.md
status: review       # draft | review | final
words: 5235   # 汉字计数，由脚本实测
---
```

渲染时按 `order` 排序，`sources` 用于回查原文，`status` 控制是否进书。

## 目标读者（一句话）

工作 3–5 年、已经在线上扛过责任的 Java 后端。**写给"要负责"的人，不写给"要面试"的人。**

对应取舍：
- 不解释什么是事务，直接讲它为什么失效
- 不追求覆盖全，一个失效根因讲透，比列十个现象有用
- 允许出现"我们当时判断错了"，因为这是这类书唯一值钱的部分

## 渲染

当前用 `build/` 自建流水线（Markdown → 印刷 HTML → Chrome 无头打印）：

```bash
cd book/build && python build.py
```

产物：`book/Java后端故障图鉴-初稿.pdf`（170×240mm，435 页，8.3 MB）。

管线分工：
- `build/merge.py`：27 章 → `_全书合订.md`（去 front-matter、生成目录）
- `build/md2html.py`：27 章 + 前言 → 单文件 `_book.html`（解析 front-matter、转 HTML）
- `build/paginate.js`：浏览器里分页（按固定页高搬块、长代码/表格按行拆）、
  生成**带页码的目录**、页眉（卷名 + 章名）、页脚页码
- `build/book.css`：印刷样式（宋体正文 / 雅黑标题 / Consolas 代码）
- `build/check.py`：改稿后体检（引号归一、落单 `**`、代码围栏、表格列数、words 核对）
- `build/expand_spec.txt`：扩写规范（成书密度、实料类型、技术准确性红线）

改了章节 md 后重跑 `build.py` 即可：合订本、目录页码、页眉页脚一起更新。
以后若接 Quarto，此层可整体替换（front-matter 约定两者兼容）。

3. 坦白程度：保留「我们判断错了三次」，不软化
